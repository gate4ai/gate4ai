# Архитектура секретов gate4.ai

> Версия 0.4, 2026-10-18. Дополняет разделы «Vault (секреты)» и «Изоляция локальных агентов» в [спецификации](specification.md) и [connector-architecture.md](connector-architecture.md).

> **Статус:** спецификация. Решения от 2026-10-13: три уровня — ядро, auth-модули, коннекторы; ядро не знает протоколов аутентификации. Заголовок HTTP ставится целиком по привязке. Формы заполняет ядро через CDP, вход атомарный, без LLM. Решения от 2026-10-18: простой вход — `browser.login {account}` по форме, которую владелец описал в учётке; сложный — коннектор входа (обычный WASM-коннектор) с примитивом `browser.fill_secret`; сценарии и подписи форм не записываются. Экземпляр выбирается аргументом `account`, у каждого экземпляра браузера свой профиль Chrome. Значения хранятся в зашифрованном файле. Отклонённые варианты — в конце документа.

## Что нужно

1. **Ключи в заголовках HTTP и HTTPS** — в запросах коннекторов и локальных агентов в песочнице.
2. **Формы входа на сайтах:** логин, пароль, PIN, одноразовый код.
3. **Несколько экземпляров коннектора, у каждого своя учётка.**
4. **Сохранение новых секретов** без показа агенту и коннектору: регистрация, смена пароля, ключ, показанный один раз, токен из ответа API.
5. **Любые протоколы аутентификации без роста ядра:** SSH, подписи банков, OAuth-потоки, SigV4, ГОСТ. Автор коннектора не должен ждать новую функцию в ядре.

Инварианты (спецификация, «Принципы дизайна»):
- агент никогда не видит значения секретов;
- коннектор не видит значения (исключение `reveal` — только с согласием пользователя, см. ниже);
- секрет уходит только туда, куда привязан;
- значения не попадают в журнал, вывод, доказательства и тесты.

## Три уровня

| Уровень | Видит значение | Что делает | Как меняется |
|---|---|---|---|
| **Ядро** (daemon) | да | хранилище и версии, привязки, граница потока данных, песочница auth-модулей, шаблоны, ввод в браузере, маскирование, журнал | редко; протоколов аутентификации не знает |
| **Auth-модули** (WASM; нативные — позже) | да, но вывести значение может только к адресу привязки | протокол: IMAP LOGIN, XOAUTH2, SSH, HMAC-подписи, SigV4, OAuth-потоки, TOTP, проверка подписи ответа | пакеты магазина с самым строгим ревью; их немного, они переиспользуются |
| **Коннекторы** (WASM; нативные — позже) | нет | логика действий | пакеты магазина; их много |

```
 Агент ──MCP/CLI──▶ Action Pipeline ──▶ Коннектор (без значений)
                                           │ http_request(auth: slot) · conn_open(slot) · browser_fill_secret
                                           ▼
 ┌─ Ядро ──────────────────────────────────────────────────────────────────┐
 │ Vault (vault.age) · привязки · шаблоны · ввод в браузере · маскирование │
 │ журнал secret.use · граница потока данных                               │
 │          │ значение + запрос / соединение       ▲ типизированный итог   │
 │          ▼                                      │                       │
 │   Auth-модуль (WASM): apply / verify / handshake / resolve / refresh    │
 │          │ только bound_http / bound_conn к адресу привязки             │
 └──────────┼──────────────────────────────────────────────────────────────┘
            ▼
       сервер привязки
```

Когда автору коннектора нужен новый протокол, он берёт готовый auth-модуль или публикует свой. Ядро при этом не меняется. Доверие сосредоточено в небольшом наборе модулей, которые переиспользуют многие коннекторы: модуль SSH проверяют один раз, а пользуются им все SSH-коннекторы.

## Модель угроз

| Кто | Чего опасаемся | Чем закрыто |
|---|---|---|
| Агент (prompt injection) | выманить секрет: подставить его в другое место, прочитать из DOM, скриншота или ответа | место подстановки задаёт привязка; режим «секрет на странице»; маскирование |
| Коннектор | получить значение и вывести его на свой сервер или в ответ | значение есть только у ядра и auth-модуля; коннектор получает только типизированный итог |
| Коннектор на том же сайте | попросить ввести пароль в поле, которое видят другие (заголовок темы форума) | пароль — только в `type=password`; текстовые поля — только по подписи формы; каждый ввод в журнале |
| Auth-модуль | вывести значение | сети нет, есть только соединение к адресу привязки; итог для коннектора — типизированный и маскируется; модули проходят строгое ревью |
| Веб-страница | собрать автозаполнение скрытыми полями, подменить origin через iframe | проверка origin документа и фрейма, видимости и типа поля |
| Сервер назначения | отразить секрет обратно в ответе | маскирование ответа, включая производные формы |
| Кто угодно через «сохранить секрет» | подменить рабочую учётку | подтверждение человека, версии с откатом, привязка по месту получения |

**Остаточный риск, который принимаем.** Код, который видит значение (ядро, auth-модуль), может отправить его только на сервер привязки. Если на этом сервере есть место, видимое другим, утечка через него возможна. Ядро делает этот канал узким (типы полей, подписи форм, шаблоны) и видимым (`secret.use` в журнале), но не закрывает его до конца.

## Модель данных

### Учётка

Учётка — именованный набор полей. Каждое поле секретное или публичное (`public: true`, например `username`). У учётки есть версии.

- **Типы учёток в ядре** — только два: `secret` (одно поле `value`) и `login` (`username`, `password`). Их достаточно для шаблонов и форм.
- **Остальные типы объявляет auth-модуль** со схемой полей: `gate4ai/oauth2`, `gate4ai/totp`, `gate4ai/ssh-key`, `acme/bank-hmac-key`. Ядро хранит поля по схеме и не знает, что они значат.
- **Ссылки между учётками:** поле может ссылаться на другую учётку. Например, токен Google ссылается на учётку OAuth-клиента.

### Привязка

Привязка задаёт, куда и как уходит учётка. Каждая привязка указывает **либо шаблон, либо auth-модуль**. Одна учётка может иметь несколько привязок с разными способами:

```yaml
credentials:
  "@github.personal":
    type: secret
    bind:
      - { to: "https://api.github.com", template: { header: { Authorization: "Bearer {{value}}" } } }
      - { to: "https://github.com",     template: { header: { Authorization: "Basic {{base64('x-access-token:' + value)}}" } } }
  "@forum.main":
    type: login
    bind:
      - { to: "https://forum.example", form: true }
  "@server.prod":
    type: gate4ai/ssh-key
    bind:
      - { to: "ssh://prod.example:22", module: gate4ai/auth-ssh@1, host_key: "SHA256:…" }
  "@bank":
    type: acme/bank-hmac-key
    bind:
      - { to: "https://api.bank.example", module: acme/auth-bank-hmac@2, use: ask }
```

Правила:
- `to` — точный origin (схема + хост + порт). Разрешены схемы `https`, `ssh`, `imaps`, `smtps` и т.п. `http` — только для `localhost` в разработке и тестах. Поддомены задаются только явным списком.
- `template` — подстановка без кода (см. «Шаблоны»).
- `form` — ввод в формы браузера (правила — в «Ввод в браузере»).
- `module` — auth-модуль с мажорной версией. Обновление внутри мажорной версии разрешено, смена мажорной требует согласия пользователя.
- Дополнительные параметры модуля (`host_key` для SSH, `token_url` для OAuth) задаются в самой привязке и показываются пользователю.
- `use: ask` — каждое использование ждёт подтверждения человека.
- Без привязки учётка не уходит никуда.

### Экземпляр коннектора

Экземпляр — это коннектор + настройки + слоты учёток. Имя: `<коннектор>.<имя>`. Манифест объявляет слоты и допустимые способы, а пользователь заполняет слоты своими учётками:

```yaml
# манифест коннектора
credentials:
  - { slot: login, types: [login], form: true, bind: ["https://${setting:host}"] }
  - { slot: api,   types: [secret], template: { header: { Authorization: "Token {{value}}" } }, bind: ["https://${setting:host}"] }
  - { slot: mail,  types: [login, gate4ai/oauth2], module: gate4ai/auth-imap@1, bind: ["imaps://${setting:imap}:993"] }
```

```yaml
# конфигурация пользователя
instances:
  jira.acme: { connector: jira, settings: { host: acme.atlassian.net }, credentials: { api: "@jira.acme" } }
  jira.oss:  { connector: jira, settings: { host: issues.apache.org },  credentials: { api: "@jira.oss" } }
  mail.work: { connector: mail, settings: { imap: imap.yandex.ru, smtp: smtp.yandex.ru }, credentials: { mail: "@mail.work" } }
  browser.personal: { connector: browser, settings: { profile: personal } }
  browser.work:     { connector: browser, settings: { profile: work } }
```

- Привязка слота — это шаблон от настроек. Ядро раскрывает его при создании экземпляра и показывает итог («@jira.acme → https://acme.atlassian.net, заголовок Authorization»). Несовместимые тип или способ — экземпляр не создаётся.
- Конфигурация `connectors.<имя>` без экземпляров читается как экземпляр `<имя>.default`.
- Сейчас (без экземпляров) манифест разбирает слоты как `{slot, bind, description, types, fields}` (`types`: `form` — учётка с формой, `via` — с коннектором входа; учётка другого вида слоту не подходит; `fields` — поля, которые коннектор вводит сам); слот связывается с учёткой в `connectors.<имя>.credentials: {login: "@emias"}`, а коннектор передаёт в `browser.login` / `fill_secret` имя слота или алиас.

## Уровень 1. Ядро

### Состав (закрытый список)

1. Vault: учётки, поля по схемам, версии, хранилище `vault.age`.
2. Привязки и их проверка; события `secret.use` и `secret.save`.
3. Граница потока данных: что и куда может отдать auth-модуль.
4. Песочница auth-модулей (wazero, свой ABI функций хоста — как у WASM-коннекторов) и их функции хоста.
5. Шаблоны.
6. TLS: ядро открывает соединения, проверяет сертификаты сервера и предъявляет клиентский сертификат из учётки (`tls: { client_cert: "@bank.cert" }` в привязке).
7. Ввод в браузере и режим «секрет на странице».
8. Источники значений для ввода: поле учётки, `resolve` auth-модуля, коннектор-источник, человек, генерация.
9. Интерактивные примитивы для входа: открыть URL у пользователя, принять redirect на loopback, спросить код через канал подтверждений.
10. Маскирование и журнал.

Новый протокол в этот список не добавляется. Если для протокола не хватает примитива из пунктов 3–9, это повод пересмотреть ABI auth-модуля, а не добавлять функцию для конкретного протокола.

### Проверка при каждом использовании

1. Вызывающий (экземпляр коннектора или запуск агента) имеет доступ к учётке через слот или привязки запуска.
2. Адрес назначения совпадает с `to`.
3. Способ совпадает с привязкой: шаблон, форма или модуль.
4. При `use: ask` действие, внутри которого идёт использование, подтверждено человеком (см. «Политики и подтверждения»).

Иначе — ошибка `secret_denied` и запись в журнал. Каждое использование — событие `secret.use`: алиас, поле, экземпляр или агент, origin, способ, id действия. Значение не записывается никогда.

### Шаблоны

Шаблоны закрывают API, где ключ подставляется как есть или с простым преобразованием. Кода в них нет.

- **Куда:** `header`, `query`, `body_field` (форма или JSON, по точному имени).
- **Выражения:** поля учётки; `base64`, `base64url`, `hex`, `urlencode`, `sha256`, `hmac_sha256(key, msg)`, `now_unix`, конкатенация `+`. Для подписи доступны части запроса: `req.method`, `req.path`, `req.query`, `req.body_sha256`, `req.header["X-…"]`.
- **Ограничения:** нет циклов и условий, размер результата ограничен.
- **Заголовок ставится целиком:** что бы ни прислал клиент, его значение заменяется.
- **Маскирование:** ядро само вычисляет шаблон, поэтому знает итоговые строки и добавляет их в маскирование. Отдельно перечислять производные формы не нужно.

Для подписей сложнее HMAC одной строки (SigV4, JWS, канонизация запроса) нужен auth-модуль.

### Ввод в браузере

Ввод в формы делает доверенный код: до этапа 28 — браузерный воркер ядра, с этапа 28 — нативный пакет `browser` (см. примечание ниже).

> С этапа 28 браузер — нативный пакет `browser` (connector-architecture.md): функции этого раздела — его действия через `service_call` (`browser.fill_secret`, `browser.login`, `browser.capture_secret`); значение учётки пакет получает от daemon только для origin привязки слота.

**`browser_fill_secret(target, ref, opts)`:**
1. Поле берётся по **наблюдённой** ссылке: `observe` на пустой форме или селектор из сценария.
2. Origin верхнего документа и фрейма поля должен совпадать с `to` привязки `form`.
3. Поле должно быть видимым: ненулевой размер, в пределах страницы, не прозрачное, не перекрытое.
4. Проверяется тип поля:
   - `password` и PIN-пароль — только в `input[type=password]`;
   - логин, PIN и код в текстовых полях — только по **подписи формы** (путь страницы + селектор поля). Подпись записывается при первом успешном входе, ввод в другом месте требует подтверждения человека.
5. Ввод через `Input.insertText` или посимвольно через `Input.dispatchKeyEvent` (если так задано в настройках).
6. Поле помечается как содержащее секрет.

**Режим «секрет на странице»** — до навигации верхнего документа или очистки помеченных полей:
- `observe`, `extract` и `act` на естественном языке запрещены (`secret_on_page`);
- разрешены `click`, `press`, `wait` и `fill_secret` по наблюдённым ссылкам; ответ `act` в этом режиме — без текста элемента;
- `text`, `expect_text` и `wait_for_text` не сопоставляются со значениями полей (иначе значение подбиралось бы по ответам «да/нет»);
- значение `input[type=password]` не читается никогда — ни в этом режиме, ни вне его;
- скриншоты: помеченные поля закрашиваются;
- снимки DOM и логи: значения заменяются на `[secret:@alias.field]`;
- смена `type` поля скриптом страницы значение не раскрывает: чтение помеченного поля запрещено.

**Вход по учётке (`browser.login {account}`)** — одно действие без логики: страница входа уже открыта, поля и отправку описал владелец в учётке (константы и секреты), признак успеха — префикс адреса. Ни ветвлений, ни сценариев, ни LLM, ни записи траекторий:

Простую учётку заводит Web UI (**Настройки → Пароли и учётки → Добавить учётку**): адрес страницы входа, логин и пароль. Учётка получает имя по хосту (`@login.example.com`), пароль — в Vault под `<учётка>.password`, поле логина — `input[type=email], input[autocomplete=username], input[name*=login i], input[name*=user i], input[type=text]`, пароль — `input[type=password]`, отправка — Enter; доступ — выбранным агентам (`use`). Сложный вход (несколько шагов, коды, свои селекторы) — в YAML:

```yaml
credentials:
  "@emias":
    bind: ["https://login.mos.ru"]          # точные origin, где разрешён ввод
    form:
      fields:
        - { selector: "#login",    value: "+79001234567" }       # константа: видна в конфигурации и журнале
        - { selector: "#password", secret: "@emias.password" }   # секрет из Vault
      submit: { selector: "#bind" }         # или { press: Enter } в последнем поле
      success: { url_prefix: "https://lk.emias.mos.ru/" }
    use: [connector-dev]                    # профили агентов
    connectors: [lk_emias]                  # коннекторы (вход из их действий)
    prompts: { sms: "Код из SMS" }          # вопросы человеку для fill_secret с source: human
  "@bank":
    bind: ["https://id.bank.example"]
    via: { connector: bank_login, action: login }   # сложный вход — коннектор входа
```

- У учётки либо `form`, либо `via`. Секрет по умолчанию вводится только в `input[type=password]`; в поле другого типа — только с явным `type: text` у поля (логин, PIN в текстовом поле) — это видно владельцу. Подписи форм не записываются: правило поля задаёт владелец.
- Шаги: origin верхнего документа ∈ `bind` (иначе `wrong_origin`); все поля найдены, видимы (ненулевой размер, не прозрачны, в пределах страницы), редактируемы, нужного типа (иначе `form_mismatch`, ничего не вводится); ввод (`Input.insertText`), документ помечается; отправка; ожидание ухода со страницы входа или признака успеха (до 15 с). Ответ: `logged_in` / `submitted` / `still_on_login` (капча, SMS, неверный пароль — человек завершает вход в окне Chrome gate4ai). Значений, текста страницы и DOM в ответе нет.
- **Сложный вход** (несколько шагов, выбор способа, SMS, «запомнить устройство») — не в ядре и не в `browser`, а в **коннекторе входа**: обычный WASM-коннектор с действием `login {account}`, который проходит шаги действиями браузера (`observe` до ввода секретов, `act`, `fill_secret`, `wait`) и возвращает `{status}`. Агент и другие коннекторы всегда вызывают `browser.login(account)`; если у учётки `via`, daemon сам вызывает `<коннектор>.<действие>` с тем же `account` вложенным вызовом (тот же корень и страница, в сеансе агента — его страница). Коннектор входа значений тоже не видит.
- Доступ: агенту — если его профиль в `use`; коннектору — если он в `connectors`, это коннектор входа учётки (`via`) или его слот связан с учёткой (`connectors.<коннектор>.credentials: {login: "@emias"}`, а `bind` учётки — в `bind` слота из манифеста). Иначе `secret_denied` и запись в журнал. Можно ли вызвать `browser.login` вообще, решает политика (класс `write`, в CEL доступен `account`).
- Сайты: страница может находиться на origin из `bind` учёток, доступных вызывающему, даже вне его сайтов — редирект на вход страницу не закрывает. На таком origin ответы `open` / `observe` / `network` содержат `login_required: {account}` — подсказку вызвать `login`.

**`browser.fill_secret {account, field, selector, source}`** — одно поле учётки в элемент страницы, без отправки (примитив коннекторов входа): те же проверки origin и поля. `selector` вызывающего принимается только у коннектора входа учётки (`via`); для учётки с `form` поле задаёт владелец (селектор поля в учётке), а если селектор не задан — только `input[type=password]`. `source: human` — код от человека; поле для него задаёт владелец — поле кода в форме учётки (`{name: sms, selector: "#sms", type: text}` без `value` и `secret`; `browser.login` его пропускает, `fill_secret` вызывается с `field: sms`) — или коннектор входа учётки (`via`) своим `selector`; иначе ответ вводится только в `input[type=password]`: вопрос (владельца из `prompts` учётки или коннектора) приходит в канал подтверждений (уведомление, Web UI «Подтверждения», `gate4ai approvals answer <id>`), ответ сразу идёт в поле и в маскирование ответов, коннектору не возвращается. TOTP — позже: `source` с `resolve` auth-модуля.

**Источники значения для ввода** (`ref`):

| Источник | Пример |
|---|---|
| поле учётки | `{slot: login, field: password}` |
| `resolve` auth-модуля | TOTP: `{slot: otp}` → модуль `gate4ai/auth-totp` вычисляет код |
| коннектор-источник | код из письма: действие `mail.personal.find_code` с полем результата `x-secret: true` |
| человек | SMS или push: вопрос через канал подтверждений, ответ сразу идёт в поле |
| генерация | `opts.generate: {length, charset}` — пароль при регистрации или смене |

Коннектор-источник видит код, потому что сам читает письмо. Поле результата с `x-secret: true` ядро забирает себе и не передаёт агенту.

### Сохранение секретов

| Откуда | Как |
|---|---|
| генерация в форме | `browser_fill_secret(..., generate)` создаёт **черновую** версию; поле «Подтвердите пароль» заполняется с `version: pending`; после проверки успеха — `secret_commit`, при неудаче — `secret_discard` |
| поле страницы | `browser_capture_secret(target, to)`: ключ, показанный один раз |
| ручной вход человека | браузерный воркер видит отправку формы с полем пароля и предлагает в трее «Сохранить для forum.example?» |
| ответ HTTP | `http_request(capture: [{from: "json:$.token", to: {alias, field}}])`; коннектор получает в ответе `[secret:@alias.field]` |
| auth-модуль | `refresh` и обработка ответа возвращают новые поля учётки (OAuth) |
| человек | Web UI, `gate4ai vault set` |

Правила:
- Сохранение — внутреннее действие `secret.save`, по умолчанию с подтверждением человека. Исключение — обновление auth-модулем полей своей же учётки (OAuth refresh): это не новый секрет.
- Привязка новой учётки — origin, где значение получено. Расширить её может только человек.
- Запись в существующую учётку создаёт новую версию. Хранятся 5 предыдущих версий, откат — в Web UI и `gate4ai vault rollback`.
- Коннектор пишет только в учётки своих слотов или создаёт новые в пространстве своего экземпляра: `@<экземпляр>.<имя>`.

### Хранилище и память

- **Метаданные** учёток (типы, привязки, публичные поля, слоты, номера версий) хранятся в конфигурации, с её версиями и откатом.
- **Значения** хранятся в `vault.age`: ключ age в keychain, атомарная запись, версии внутри файла. Keychain остаётся для ключей устройства.
- **В памяти** значения расшифровываются на время одного использования.
- **Маскирование** — автомат Ахо — Корасик по значениям, итогам шаблонов и строкам, которые auth-модули объявили производными (`derived`).
- **Внешние менеджеры** (1Password, Bitwarden) — позже, как отдельный вид расширения — источник значений.

## Уровень 2. Auth-модули

### Что это

Это WASM-модуль, который знает протокол аутентификации. Он получает значение учётки от ядра и действует только через соединения к адресу привязки.

Модули публикуются в магазине отдельным видом пакета. Первые модули пишем мы, они же служат образцами:

| Модуль | Для чего |
|---|---|
| `gate4ai/auth-imap`, `gate4ai/auth-smtp` | LOGIN, AUTH PLAIN, XOAUTH2 |
| `gate4ai/auth-oauth2` | authorization code + PKCE, device flow, обновление токена, перехват token endpoint |
| `gate4ai/auth-google-sa` | JWT сервисного аккаунта с `sub` |
| `gate4ai/auth-totp` | коды TOTP |
| `gate4ai/auth-ssh` | ключ или пароль, проверка ключа хоста, пароль на запрос `sudo` |
| `gate4ai/auth-sigv4` | подпись AWS |

### Экспорты (ABI v1)

| Экспорт | Назначение | Что получает ядро |
|---|---|---|
| `describe()` | имя, версия, объявленные типы учёток (схемы полей), поддерживаемые экспорты, параметры привязки | — |
| `http_apply(req, cred)` | поставить заголовки, подписать запрос | изменённый запрос; ядро проверяет, что изменены только заголовки, query и тело, а адрес — тот же |
| `http_response(req, resp, cred)` | проверить подпись ответа; заменить токены в ответе фиктивными (перехват OAuth) | `{verdict: ok \| invalid, reason_code}`, изменённый ответ, обновления полей учётки |
| `handshake(conn, cred, params)` | пройти аутентификацию на соединении (IMAP, SMTP) | `ok`; соединение передаётся коннектору, модуль из него выходит |
| `transport_open(cred, params)` / `transport_read` / `transport_write` / `transport_close` | протоколы с шифрованием сессии (SSH): модуль остаётся в канале | поток каналов для коннектора |
| `resolve(cred, field)` | вычисленное значение для ввода (TOTP) | значение — только ядру, для `browser_fill_secret` |
| `refresh(cred)` | обновить учётку (OAuth) | новые поля → новая версия |
| `login(cred, params)` | интерактивный вход (OAuth PKCE, device flow) | заполненные поля учётки |
| `write_secret(session, cred, field, prompt)` | ввести пароль в интерактивный запрос (`sudo`), только если последний вывод совпал с `prompt` | `ok` / `prompt_mismatch` |
| `derived(cred)` | строки, производные от значения (base64, подписи без времени) | добавляются в маскирование |

### Функции хоста для модуля

| Функция | Ограничение |
|---|---|
| `bound_http(req)` | только к origin привязки и адресам из её параметров (`token_url`) |
| `bound_conn()` | соединение к адресу привязки; TLS и клиентский сертификат — у ядра; для `ssh` — сырой TCP |
| `user_open_url(url)`, `user_await_redirect()` | открыть URL у человека, принять redirect на loopback ядра (OAuth) |
| `user_prompt(text)` | вопрос человеку через канал подтверждений (device code, SMS-код) |
| `time_now`, `random` | — |
| `log(level, code)` | только коды из `describe()`, без свободного текста |

У модуля нет KV, файлов, общей сети и функций коннекторов. Экземпляр модуля живёт не дольше одного использования или соединения.

### Граница потока данных

Выход модуля идёт в одно из двух мест:
- **к серверу привязки** — запросы и соединения через `bound_*`;
- **к ядру** — значения из `resolve` и `refresh` ядро использует само.

Коннектору достаются только:
- открытое соединение после `handshake` или поток `transport`;
- типизированный вердикт: `ok`, `invalid` и `reason_code` из перечисления в `describe()`.

Свободного текста модуль коннектору не отдаёт. Ответы и потоки, идущие коннектору, проходят маскирование.

Вердикты — канал в несколько бит на вызов. Поэтому вызовы пишутся в журнал и ограничиваются по частоте, а сам модуль проходит ревью.

### Доверие и поставка

- **Пакет и репозиторий:** в `registry` — `kind: auth` (у коннекторов — `kind: connector`); имя в магазине — `<издатель>/auth-<протокол>`. Наши модули — в репозитории `gate4ai/gate4ai`, каталог `connectors/auth/<модуль>` (общие тестовые фейки рядом; версия — общая с релизом), сторонние — `gate4ai-auth-<имя>`; лицензия — AGPL-3.0, как у коннекторов; у сторонних в магазине — совместимая с AGPL-3.0. Типы учёток модуль объявляет в своём пространстве имён без префикса `auth-`: модуль `gate4ai/auth-oauth2` — тип `gate4ai/oauth2`.
- **Уровни:** auth-модули ставятся только с уровнями «проверен gate4.ai» и «проверенный издатель». Модуль сообщества требует явного согласия с предупреждением «модуль видит ваши пароли от X».
- **Поставка:** подпись пакета Ed25519 (ключ издателя или gate4.ai, без Sigstore), воспроизводимая сборка, обязательный исходник — как у коннекторов.
- **Версии:** привязка закреплена за мажорной версией модуля.
- **Нативные auth-модули** (позже: ГОСТ / КриптоПро, аппаратные токены):
  - тот же ABI по stdio в процессной песочнице;
  - сеть — только через переданное ядром соединение;
  - обязательное обоснование, как у `runtime: native` коннекторов.

## Уровень 3. Коннекторы

Коннектор называет **слот**, а не значение и не протокол:

| Функция хоста | Что делает |
|---|---|
| `http_request(req)` с `auth: {slot}` | ядро применяет шаблон или `http_apply` модуля, затем `http_response`; коннектор получает ответ после маскирования и вердикт |
| `conn_open(slot, params)` | ядро открывает соединение к адресу привязки, модуль делает `handshake` или `transport_open`; коннектор получает поток |
| `conn_write_secret(conn, field, prompt)` | ввод пароля в интерактивный запрос через `write_secret` модуля |
| `browser_fill_secret`, `browser_login`, `browser_capture_secret` | ввод в браузере (ядро) |
| `secret_commit`, `secret_discard`, `secret_info(slot)` | версии и метаданные своих слотов |

Агенту доступны те же возможности как действия коннекторов, через политику и журнал: `browser.login(account)`, `browser.fill_secret(account, target, field)`, `browser.save_secret(account, target, name)`. Ответ — статус и алиас, без значения.

### Несколько экземпляров

- **Аргумент `account`.** Каждое действие коннектора с несколькими экземплярами получает аргумент `account` — перечисление экземпляров, доступных профилю агента. Если экземпляр один, аргумент необязателен. Экземпляр вне профиля — ошибка `unknown_account`, без подсказки, что он существует.
- **Профили и политика.** Профиль перечисляет экземпляры: `connectors: [mail.work, jira.acme]`; `mail` означает все `mail.*`. В CEL доступны `instance`, `account`, `credential`, `origin`.
- **Браузер.** Экземпляр браузера — отдельный профиль Chrome: свой каталог и свой процесс. Процесс запускается по требованию и закрывается после 10 минут простоя. Человек входит в профиль сам командой `gate4ai browser open <экземпляр>`.

### Исключение `reveal`

Нативный коннектор-обёртка над CLI, которую нельзя кормить через прокси, может получить значение. Условия:
- `reveal: [slot]` объявлен в манифесте;
- пользователь дал отдельное согласие;
- учётка помечена «известна коннектору X», и это видно в Web UI;
- ревью при публикации строже.

По умолчанию `reveal` выключен; у WASM-коннекторов его нет.

## Агенты в песочнице

Egress Proxy использует те же привязки, шаблоны и auth-модули, что и `http_request`:
- **Фиктивные значения.** Запуск получает одноразовые фиктивные значения правильного формата (`sk-ant-gate4ai-<random>`, `ghp_gate4ai<random>`), чтобы CLI и SDK согласились запуститься.
- **Расшифровка.** HTTPS расшифровывается только для origin с привязками: CA песочницы передаётся через `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO`. Остальное идёт прозрачным туннелем.
- **Подстановка.** Заголовок ставится шаблоном или `http_apply` целиком. Фиктивное значение в другом заголовке, теле или URL — отказ `secret_denied`.
- **Ответы.** Маскируются; `http_response` модуля перехватывает token endpoint (вход по подписке Claude Code / Codex, `gh`).
- **Редиректы** прокси не выполняет.
- **Учётки на запуск.** У каждого запуска свои привязки. Две учётки на один origin в одном запуске — ошибка конфигурации.
- **SSH-ключи.** Для агентов они доступны через сокет SSH-агента от gate4ai с расширением `session-bind@openssh.com`: подпись выдаётся, только если ключ хоста совпал с `host_key` привязки. Сокет обслуживает модуль `gate4ai/auth-ssh`. Пароли SSH для агентов — позже, через gate4ai как бастион.

## Сценарии

### Форум: регистрация и вход

**Регистрация коннектором:**
1. `browser_fill_secret(pwd, {slot: login, field: password}, generate: {length: 20})` — черновая версия v1.
2. `browser_fill_secret(confirm, {slot: login, field: password, version: pending})`.
3. Логин: публичное поле, задаётся через `secret_info` / `secret_set_public`.
4. `click(submit)`, проверка успеха, `secret_commit`. Человек подтверждает `secret.save`, привязка — origin страницы регистрации.

**Учётка уже есть:**
- человек вводит её в Web UI;
- или ядро захватывает её при ручном входе в выделенном профиле.

**Вход:** `browser.login(@forum.main)`. Пароль вводится только в `type=password`; логин — в поле, которое владелец указал в учётке (`type: text`). Ввод пароля в «Заголовок темы» невозможен: это поле не `type=password`.

Чего нет в ядре: ничего специфичного для форума.

### SSH

- Привязка `ssh://prod.example:22`, модуль `gate4ai/auth-ssh@1`, `host_key` в привязке.
- Коннектор вызывает `conn_open(ssh)`. Ядро даёт модулю сырой TCP, модуль проходит рукопожатие ключом или паролем и проверяет ключ хоста. Коннектор получает поток каналов (`exec` / `shell`).
- `sudo`: коннектор вызывает `conn_write_secret(conn, password, "[sudo] password for")`. Модуль пишет пароль, только если последний вывод совпал с запросом.
- Агент в песочнице: сокет SSH-агента с `session-bind`.

Чего нет в ядре: SSH.

### Банковский REST с подписью

- Учётка `acme/bank-hmac-key` (тип объявлен модулем). Клиентский сертификат — учётка `secret` в `tls.client_cert` привязки, его предъявляет ядро.
- `http_request(auth: {slot: bank})`: `http_apply` подписывает запрос, `http_response` проверяет подпись ответа общим секретом. Коннектор получает ответ и `verdict: ok`.
- Для `class: money` вердикт попадает в квитанцию как доказательство.
- ГОСТ / КриптоПро — нативный auth-модуль с тем же ABI.

Чего нет в ядре: схема подписи банка.

### Google (по образцу gog)

- **OAuth-клиент пользователя.** Учётка `gate4ai/oauth2-client` (`client_id`, `client_secret`).
- **Аккаунт.** Учётка `gate4ai/oauth2` со ссылкой на клиент, scope — публичные поля, они видны политике.
- **Подключение.** В Web UI пользователь нажимает «Подключить», и модуль `gate4ai/auth-oauth2` проводит `login`: PKCE S256 через `user_open_url` и `user_await_redirect`. Verifier только в памяти модуля.
- **Несколько аккаунтов.** Экземпляры `gmail.work` и `gmail.personal`: разные учётки, общий клиент.
- **Использование.** `http_request(auth: {slot: google})`; модуль обновляет токен через `refresh` и ставит Bearer для origin `*.googleapis.com` из явного списка.
- **Сервисный аккаунт.** Модуль `gate4ai/auth-google-sa` подписывает JWT с `sub`.
- **Сам gog в песочнице.** `gog --access-token <фиктивный>`, Egress Proxy ставит настоящий токен.

Чего нет в ядре: OAuth.

### GitHub CLI

- Агент получает `GH_TOKEN=ghp_gate4ai<random>`.
- Одна учётка `secret`, две привязки-шаблона: Bearer для `api.github.com` и Basic `x-access-token:<token>` для `github.com` (git по HTTPS).
- **Вход.** Device flow проводит модуль `gate4ai/auth-oauth2` через `user_prompt` (код показывается в Web UI или трее).
- **Защита.** `gh auth login` внутри песочницы закрыт в egress.
- **Права.** Предпочтителен fine-grained PAT. Web UI предупреждает, что OAuth-токен `gh` даёт `repo` на все приватные репозитории.
- **`gate4ai doctor`** ищет открытые токены в `~/.config/gh/hosts.yml`.

Чего нет в ядре: ничего, достаточно шаблонов.

## Политики и подтверждения

- **Одно подтверждение на действие.** Учётка используется только внутри действия агента и только через слоты своего экземпляра — других учёток коннектору не достать. Поэтому её использование отдельно не подтверждается: его покрывает решение по самому действию (`allow` или подтверждённый `ask`). Пример: «перевести через Т-Банк» спрашивается один раз, второго вопроса «отдать ли пароль от Т-Банка» нет.
- Запрос подтверждения перечисляет учётки, которые действие может использовать (слоты экземпляра и их привязки): «войдёт с учёткой @amazon на https://www.amazon.com».
- `use: ask` в привязке — действия, которые используют эту учётку, всегда идут через человека: `allow` по политике для них становится `ask`. Отдельного вопроса на каждое использование нет.
- `secret.use` — событие журнала со ссылкой на квитанцию действия (`parent`), а не отдельное решение pipeline. `secret.save` проходит обычный pipeline: политика, подтверждение, квитанция.
- Коннектор-источник (код из письма) ядро вызывает внутри того же действия от имени того же агента: политика проверяется (`deny` — вход не состоялся), а `ask` покрыт подтверждением исходного действия; в журнале — с `parent`.
- В CEL доступны `instance`, `account`, `credential`, `origin`, `module`.
- Инструментов для чтения, создания и изменения учёток у агента нет. Управление учётками — только Web UI и `gate4ai vault …` от имени владельца.

## Отклонённые варианты

| Вариант | Почему нет |
|---|---|
| Протоколы аутентификации в ядре (`tls_dial` со схемами, SSH, подписи в daemon) | ядро растёт с каждым коннектором; у авторов коннекторов нет пути, кроме запроса к нам |
| Значение — коннектору по умолчанию | утечка на любой хост коннектора, в любом виде и незаметно; оставлено только как `reveal` с согласием |
| Только шаблоны, без кода | не покрывают SSH, OAuth-потоки, SigV4, проверку подписи ответа |
| Замена подстроки-заглушки в любом заголовке (текущий Egress Proxy) | заглушка в «своём» заголовке и эхо сервера выдают значение; остаётся только на время перехода |
| Подмена заглушки в теле POST при отправке формы | ломается на сайтах с проверкой формата и JS-шифрованием пароля |
| Менеджер паролей в профиле Chrome (расширение) | нет контроля, журнала и привязки к экземпляру |
| Инструмент на каждый экземпляр (`mail_work_send`) | раздувает каталог |
| Контексты браузера вместо профилей | cookie теряются; возможно позже как оптимизация |
| Keychain, запись на каждое поле | неудобно для структурных учёток и версий; нет Secret Service на части Linux |

## Риски и что проверить первым

- `golang.org/x/crypto/ssh` и криптография Go собираются под `wasip1` и работают в wazero с приемлемой скоростью.
- Поток `transport_*` через функции хоста wazero для интерактивной SSH-сессии даёт незаметную задержку.
- Граница «модуль изменил только заголовки, query и тело» проверяется надёжно для HTTP/1.1 и h2.
- Канал утечки через вердикты: ограничение частоты и журнал достаточны для модулей с ревью.

## Текущее состояние и переход

Сейчас (после этапов 17–18 и 12):
- Vault хранит плоские строки в keychain с маскированием;
- вход на сайты: `credentials` в конфигурации (форма или `via`, `use`, `connectors`), действия `browser.login` и `browser.fill_secret` (значения daemon передаёт пакету `browser` только в них — в `ExecRequest.Revealed`, форму — в `ExecRequest.Login`, учётки вызывающего без значений — в `ExecRequest.Accounts`), режим «секрет на странице», события `secret.use` в журнале (алиас, поле, origin, агент или коннектор, `parent` — квитанция действия), слоты `credentials` в манифесте (`{slot, bind}`, показываются в согласии) и связь `connectors.<имя>.credentials`; экземпляров, типов учёток, подписей форм, генерации и сохранения секретов ещё нет; режим «секрет на странице» запрещает чтение страницы, а снимки делаются с закрашенными полями секрета и пароля; слоты манифеста — `{slot, bind, types (form | via), fields}`; вопрос с вводом кода приходит и в Telegram (ответ сообщением, сообщение с кодом бот удаляет);
- вопрос `fill_secret` с `source: human` — из `prompts` учётки, иначе — от коннектора входа (одной строкой, не длиннее 200 символов); текст, присланный агентом, человеку не показывается (нейтральный «a one-time code»), кто спрашивает и для какого сайта — показывает канал;
- коннекторы — WASM-модули, значения в `Settings` не передаются;
- `http_request` подставляет плейсхолдер `{{secret:@alias}}` по `capabilities.secrets[].bind` только **целиком в заголовок аутентификации** (`Authorization`, `Cookie`, заголовки с `key`, `token`, `auth`, `secret`, `signature`, `session`, `password`, `credential` в имени): значение заголовка — плейсхолдер, перед ним может стоять схема (`Bearer `). В теле, URL и прочих заголовках — `bad_request`. Заголовки `Accept-Encoding`, `TE`, `Range`, `If-Range` коннектора удаляются: сжатие согласует и снимает хост, а ответ с неизвестным `Content-Encoding` в вызове с секретами — ошибка (иначе маскирование не увидит значение);
- привязка секрета в манифесте (`bind`) — точный хост (без `*.`: поддомены — явным списком) или точный origin (`https://api.example.com:8443`, `imaps://imap.example.com`); у привязки-хоста схему и порт ограничивает `capabilities.network` (без TLS — только loopback). Алиас может быть объявлен несколько раз с разными привязками (пароль IMAP для SMTP) — подходит любая;
- маскирование (Vault, ответы и лог коннектора, текстовые доказательства) — за один проход по всем значениям (пересекающиеся участки закрываются целиком, порядок значений не важен) и их производным формам: base64 и base64url (во всех выравниваниях), URL-, JSON- и HTML-экранирование, hex, другой регистр. Это не Ахо — Корасик, а поиск каждой строки, — значений немного;
- `tls_dial` выполняет вход в IMAP / SMTP хостом (`netauth` в sdk-go: `imap-login`, `smtp-auth-plain`) — это протокол в ядре, который переносится в auth-модули; непрочитанные модулем данные соединения ограничены 8 МиБ (дальше хост не читает);
- `fs_*` открывают файлы относительно дескриптора разрешённого корня (`os.Root`) и сверяют, что корень — тот самый каталог; для правила на один файл последний компонент не может оказаться симлинком: подмена компонента пути после проверки не выводит запись за пределы `capabilities.files`;
- Vault — значения в keychain по записи на алиас и индекс алиасов; временная ошибка keychain не выкидывает алиас из индекса (значение читается позже); в режиме `--keystore file` значения лежат в `keys.json` (0600, каталог 0700, атомарная запись с fsync) открытым текстом;
- Egress Proxy заменяет заглушку в заголовке (переходный вариант, см. «Отклонённые варианты»): `egress.secrets[]` — `{domain, header, env, placeholder, secret, agents}`. С `env` заглушка **одноразовая на запуск**: `gate4ai run` получает от daemon свою заглушку `<placeholder или gate4ai>-<32 hex>` в переменной `env` (окружение агента, в контейнере — env-file), и прокси принимает только заглушку этого запуска (учётные данные прокси определяют запуск). Без `env` — постоянная `placeholder` из конфигурации (совместимость, daemon предупреждает при каждом запуске; короче 16 символов — не действует). `domain` — точный хост (origin `https://<хост>:443`) или точный https-origin, без wildcard; подстановка — только в HTTPS через расшифровку, в обычный HTTP — никогда (заглушка в нём — `403 secret_denied`). Значение заголовка — заглушка целиком (можно со схемой: `Bearer <заглушка>`); заглушка в URL или другом заголовке — `secret_denied`; заглушка в теле не проверяется (секрет туда не подставляется). `Host` внутреннего запроса должен совпадать с хостом CONNECT (иначе `421`: ключ не уходит на чужой хост за тем же фронтом). Ответ маскируется (значения и производные формы, заголовки и тело) и отдаётся потоком (SSE); сжатие у сервера не запрашивается (`Accept-Encoding: identity`), gzip/deflate распаковываются до маскирования, прочее — `502`. `agents` — агенты, которым доступна подстановка (пусто — всем агентам, у которых домен разрешён профилем). Соединения на адреса этой машины и частных сетей (loopback, private, link-local, multicast, unspecified — проверяется IP, с которым действительно соединяемся, после резолва) запрещены, если хост (имя или IP) не указан явно, без wildcard, в `allow_domains` / `ask_domains` профиля;
- запуск агента живёт, пока его продлевает `gate4ai run` (`POST /v1/runs/{id}/keepalive` каждые 5 минут): токен запуска выдаётся на 30 минут и продлевается, учётные данные прокси без продления перестают действовать — если CLI убит, запуск гаснет сам. Токен запуска и пароль прокси не попадают в argv (`srt` — окружение, контейнер — env-file, `--microvm` — `-e ИМЯ` со значением в окружении процесса docker) и в вывод `--dry-run`.

Порядок перехода:
1. ядро: модель, хранилище, проверки, шаблоны;
2. ABI и песочница auth-модулей, первые модули (`auth-imap`, `auth-smtp`, `auth-totp`);
3. перевод почты на `conn_open`, `netauth` и `tls_dial` со схемами — в auth-модули; плейсхолдеры `{{secret:@alias}}` — в `auth: {slot}`;
4. браузерный ввод;
5. Egress Proxy на привязках;
6. OAuth и SSH модулями;
7. сохранение секретов.

Тесты — на фейках: HTTPS-сервер с эхо заголовков, страница с формой, скрытым полем и iframe чужого origin, фейковые IMAP/SMTP/SSH, TOTP с фиксированным временем, фейковый OAuth-сервер.
