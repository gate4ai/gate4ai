# Браузер gate4ai по ссылке: смотреть и управлять (результаты исследования)

> Исследование и предложения, без разработки. Продолжает [headless-server.md](headless-server.md) и **пересматривает** его выбор (Xvnc + noVNC как основной путь): новые требования — ссылка на каждый сеанс агента, список сеансов в Web UI, кроссплатформенность — лучше закрывает CDP-screencast, а VNC остаётся запасным путём для Linux-сервера. Правки [спецификации](specification.md) — в конце, только с согласия владельца.

## Требования

1. Агент, открыв сеанс браузера (`browser.open` без `session`), сразу получает ссылку на него и может отдать её пользователю — в чат OpenClaw, Telegram и т.п.
2. По ссылке человек **видит вживую**, что делает агент, с телефона или ноутбука, и при необходимости **берёт управление** — не только во время `browser.handoff`.
3. В Web UI — список сеансов браузера с кнопкой «Подключиться»; то же в терминале (`gate4ai browser sessions`) и в трее.
4. Работает на Linux-сервере без графики, а по возможности — везде, где работает gate4ai (Linux, macOS, Windows).
5. Установщик проверяет и ставит Chrome и «виртуальный дисплей»; функцию можно выключить, если чего-то не хватает.
6. Лицензии новых зависимостей совместимы с AGPL-3.0-only (ядро, коннекторы) и не затрагивают Apache-2.0 (`sdk-go`).

## Что такое «виртуальный дисплей» и насколько это кроссплатформенно

Обычному (не headless) Chrome нужен графический сервер, где он рисует окна. На сервере без монитора и рабочего стола его нет. **Виртуальный дисплей** — графический сервер, который рисует в память, а не на экран: Chrome считает, что у него обычный монитор, и работает как на десктопе (это и нужно спецификации — настоящий Chrome, а не headless, ради антифрода). Посмотреть на такой экран можно по VNC, если сам виртуальный дисплей умеет VNC (Xvnc), или через отдельный VNC-сервер поверх него (Xvfb + x11vnc). Можно и вовсе без VNC — снимать кадры самой страницы через CDP (ниже).

| ОС | Нужен ли виртуальный дисплей | Чем | Замечания |
|---|---|---|---|
| **Linux без графики** (VPS, домашний сервер, контейнер) | да | X11: **Xvfb** (только дисплей) или **Xvnc** из TigerVNC (дисплей + VNC в одном процессе); Wayland: `weston --backend=headless` (у Weston 12+ есть VNC-бэкенд) или `sway` headless + `wayvnc` | X11-путь проще и проверен годами (так же сделан sandbox-browser OpenClaw); Chrome на X11 — без лишних флагов |
| **Linux с рабочим столом** | нет | есть `DISPLAY` / `WAYLAND_DISPLAY` | как сейчас; по желанию — виртуальный дисплей, чтобы окно gate4ai не мешало человеку |
| **macOS** | понятия нет | Chrome рисует только в графической сессии вошедшего пользователя (Aqua); daemon уже запускается LaunchAgent в ней | Mac mini без монитора: автологин; без подключённого монитора macOS даёт небольшой экран по умолчанию — для CDP-screencast это не важно (кадры — размер окна Chrome), для полного экрана — HDMI-заглушка. Публичного API виртуального дисплея нет (`CGVirtualDisplay` — приватный), не используем. Полный экран удалённо — только встроенный «Общий экран» macOS, это весь рабочий стол, не продуктовый путь |
| **Windows** | понятия нет | daemon работает в интерактивной сессии пользователя (ключ `Run`) | Без вошедшего пользователя daemon не работает вовсе. Windows Server через RDP: отключённая RDP-сессия продолжает жить, но перекрытые и свёрнутые окна Chrome перестаёт рисовать (`CalculateNativeWinOcclusion`) — нужны флаги ниже; проверить на стенде. Своего Xvfb нет (только сторонние драйверы IddCx) — не используем |

**Вывод:** виртуальный дисплей — вещь только для Linux. Механизм, который одинаково работает везде, — **CDP-screencast**: Chrome сам отдаёт по CDP JPEG-кадры содержимого вкладки (`Page.startScreencast`) и принимает ввод (`Input.dispatchMouseEvent` / `dispatchKeyEvent` / `insertText` / `dispatchTouchEvent`). Screencast — это *как смотреть*, а дисплей — *где Chrome рисует*: обычному Chrome на Linux без графики Xvfb нужен и со screencast, без него Chrome не запустится. VNC при этом не нужен. Обойтись без Xvfb можно только headless-режимом Chrome — см. «Зависимости и как их минимизировать».

## Зависимости и как их минимизировать

### Нужен ли Xvfb, если картинку отдаёт сам Chrome

Обычный (headful) Chrome на Linux рисует окна через X11 или Wayland. Нет ни того, ни другого — он завершается при запуске («Missing X server or $DISPLAY»), и до CDP дело не доходит. Screencast лишь снимает кадры с того, что Chrome нарисовал, поэтому дисплей ему всё равно нужен. Без дисплея работает только **`--headless=new`**: с Chrome 132 это тот же браузер, что и обычный (старый headless вынесен в отдельный `chrome-headless-shell`), но без окон.

Проверено 2026-10-24 на Google Chrome 155/156 (Linux): обычный Chrome на Xvfb в `debian:trixie-slim` и `--headless=new` на хосте; скрипт — открыть вкладки, включить screencast на 2 с, снять признаки страницы.

| | Обычный Chrome на Xvfb | `--headless=new` |
|---|---|---|
| Кадры screencast, вкладка на переднем плане | 21 за 2 с | 21 за 2 с |
| Фоновая вкладка в том же окне | **0** кадров (`visibilityState: hidden`) | **0** кадров |
| Сеанс в своём окне (`newWindow: true`) | 21 кадр, без дополнительных флагов | 21 кадр |
| Расширение через `Extensions.loadUnpacked` (так Stagehand ставит своё) | работает | работает |
| `navigator.userAgent` | `Chrome/156…` | **`HeadlessChrome/155…`** |
| `navigator.webdriver` (с `--disable-blink-features=AutomationControlled`) | `false` | `false` |
| WebGL | недоступен (нет GPU, в контейнере) | SwiftShader (программный) |
| UA через флаг `--user-agent` | — | UA правится, но `userAgentData.fullVersionList` становится пустым — сам по себе признак; правка без следов — `Emulation.setUserAgentOverride` с `userAgentMetadata` на каждую вкладку |

Итого: screencast, окно на сеанс и Stagehand работают в обоих режимах. Отличается только то, как сайт видит браузер. У headless есть явные признаки (UA, детекторы headless вроде CreepJS); часть закрывается подменой UA, но не все. Спецификация требует «не headless» именно из-за антифрода, поэтому headless — только запасной режим. Окно на сеанс работает на Xvfb без флагов против фонового режима; на Windows (`CalculateNativeWinOcclusion`) и macOS это ещё нужно проверить.

### Что весит сколько

Замеры `apt-get install --simulate --no-install-recommends` на чистых `debian:trixie-slim` и `ubuntu:24.04`, сверх уже установленного Chrome:

| Компонент | Debian 13 | Ubuntu 24.04 | Нужен |
|---|---|---|---|
| Google Chrome (`.deb`) | ~445 МБ сам + 142 пакета зависимостей ~346 МБ | ~445 МБ + 141 пакет ~343 МБ | всегда, на всех ОС |
| Xvfb | +21 пакет, **~12 МБ** (mesa, libxfont, xkb) | +23 пакета, **~7 МБ** | Linux без графики, для обычного режима |
| TigerVNC Xvnc | +30 пакетов, ~57 МБ (тянет perl) | +29 пакетов, ~56 МБ | только для запасного полного экрана |
| noVNC | ~0,5 МБ статики в бинарнике | | только для полного экрана |
| CDP-screencast, websocket | 0: наш код и `coder/websocket` (уже в `go.mod`) | | всегда |

Главная зависимость — сам Chrome (~0,8 ГБ на голом сервере). Xvfb рядом с ним — около 1 %. Отказ от Xvnc и noVNC экономит больше, чем отказ от Xvfb, и заодно убирает GPL и MPL из поставки.

### Как минимизировать, не теряя универсальности

1. **Обязателен только Chrome**, везде. Остальное зависит от ОС и окружения и выбирается само (`display: auto`):
   - есть графическая сессия (`DISPLAY` / `WAYLAND_DISPLAY`, macOS, Windows) → обычный Chrome, ничего не нужно;
   - Linux без графики и есть `Xvfb` → обычный Chrome на Xvfb, который поднимает пакет browser (**рекомендуется**: +7–12 МБ);
   - Linux без графики, Xvfb нет (нет root, минимальный контейнер) → `--headless=new` с подменой UA через `Emulation.setUserAgentOverride` (с метаданными). В Web UI и `gate4ai doctor` — предупреждение: «браузер без экрана: сайты с защитой от ботов чаще просят капчу или блокируют; поставьте xvfb: `sudo apt install xvfb`». Агент работает, ссылка `view_url` работает так же.
   
   Так браузер есть везде, где есть Chrome, а Xvfb — рекомендация, а не требование.
2. **Без VNC в основной поставке.** Screencast и ввод через CDP закрывают просмотр и управление на всех ОС. Xvnc и noVNC — отдельная поздняя опция «полный экран» на Linux, только если реально встретятся окна, которые CDP не показывает.
3. **Без root.** На Linux x86_64 Chrome for Testing распаковывается в каталог пользователя (zip, без пакетного менеджера; системные библиотеки Chrome на голом сервере всё равно нужны — `gate4ai browser setup` проверяет их через `ldd` и печатает команду). Без Xvfb работает headless-режим из п. 1. Для arm64 Chrome for Testing нет — только пакет из репозитория (нужен root) или `chromium` дистрибутива.
4. **Готовый образ** для Docker-установок: `gate4ai` + Chrome + Xvfb + шрифты в одном образе. Пользователю ничего не ставить, зависимости зафиксированы; GPL в образе нет, если не класть туда Xvnc.
5. **Шрифты** — `fonts-noto-core` и, по желанию, `fonts-noto-cjk` (~100 МБ): без них сайты показывают «квадраты», в том числе человеку в просмотрщике. Установщик предлагает их, но не требует.
6. **Без новых Go-зависимостей.** Мост кадров — поверх уже имеющегося JSON-RPC пакета и `coder/websocket`; JPEG декодирует сам браузер зрителя, перекодирования нет (ffmpeg и аналоги не нужны).

## Варианты

| | **A. CDP-screencast для всех + Xvnc запасным (рекомендую)** | B. Только Xvnc + noVNC (выбор из headless-server.md) | C. Только CDP-screencast |
|---|---|---|---|
| Ссылка на сеанс агента | да: кадры именно вкладки сеанса, независимо от того, что на переднем плане | плохо: VNC показывает весь экран — на переднем плане может быть чужая вкладка или сеанс; нужно окно на сеанс и обрезка | да |
| Несколько сеансов одновременно | да, каждый в своём окне (ниже) | один экран на всех, или по Xvnc на сеанс (тяжело) | да |
| ОС | Linux, macOS, Windows | только Linux | Linux, macOS, Windows |
| Зависимости | Chrome; на Linux без графики — Xvfb (MIT); Xvnc — по желанию | Chrome, Xvnc (GPL-2.0), noVNC (MPL-2.0) | Chrome; на Linux без графики — Xvfb |
| Чего не видно | нативные окна вне страницы: диалог печати, меню расширений, системное окно прокси-авторизации — для них Xvnc | ничего | то же, что у A, без запасного пути |
| Трафик | только пока кто-то смотрит; кадры шлются при изменении страницы | постоянный поток экрана, пока смотрят | как A |
| Свой код | средний: мост кадров и ввода, страница-просмотрщик | средний: процесс Xvnc, мост websocket ↔ RFB | средний |

Большую часть «нестраничных» окон CDP закрывает и без VNC: попапы OAuth — это новые цели (`Target.setAutoAttach` → показываем вкладкой сеанса), выбор файла — `Page.setInterceptFileChooserDialog` (файл человек загружает через просмотрщик), JS-диалоги уже обрабатывает `dialog.go`, HTTP Basic auth — `Fetch.authRequired`, запросы разрешений (геолокация, уведомления) — `Browser.grantPermissions` / отказ по политике. Поэтому в варианте A Xvnc — редкий запасной путь «показать весь экран» на Linux, его можно делать вторым шагом или не делать вовсе.

## Схема (вариант A)

```
 агент (OpenClaw)                   gate4ai daemon                         пакет browser (нативный)
 ───────────────                    ──────────────                         ───────────────────────
 browser open --url …  ──────────▶  pipeline ─────────────── exec ───────▶ новый сеанс s-7f… в своём окне Chrome
                       ◀──────────  {session: "s-7f…",                     
                                     view_url: "https://<адрес>/ui/browser/s-7f…"}
 «Смотрите: <view_url>» → в чат

 человек открывает view_url ───────▶ /ui/browser/s-7f…  (вход владельца: пароль / Telegram)
                                     websocket /ui/browser/s-7f…/ws ◀═════▶ view.start / frames / view.input
                                     ▲ кадры JPEG, текущий URL,                  Page.startScreencast,
                                     │ шаги агента из журнала                     Input.dispatch*
                                     └ «Взять управление» / «Вернуть агенту»
```

### Ссылка

- `browser.open` без `session` (новый сеанс) возвращает `view_url`. Адрес — публичный адрес устройства (relay или `--public`), если он есть, иначе `http://127.0.0.1:7431/ui/browser/<session>`; для сервера без публичного адреса подсказка — `ssh -L 7431:127.0.0.1:7431 <сервер>`.
- В ссылке нет секрета — только id сеанса. Доступ даёт **сессия владельца в Web UI** (пароль и/или подтверждение в Telegram; одной «ссылки входа» на сервере мало: её может получить агент того же пользователя ОС). Поэтому ссылку не страшно отдавать агенту и пересылать в чат: агент ею не воспользуется, а посторонний без входа владельца увидит только страницу входа.
- Сеанс закрыт — по ссылке видна запись: кто закрыл, когда, шаги (как в `browser.close`, `ClosedKeep` — час).
- SKILL.md: «открыв сеанс для задачи, которую пользователь может захотеть увидеть, отправь ему `view_url`»; `handoff` — «отправь `view_url`, если пользователь не ответил в канале gate4ai».

### Просмотр и управление

- **Смотреть** — по умолчанию: кадры и текущий адрес, рядом — лента шагов агента из журнала (`act: click «Войти»`, `open: https://…`), точка последнего клика поверх кадра. Ввод не идёт.
- **Взять управление** — кнопка; сеанс переходит в состояние `user_control`: действия агента в этом сеансе отвечают `session_held_by_user` (агент ждёт или делает другое), человек кликает и печатает через CDP-ввод. «Вернуть агенту» снимает блок. Действия человека — записи журнала от владельца (без введённого текста: там бывают пароли).
- **handoff** — то же управление, но по просьбе агента: уведомление уже несёт `view_url`, управление включено сразу, «Готово» досрочно завершает ожидание, «Отклонить» — агент получает `status: "declined"`.
- **Телефон**: тач → `Input.dispatchTouchEvent` / клик, своя кнопка клавиатуры (скрытое поле ввода → `Input.insertText`, служебные клавиши — `dispatchKeyEvent`), масштаб кадра по ширине экрана; размер окна сеанса не меняем (антифрод, вёрстка сайта).
- **Удалённо вне handoff** — только просмотр; «Взять управление» удалённо — по решению владельца (правка спецификации ниже; предлагаю: разрешено, с подтверждением в Telegram, если вход в `/ui/` был без него).

### Список сеансов

- **Web UI → «Браузер»** (новый раздел; на **Главной** — блок «Сейчас в браузере», если сеансы есть): агент и его экземпляр, адрес и заголовок страницы, с какого времени, состояние (`работает`, `ждёт вас` — handoff, `под вашим управлением`, `простаивает`), миниатюра (последний кадр, обновляется раз в несколько секунд, пока открыта страница), кнопки «Смотреть», «Взять управление», «Закрыть сеанс». Удалённо — тот же список; закрыть сеанс удалённо можно (это не расширяет прав агента).
- **Терминал**: `gate4ai browser sessions` (владелец: все сеансы; агент: свои) — таблица с `view_url`; `gate4ai browser watch s-…` — открыть просмотр в браузере (или напечатать ссылку на сервере без графики).
- **Трей**: пункт «Браузер: N сеансов» → страница списка; уведомление handoff — с кнопкой «Открыть».

### Несколько сеансов и фоновые вкладки

Сейчас сеанс — вкладка (`Target.createTarget`, иногда в фоне). Chrome не рисует фоновые вкладки: у них 0 кадров screencast (проверено, см. выше), а ввод в скрытую вкладку теряется. Предложение: **сеанс — своё окно** (`Target.createTarget {newWindow: true}`). На Xvfb и в `--headless=new` оба окна дают кадры одновременно без дополнительных флагов (проверено). На Windows и macOS перекрытые и свёрнутые окна Chrome может перестать рисовать, поэтому там флаги `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding` и на Windows `--disable-features=CalculateNativeWinOcclusion` — проверить на стенде, в том числе в отключённой RDP-сессии. Одноразовые `read` / `screenshot` остаются во временной вкладке.

### Транспорт кадров

Пакет browser — дочерний процесс daemon с JSON-RPC по stdin/stdout. Нужен поток событий от пакета к daemon: `view.start {session, max_width, quality}` → уведомления `view.frame {session, jpeg, url, ts}`, `view.input {...}`, `view.stop`. Кадры в base64 по stdio при 1280 px и JPEG 60 — порядка 50–150 КБ на кадр; screencast шлёт кадры только при изменениях, `screencastFrameAck` даёт обратное давление: следующий кадр — после того, как просмотрщик принял предыдущий. Daemon раздаёт кадры всем зрителям сеанса и сам к CDP не ходит: CDP остаётся только у пакета. Websocket в daemon — уже имеющийся `github.com/coder/websocket`.

## Установщик: Chrome и виртуальный дисплей

Сейчас `install.sh` **никогда не вызывает sudo** и не трогает систему — этот принцип стоит сохранить. Предложение:

1. Новая команда `gate4ai browser setup` (её же вызывают установщик и мастер Web UI):
   - проверяет: Chrome / Chromium (`chrome_path`, `ChromeCandidates`), версию; на Linux без `DISPLAY` / `WAYLAND_DISPLAY` — `Xvfb` (и `Xvnc`, если включён полный экран); шрифты (без `fonts-noto` / `fonts-noto-cjk` сайты показывают квадраты);
   - печатает, чего не хватает, и **команду под дистрибутив** (`/etc/os-release`);
   - `--yes` выполняет её через `sudo` (спрашивает пароль sudo в терминале); без sudo на Linux x86_64 — предлагает **Chrome for Testing** в каталог пользователя (официальная сборка Google, ставится без root; для arm64 его нет), а Xvfb без root не поставить — сообщает об этом.
2. `install.sh`: в конце, если терминал интерактивный, — `gate4ai browser setup` (только проверка и вопрос «Поставить сейчас? [y/N]»); `GATE4AI_INSTALL_DEPS=1` — ставить без вопроса (для скриптов), **`GATE4AI_NO_BROWSER=1`** — не проверять и не ставить пакет `browser` из магазина. В неинтерактивном запуске без `GATE4AI_INSTALL_DEPS` — только проверка и печать команды.
3. `install.ps1` (Windows): проверка Chrome; установка — `winget install --id Google.Chrome --scope user` (без прав администратора) с вопросом; `GATE4AI_NO_BROWSER=1` — так же.
4. macOS: проверка `/Applications/Google Chrome.app`; установка — `brew install --cask google-chrome`, если есть Homebrew, иначе ссылка на загрузку.
5. **Выключение**: если чего-то не хватает или задан `GATE4AI_NO_BROWSER`, пакет `browser` не ставится или стоит выключенным; в Web UI на месте браузера — «Браузер недоступен: нет Chrome / нет дисплея» с выводом `gate4ai browser setup` и кнопкой «Проверить снова»; `gate4ai doctor` пишет то же. Агент получает понятную ошибку `browser_unavailable` с подсказкой, а не падение пакета.
6. Пакет browser на Linux без графики **сам** поднимает Xvfb (`display: auto | virtual | headless | host`; auto — порядок из «Как минимизировать», п. 1): `Xvfb :N -screen 0 1920x1080x24 -nolisten tcp` (номер дисплея — свободный, сокет в `/tmp/.X11-unix`, доступ — по `-auth` с cookie в каталоге пакета), при падении — перезапуск вместе с Chrome. Xvfb нет — `--headless=new` с предупреждением, а не отказ.
7. Отсутствие Xvfb установщик не считает ошибкой: только Chrome обязателен. Xvfb и шрифты — «рекомендуется», с командой установки.

## Безопасность

- **Порт отладки Chrome** (`--remote-debugging-port` на `127.0.0.1`, TCP без аутентификации) — главный обход политик на сервере: любой локальный процесс, в том числе OpenClaw другого пользователя, управляет профилем с живыми сессиями. Закрыть до запуска на сервере: `--remote-debugging-pipe` (мост pipe → unix-сокет `0600` для Stagehand SDK, если он не умеет pipe) или отдельный network namespace пакета. Подробнее — [headless-server.md](headless-server.md#безопасность).
- **Xvfb**: `-nolisten tcp`, доступ к дисплею — по cookie (`-auth`) из каталога пакета: агент другого пользователя ОС не снимет экран и не пошлёт ввод через X.
- **Просмотр**: websocket — только с сессией владельца, проверкой `Origin` и CSRF; id сеанса не даёт доступа; в журнал — начало и конец просмотра и управления (кто, откуда, какой сеанс). Кадры могут показывать пароли, которые человек вводит сам, — кадры не пишутся на диск и не попадают в журнал.
- **Агент не получает экран**: `view_url` ему бесполезен; свои снимки — по-прежнему `page_screenshot` своего сеанса под политикой.
- **relay** — passthrough TLS: кадры и ввод relay не видит.

## Доработки (для отдельных задач)

1. Сеанс — своё окно, флаги против «засыпания» перекрытых окон; тест кадров двух сеансов одновременно.
2. Поток событий в протоколе нативных пакетов (`view.start` / `view.frame` / `view.input` / `view.stop`) с обратным давлением.
3. Daemon: websocket `/ui/browser/<session>/ws`, раздача кадров зрителям, состояние `user_control` и ответ агенту `session_held_by_user`.
4. Web UI: раздел «Браузер» (список, миниатюры, «Смотреть», «Взять управление», «Закрыть»), просмотрщик (тач, клавиатура телефона, лента шагов), блок на Главной.
5. `view_url` в ответе `browser.open` и в уведомлениях handoff; `gate4ai browser sessions`, `gate4ai browser watch`; пункт в трее; SKILL.md.
6. Виртуальный дисплей Xvfb в пакете browser и запасной `--headless=new` с подменой UA (`display: auto | virtual | headless | host`), предупреждение о headless в Web UI и `doctor`.
7. `gate4ai browser setup` + интеграция в `install.sh` / `install.ps1` (`GATE4AI_INSTALL_DEPS`, `GATE4AI_NO_BROWSER`), «Браузер недоступен» в Web UI и `doctor`, ошибка `browser_unavailable`.
8. Закрыть порт отладки Chrome.
9. По желанию, вторым шагом: полный экран через Xvnc + noVNC на Linux (из [headless-server.md](headless-server.md)).
10. e2e на стенде без X: Xvfb поднимается, `browser.open` возвращает `view_url`, без сессии владельца — вход, с ней — приходит кадр, «Взять управление» блокирует действие агента.

## Правки спецификации (нужно согласие владельца)

- «Браузер → Подключение»: на Linux без графического сеанса пакет запускает Chrome на виртуальном дисплее (Xvfb), а без Xvfb — в `--headless=new` как запасной режим с предупреждением (сейчас спецификация говорит «не headless»); каждый сеанс агента — своё окно; человек видит сеанс по ссылке `view_url` и может взять управление.
- «Удалённый доступ человека к своему устройству» и строка «Вход в удалённый Web UI»: удалённо, кроме подтверждений и журнала, — список сеансов браузера, просмотр и управление (вне handoff — с подтверждением в Telegram, если вход был без него).
- «Режимы развёртывания», п. 2: сервер без графики; агент — отдельным пользователем ОС или в `gate4ai run`.
- «Связь между процессами»: поток кадров пакет → daemon; исключение «TCP на localhost без аутентификации не используется нигде» сейчас нарушает порт отладки Chrome — закрыть (доработка 8).
- Установщик: проверка и (с согласия) установка Chrome и Xvfb, `GATE4AI_NO_BROWSER`.
