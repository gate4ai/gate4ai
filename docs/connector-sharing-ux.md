# Агент сам создаёт коннектор к сайту и делится им: UX-схема

> Проект UX, без реализации. Дополняет [connector-authoring.md](connector-authoring.md) (как агент пишет коннектор) и [connector-architecture.md](connector-architecture.md) (магазин, доверие). Сквозной пример — «купи билет на rzd.ru». Решения по спецификации: в ней ничего не меняется, схема живёт поверх существующих Браузера, коннекторов `runtime: wasm`, самонастройки `change_policy` и каталога на gate4.ai; что потребует правки спецификации — отмечено в [открытых вопросах](#открытые-вопросы).

## Цели и мотивация

Три цели пользователя и один ответ на каждую:

| Цель | Как достигается |
|---|---|
| 1. Личная база знаний, как работать с сайтами | каждый сеанс с сайтом оставляет **рецепт** в папке знаний пользователя (git-репозиторий на его компьютере), а повторяемое — становится **коннектором** |
| 2. Делиться знаниями | папка знаний — это обычный репозиторий `gate4ai-<сайт>`; публикация на GitHub одной командой с подтверждением владельца; поисковики индексируют README и страницу хаба gate4.ai; агенты читают машиночитаемую часть |
| 3. Продвигать gate4ai | агенту, который натыкается на сайт, выгоднее поставить gate4ai, потому что он получает **готовый проверенный путь** (одна команда вместо 30 действий браузера), вход без пароля в чате, подтверждения и журнал, а не только «правила» |

Ключевая идея: **два уровня знаний**. Рецепт появляется бесплатно, с первого раза, и уже полезен и индексируем. Коннектор — второй, более дорогой уровень: исполняемый, в песочнице, с проверкой результата. Другой агент, найдя страницу, получает коннектор, если он есть, или хотя бы рецепт.

```
   первый запуск                         повторные запуски                      другой пользователь
┌──────────────────────┐   ┌────────────────────────────────────┐   ┌────────────────────────────────┐
│ коннектора нет        │   │ коннектор-черновик (verified: 0)    │   │ агент ищет «rzd.ru купить      │
│ агент действует через │   │ коннектор ведёт с --trace,          │   │ билет» → README / gate4.ai/    │
│ Браузер gate4ai       │──►│ агент страхует: при сбое получает   │──►│ sites/rzd.ru → ставит gate4ai  │
│ → рецепт (сразу)      │   │ сеанс, доделывает, правит код       │   │ → connectors install <git>     │
│ → черновик коннектора │   │ → публикует правки                  │   │ → запуск с --trace → PR назад  │
└──────────────────────┘   └────────────────────────────────────┘   └────────────────────────────────┘
          │                              │                                        ▲
          ▼                              ▼                                        │
   ~/gate4ai-knowledge/rzd  ──push──►  github.com/<user>/gate4ai-rzd  ──индексатор──►  gate4.ai/sites/rzd.ru
   (личная база знаний)                (README, RECIPE.md, коннектор)              (хаб: SEO, JSON, llms.txt)
```

## Что создаётся

### Папка знаний

`~/gate4ai-knowledge/` (настройка `knowledge.dir`; создаётся мастером или первой командой). Внутри — по репозиторию на сайт: `gate4ai-rzd/`, `gate4ai-emias/`. Это обычные git-репозитории: их можно читать, править руками, публиковать и клонировать на другой компьютер. Имя репозитория совпадает с правилом магазина (`gate4ai-<имя>`), чтобы тот же репозиторий позже без переделки пошёл в registry.

```
gate4ai-rzd/
  README.md            # для людей и поисковиков: что умеет, как поставить, как вызвать; генерируется
  RECIPE.md            # рецепты сайта: YAML-шапка + шаги; читают агенты и люди
  manifest.yaml        # коннектор (появляется на уровне 2)
  connector.go, connector_test.go, testdata/*.json, go.mod
  .explore/            # сырые записи сеансов (в .gitignore, личные данные)
```

### Уровень 1: рецепт (`RECIPE.md`)

Что агент узнал о сайте, в форме, пригодной и человеку, и другому агенту:

```markdown
---
site: rzd.ru
domains: [ticket.rzd.ru, pass.rzd.ru]
tasks:
  - id: buy_ticket
    title: Купить билет на поезд
    class: money
    status: draft            # draft | verified
    verified_runs: 0
    last_verified: 2026-10-26
    gate4ai: v0.7.15
login: { kind: form+sms, bind: https://pass.rzd.ru }   # вход: учётка + код из SMS
human_steps: [sms_code, payment]                         # что делает человек всегда
---
## buy_ticket — купить билет
1. Открыть https://ticket.rzd.ru/searchresults/… (параметры в адресе: откуда, куда, дата).
   Ждать текст «Найдено поездов».
2. Кнопка «Выбрать» у поезда → ждать `[data-testid=car-scheme]`.
…
### Ловушки
- Схема вагона рисуется после клика с задержкой; ждать селектор, не время.
- Сайт сам отправляет SMS при входе без сессии: запускать, когда человек рядом.
```

Правила:
- Источник рецепта — запись шагов сеанса (`gate4ai browser close --save_steps`) после `gate4ai fixture scrub`: адреса, селекторы, тексты ожиданий, ошибки и то, как агент их обошёл. Комментарии («ловушки», развилки, решения человека) агент дописывает словами.
- В рецепте нет личных данных: `gate4ai knowledge check` (ниже) не пропускает публикацию, пока в тексте есть то, что `scrub` заменил, или похожие на номера документов и телефоны значения.
- Рецепт для другого пользователя — **недоверенный текст**: его агент получает рецепт как данные с меткой `untrusted_content`, как любую страницу. Поэтому для чужого использования предпочтителен коннектор (песочница, манифест, согласие), а рецепт — подсказка и запасной путь.

### Уровень 2: коннектор

Как в [connector-authoring.md](connector-authoring.md): WASM, манифест с `sites`, `credentials`, классами действий, `verify` для `money`, тесты на фикстуре `hosttest.Replay` из того же очищенного сеанса. Новое — **статус проверенности** и **режим трассировки** (ниже), а также путь установки из git без магазина.

Лицензии: код коннектора — совместимая с AGPL-3.0 (правило магазина); рецепты и README — CC0 (как индекс registry), чтобы хаб и другие авторы могли их переиспользовать без согласований. Это печатает `LICENSE` заготовки.

## Сценарий 1: первый запуск — коннектора нет

Человек: «Купи билет Москва → Казань на 5 ноября на rzd.ru, плацкарт, нижнее место».

1. **Проверка знаний.** Skill предписывает первым делом `gate4ai sites lookup rzd.ru`. Ответ:
   ```json
   {"domain":"rzd.ru","installed":[],"store":[],"hub":[],"knowledge":[],
    "hint":"No connector or recipe. Work in a browser session; when done, run `gate4ai connectors new rzd --site rzd.ru --from-session <s-…>` to keep what you learned."}
   ```
   `installed` — поставленные коннекторы с сайтом в `sites`; `store` — индекс registry; `hub` — индекс хаба gate4.ai (этап 2, с кэшем как у registry); `knowledge` — репозитории в папке знаний. Один вызов вместо трёх разных команд: агент не должен помнить, где искать.
2. **Доступ к сайту.** `browser.open` на `ticket.rzd.ru` упирается в список доступа → `capability_denied` с готовым `change_policy`; агент отправляет, человек подтверждает «Добавить в разрешённые» (как сейчас).
3. **Действие через Браузер.** Поиск поезда, выбор вагона и места — `open` / `observe` / `act`. Данные пассажира (ФИО, дата рождения, документ) агенту говорит человек в чате или они лежат в настройках будущего коннектора (см. открытые вопросы); вход — учётка `@rzd` + код из SMS (`browser.login` → `still_on_login` → человек вводит код в просмотре сеанса); оплата — `handoff` человеку: карту вводит он, агент ждёт смены адреса на «Заказ оплачен». Всё это уже есть в продукте.
4. **Сеанс завершён — рецепт сразу.** Агент закрывает сеанс с `--save_steps` и вызывает:
   ```sh
   gate4ai connectors new rzd --site rzd.ru --from-session s-7f3a --task buy_ticket
   ```
   Команда создаёт `~/gate4ai-knowledge/gate4ai-rzd/` (git init), черновик `RECIPE.md` из очищенной записи (шаги с адресами, селекторами, ожиданиями; ветки `still_on_login`, `handoff` → `human_steps`), заготовку манифеста (действие `buy_ticket`, класс `money` — из подвызовов: был `act`, был платёж; `search_trains`, класс `read` — из первой части шагов до первого клика с эффектом), тесты и `README.md`. Шаги, которые делал человек, в коннектор не попадают: они остаются ветками `login` / `handoff`. Агент дописывает «Ловушки» и развилки словами и показывает человеку в чате: «Билет куплен (заказ №…, квитанция `#e19…`). Я сохранил рецепт rzd.ru в вашу базу знаний: `~/gate4ai-knowledge/gate4ai-rzd/RECIPE.md`».
5. **Черновик коннектора — параллельно, а не вместо.** Пока человек оплачивает (ожидание `handoff` занимает минуты), агент уже пишет `connector.go` по записанным шагам и гоняет тесты на фикстуре; реальный сайт при этом не трогается. Это и есть «параллельно»: второго сеанса браузера на том же сайте не нужно, обе работы идут от одной записи. После оплаты агент ставит свою сборку (`install_dev_connector` через `change_policy`, подтверждение владельца показывает возможности) и один раз прогоняет действие класса `read` (`gate4ai rzd search_trains …`) на живом сайте — это дёшево и безопасно; `buy_ticket` на живом сайте в первый день не запускается (он уже куплен), остаётся `draft`.
6. **Публикация — с подтверждением.** Агент вызывает `gate4ai knowledge publish rzd`. Это действие класса `external` встроенного коннектора `gate4ai`: оно проходит проверку `knowledge check` (личные данные, секреты, сырые записи вне `.gitignore`) и запрос подтверждения владельцу: «Опубликовать `gate4ai-rzd` на GitHub как `github.com/alex/gate4ai-rzd` (публичный)? Файлы: README.md, RECIPE.md, manifest.yaml, connector.go, testdata/buy_ticket.json. Личных данных не найдено. Лицензии: AGPL-3.0 код, CC0 рецепты». Кнопки: «Опубликовать», «Только сохранить локально», «Больше не спрашивать для этого репозитория». Daemon делает `git push` через системный `git` и `gh` владельца (учётка GitHub — его, не агента) и ставит теме репозитория `gate4ai-connector`; результат — ссылка в журнале и в чате. Настройка `knowledge.publish: ask | auto | never` (по умолчанию `ask`).

Что видит человек в итоге одного запроса: билет, квитанция, рецепт в своей папке, ссылка на публичный репозиторий (если согласился). Что видит агент: один сценарий, подсказанный skill'ом, без собственных решений «надо ли сохранять».

## Сценарий 2: повторный запуск — коннектор есть, но не проверен

Через месяц: «Купи билет Казань → Москва на 3 декабря».

1. `gate4ai sites lookup rzd.ru` → `installed: [{connector: rzd, actions: [search_trains (verified 4), buy_ticket (draft, verified 0)], source: knowledge, repo: github.com/alex/gate4ai-rzd}]`, подсказка: «`buy_ticket` is a draft: run it with `--trace`; on failure you get the browser session back».
2. **Коннектор ведёт, агент страхует.** `gate4ai rzd buy_ticket --from Казань --to Москва --date 2026-12-03 --trace`. Трассировка — режим вызова (флаг CLI, поле MCP; для действий со статусом `draft` daemon включает её сам): в ответ попадает `trace` — список подвызовов браузера (действие, аргументы без секретов, `status`, адрес и начало текста страницы после шага) — и `log` коннектора. Для human-шагов коннектор делает то же, что делал агент: `login` → SMS человеку, оплата → `handoff`; подтверждение `money` — одно на действие, как по спецификации.
3. **Сбой.** Сайт переименовал кнопку: `act {text: "Выбрать"}` → `not_found`. Коннектор возвращает ошибку, а daemon в режиме трассировки **не закрывает страницу**, а передаёт её агенту:
   ```json
   {"status":"handoff_to_agent","connector":"rzd","action":"buy_ticket","failed_step":3,
    "error":{"code":"not_found","similar":[{"text":"Выбрать места","selector":"button.select"}]},
    "session":"s-91c0","trace":[…],"hint":"Continue in the session with `gate4ai browser … --session s-91c0`; fix the connector and reinstall (`gate4ai connectors install ~/gate4ai-knowledge/gate4ai-rzd --watch`)."}
   ```
   Сеанс продолжается под именем агента с теми же правилами: его `act` — класс `write`, его клики на сайте проходят список доступа и правила как обычно, разрешение `money` коннектора на действия агента не переносится. Агент доделывает покупку через Браузер, человек оплачивает в `handoff`.
4. **Правка.** Агент меняет селектор в `connector.go`, обновляет фикстуру из новой записи (`fixture scrub`), прогоняет тесты, переустанавливает (`--watch` уже подхватил), дописывает в рецепт «с 2026-12 кнопка называется „Выбрать места“» и коммитит. Если изменился манифест (`sites`, подвызовы) — переустановка идёт через подтверждение владельца, как сейчас.
5. **Публикация правки.** `gate4ai knowledge publish rzd` → подтверждение (или `auto`, если владелец выбрал «Больше не спрашивать» для этого репозитория). В сообщение коммита и README попадает «last verified 2026-12-03».
6. **Всё хорошо.** Если действие прошло с `verified: true`, daemon увеличивает `verified_runs` действия (счётчик в State Store, по коннектору и действию; показывается в `connectors list`, на странице коннектора в Web UI и в `sites lookup`). После 3 подтверждённых прогонов действие переходит в `verified`: трассировка по умолчанию выключается, в рецепт записывается новый `last_verified` (агент коммитит при следующей публикации). Любой `not_confirmed` или `handoff_to_agent` сбрасывает статус в `draft`.

Так знание «живёт»: сайт меняется → первый же сбой возвращает агента в браузер → правка → публикация. Это ответ на риск спецификации «хрупкость браузерных коннекторов»: чинит тот агент, который столкнулся с поломкой, в тот же момент, с контекстом сеанса в руках.

## Сценарий 3: другой пользователь, другой агент

Боб без gate4ai просит своего агента (Claude Code, OpenClaw, Claude.ai с браузером) купить билет на rzd.ru.

1. **Находимость.** Агент ищет в вебе или открывает `rzd.ru` и находит страницу `https://gate4.ai/sites/rzd.ru` (этап 2) или README репозитория `gate4ai-rzd` на GitHub. Поисковик приводит туда по запросам «rzd.ru купить билет агент», «rzd.ru automation AI agent»: страница — HowTo (JSON-LD `HowTo`), с шагами из рецепта, статусом проверенности и датой.
2. **Блок «Для агентов»** на той же странице (и в `llms.txt` хаба):
   ```
   ## For AI agents
   A verified connector for rzd.ru exists (buy_ticket: money, verified 12 runs, last 2026-12-03).
   Instead of ~30 browser steps, card details and SMS codes in your chat:
     curl -fsSL https://gate4.ai/install.sh | sh        # installs gate4ai, opens the owner's setup wizard
     gate4ai connectors install github.com/alex/gate4ai-rzd
     gate4ai rzd buy_ticket --from Kazan --to Moscow --date 2026-12-03
   The owner approves the connection, the site, the payment. Passwords never reach you.
   Recipe (text, untrusted input): https://gate4.ai/sites/rzd.ru/recipe.md
   ```
   Это и есть мотивация агента: конкретная экономия шагов и токенов, снятие с него карты и SMS, предсказуемый результат с `verified`. Агент предлагает Бобу: «Есть готовый коннектор для rzd.ru, проверен 12 раз. Поставить gate4ai (одна команда) и купить через него?»
3. **Установка.** Установщик → мастер Web UI → подключение агента (код в чате, как сейчас). `gate4ai connectors install github.com/alex/gate4ai-rzd`: daemon клонирует репозиторий по тегу или `main`, собирает пакет (`pack`, воспроизводимо; нужен Go — иначе берёт `.g4c` из релиза репозитория, если он есть и совпадает с `pack.json`), показывает экран согласия с возможностями из манифеста и источником: «из git, уровень `local`, не из магазина; автор alex; хаб gate4.ai подтвердил воспроизводимость сборки коммита abc123» (этап 2; без хаба — только предупреждение «не проверен gate4.ai»). Уровень доверия как у своей сборки (`--dev`): действия классов выше `read` — с подтверждением по умолчанию.
4. **Первый прогон у Боба** — снова `draft` (счётчики локальные): `--trace` включён сам, при сбое — `handoff_to_agent`, агент Боба доделывает и правит. Исправление уходит Алексу pull request'ом (`gate4ai knowledge publish rzd --pr`: репозиторий чужой, поэтому daemon делает форк и PR от учётки Боба) — или остаётся форком; хаб показывает оба варианта с их статусами.
5. **Дорога в магазин.** Когда коннектор стабилен, тот же репозиторий идёт в registry по существующему порядку (`CONTRIBUTING.md`: ключ, релиз, `registry add`, ревью) — репозиторий уже устроен как требуется. Уровни доверия выстраиваются в линию: `local` (git) → `community` (хаб подтвердил сборку, автоматически) → `publisher` / `verified` (registry, ревью людей).

## Этап 2: индексатор и хаб gate4.ai

Этап 1 обходится GitHub'ом: README индексируют поисковики, агенты читают репозиторий. Этап 2 берёт лучшее от централизованного хаба, не меняя модели «локально, без облака» для самого gate4ai:

- **Индексатор** на www: источники — индекс registry (как сейчас), репозитории GitHub с темой `gate4ai-connector` (поиск по API раз в несколько часов) и `knowledge publish`, который после push стучится `POST https://gate4.ai/hub/ping {repo}` (без данных пользователя; daemon и так ходит на gate4.ai за `/latest`). Для каждого репозитория индексатор читает `RECIPE.md` и `manifest.yaml`, пересобирает пакет из коммита и записывает `reproducible: true/false`.
- **Страницы.** `/sites/<домен>` — все рецепты и коннекторы для сайта от всех авторов (статус, `verified_runs` из шапки рецепта, дата, лицензия, ссылка на репозиторий, кнопка «Открыть в gate4.ai» как у каталога); `/sites/<домен>/<автор>` — страница репозитория: рецепт целиком, возможности манифеста человеческим языком (как `/connectors/<имя>`), команды установки. Существующий `/connectors` остаётся витриной магазина; `/sites` — витриной знаний. Всё без JS и трекеров, на двух языках, по требованиям [www/REQUIREMENTS.md](../../www/REQUIREMENTS.md).
- **Для поисковиков:** `sitemap.xml` со страницами сайтов, JSON-LD `HowTo` (шаги рецепта) и `SoftwareSourceCode` (репозиторий), заголовки вида «rzd.ru: купить билет через AI-агента — рецепт и коннектор gate4ai».
- **Для агентов:** `/sites/<домен>.json` и `/hub/index.json` (подписан ключом gate4.ai: подпись удостоверяет лишь «это то, что лежит в таком-то репозитории на таком-то коммите»), `/llms.txt` с перечнем сайтов и блоком «Для агентов». `gate4ai sites lookup` читает `/hub/index.json` с кэшем и проверкой подписи, как индекс registry.
- **Доверие.** Хаб ничего не ревьюит: он подтверждает воспроизводимость и показывает счётчики из рецептов (их пишет автор; телеметрии прогонов нет). Жалоба на репозиторий — кнопка на странице → исключение из индекса. Это уровень `community`; `publisher` и `verified` — только через registry.

## Что меняется в продукте (без реализации)

**gate4ai (ядро, CLI, skill, Web UI)**

| Что | Зачем |
|---|---|
| `gate4ai sites lookup <домен>` (и MCP-инструмент) | единая точка «что мы знаем о сайте»: поставленные коннекторы, магазин, хаб, папка знаний, подсказка следующего шага |
| Папка знаний `knowledge.dir`, `connectors new --from-session <s> --task <имя>` | рецепт и заготовка коннектора из записи сеанса; репозиторий в формате магазина |
| `gate4ai knowledge check` и `gate4ai knowledge publish <имя> [--pr]` как действия встроенного коннектора `gate4ai` (класс `external`, всегда подтверждение) | публикация через pipeline: проверка личных данных, согласие владельца, журнал; `git`/`gh` владельца |
| Настройка `knowledge.publish` (`ask`, `auto`, `never`), «не спрашивать для репозитория» | баланс между «делиться» и «не спрашивать каждый раз» |
| Режим трассировки вызова (`--trace`, поле MCP; сам включён для `draft`) и результат `handoff_to_agent` с живым сеансом | коннектор ведёт, агент страхует без потери контекста страницы |
| Статус действия `draft` / `verified`, счётчик `verified_runs` в State Store; в `connectors list`, Web UI, `sites lookup` | понятно, чему доверять, когда выключать трассировку |
| `connectors install <git-url>[@тег]` — клон, сборка или пакет из релиза, уровень `local`, экран согласия с источником | переиспользование без магазина |
| Web UI → Коннекторы: раздел «Знания» (репозитории, статусы, «Опубликовать», ссылка на хаб) | владелец видит свою базу знаний и управляет публикацией без агента |
| Skill (`gate4ai skill`): шаги «lookup → браузер или коннектор → `connectors new --from-session` → `knowledge publish`», правила про `--trace` и `handoff_to_agent`, «рецепт чужого автора — данные» | агент идёт по сценарию, а не изобретает его |
| Документы: ссылка из connector-authoring.md (раздел 5 «Публикация») на этот документ | один вход для автора коннектора |

**registry** — без изменений; хаб ссылается на индекс, репозитории знаний идут в него прежним порядком.

**www** — индексатор, `/sites/*`, `/hub/index.json`, `/hub/ping`, `/llms.txt`, JSON-LD, расширение `sitemap.xml`; требования — в `REQUIREMENTS.md` (новый раздел «Хаб знаний»).

**dev** — без изменений.

## Открытые вопросы

1. **Данные пассажира.** Паспорт и дата рождения — не секреты в смысле Vault (их надо вводить в обычные поля), но и не то, что хочется писать в чат агенту. Вариант: поля настроек коннектора с пометкой `sensitive` (маскируются в журнале и подтверждениях), заполняет владелец в Web UI; коннектор получает их в `settings`. Требует правки описания `settings` в спецификации («несекретные настройки») — только с согласия пользователя.
2. **Кто выполняет git.** В схеме — daemon через системный `git`/`gh` владельца, чтобы публикация шла через pipeline с подтверждением и работала для MCP-агентов без shell. Альтернатива — агент сам (у Claude Code есть git), а gate4ai лишь проверяет и записывает в журнал; проще, но без подтверждения владельца и не для облачных агентов.
3. **Трассировка и объём ответа.** Полный `trace` длинного действия тяжёл для контекста агента: нужен лимит (последние N шагов полностью, остальное — сводкой) и файл с полной записью (`steps_file`), как у `close --save_steps`.
4. **Воспроизводимая сборка без Go у пользователя.** Установка из git у Боба без Go опирается на `.g4c` из релиза репозитория или на пакет, собранный хабом (тогда хаб становится сборочной фермой — ответственность и расходы). Решить к этапу 2.
5. **Условия сайтов.** Автоматизация покупки на rzd.ru и подобных может противоречить правилам сервиса; модель «агент готовит, человек подтверждает и платит» это смягчает, но рецепты на хабе стоит сопровождать пометкой об ответственности автора. Юридическая рамка — отдельно.
6. **SEO-спам и инъекции.** Открытый индекс по теме GitHub соберёт и мусор. Защита: только репозитории с валидным `RECIPE.md` и манифестом, `reproducible: true` для показа команды установки, жалобы, ручной бан; рецепты для агентов — всегда `untrusted_content`.
7. **Имена.** «Рецепт» и «Знания» — рабочие названия; альтернативы: «Заметки о сайте», «Плейбук». Решить до появления в skill и Web UI, потом переименовывать дорого.
