## Суть

Приложение для компьютера пользователя, через которое **любой** AI-агент — Claude.ai, ChatGPT, облачный OpenClaw, Hermes Agent, Claude Code — получает доступ к браузеру и файлам этого компьютера — и только к ним: других выходов наружу (почта, shell, произвольная сеть) через gate4.ai нет. Агент не получает прямого доступа и не видит пароли: каждый его запрос проходит через **policy engine**, который разрешает, запрещает или запрашивает подтверждение у человека, подставляет секреты сам и сохраняет доказательство выполненного действия.

Транспорт «облачный агент → мой компьютер» уже существует во многих вариантах. Ценность продукта — **слой политик поверх него, единый для всех агентов**.

## Проблема

1. **Агентам дают слишком много.** Персональные ассистенты (OpenClaw, Hermes и др.) получают shell, залогиненный браузер и почту целиком. Итог 2026 года: CVE, вредоносные skills в маркетплейсах, десятки тысяч открытых в интернет инстансов, запреты на рабочих ноутбуках.
2. **Prompt injection превращается в действия.** Письмо или веб-страница с инструкцией может заставить агента переслать данные или отправить деньги.
3. **Агенты отчитываются «сделано», не сделав.** Самооценка агентов систематически завышена; проверки по факту нет.
4. **Существующие защиты не для людей.** MCP-шлюзы и credential-прокси — корпоративные: RBAC, SSO, SOC. Правила на уровне «какой инструмент», а не «кому и сколько».
5. **У каждой платформы свой мост и свои права.** Claude in Chrome — только для Claude, OpenClaw nodes — только для OpenClaw. Единых правил «для всех моих агентов» нет.

## Для кого

- **Основная аудитория (глобально):** пользователи персональных агентов — OpenClaw, Hermes, Claude Code / Claude.ai, ChatGPT, — которые уже доверяют агенту почту, файлы и рутину и хотят ограничить риск.
- **Локальное применение (РФ):** бытовые сценарии (ЖКХ, штрафы, документы), где у сервисов нет API и единственный путь — браузер пользователя.

Основной пользователь — не программист. Политики настраиваются в Web UI; файл конфигурации доступен, но нужен только техническим пользователям. Свежая установка открывает в Web UI мастер первого запуска: какой ассистент → что ему можно (папки, сайты, решения по группам действий «читать / менять / отправлять») → проверка с первым подтверждением. Основной язык интерфейса — английский, русский — перевод (выбор языка — в Web UI, по умолчанию — по языку браузера).

## Как это работает

```
 Claude.ai / ChatGPT / облачный OpenClaw / Hermes / Claude Code
                         │  remote MCP (OAuth) или CLI по HTTPS — отдельный токен на агента
                         ▼
              Relay (исходящее соединение, без открытых портов)
              или свой HTTPS-адрес устройства
                         │
┌─────────────── Приложение на компе (трей) ───────────────────┐
│  Policy engine: агент × действие × данные →                  │
│                 allow / deny / ask  + лимиты, whitelist      │
│  Подтверждения: уведомление на компе + Telegram / телефон    │
│  Хранилище секретов: агент видит алиасы, не пароли           │
│  Журнал + доказательства (скриншот, ответ сервера, выписка)  │
├──────────────────────────────────────────────────────────────┤
│  Встроены: Браузер (отдельный профиль Chrome, домены по      │
│            списку доступа) · Файлы (папки по списку доступа) │
│  Коннекторы к сайтам (WASM, из магазина) — поверх браузера   │
└──────────────────────────────────────────────────────────────┘
```

**Пример потока**

1. Агент в Claude.ai вызывает `browser.act` — нажать «Оплатить» на странице `account.example.org`, открытой в сеансе браузера.
2. Policy engine: в списке доступа Браузера для `account.example.org` нет своей строки, действует строка `*` → **ask**.
3. В Telegram: «Claude.ai хочет нажать на account.example.org `#a3f9c21e` [Разрешить] [Отклонить] [Показать текст] [➕ В разрешённые: account.example.org] [⛔ В запрещённые]».
4. Пользователь нажимает «Разрешить» → встроенный браузер выполняет клик в выделенном профиле Chrome; «В разрешённые» заодно добавило бы строку в список, и дальше этот сайт не спрашивал бы.
5. Шлюз сохраняет снимок элемента как доказательство, проверяет результат на странице и возвращает агенту итог. Квитанция — в журнал.

При отказе агент получает честную, понятную ошибку: `denied_by_policy: recipient not in allowlist; user notified`. Маскировка отказа под сбой провоцирует агента на повторы и обходные пути.

## Принципы дизайна

1. **Высокоуровневые инструменты вместо «сырого» доступа.** `files.append(...)`, действия коннекторов к конкретным сайтам — к ним применимы правила. Сырой браузер — только домены из списка; действия на странице (клик, ввод) — класса `write`, под правилами и подтверждением, как любое действие.
2. **Решает код, а не LLM.** Политики детерминированы и не обходятся промптом. LLM в решении не участвует.
3. **Недоверенные данные помечаются.** Всё, что пришло с веб-страниц и из файлов, имеет метку происхождения. Пример правила: нельзя отправить деньги получателю, который появился только из недоверенного контента.
4. **Права на каждого агента отдельно.** Свой токен, свой профиль прав, отзыв в один клик.
5. **Доказательство вместо «сделано».** Каждое действие с эффектом подтверждается фактом: ответ сервера, письмо в «Отправленных», строка в выписке, скриншот.
6. **Секреты не покидают устройство.** Агент оперирует алиасами (`@amazon`, `@gosuslugi`); реальные данные подставляет ядро и только по адресу привязки учётки; коннектор значений не видит. Relay видит только шифротекст.
7. **Открытый исходный код.** Никто не поставит закрытый бинарник с доступом к браузеру и файлам. Ядро, relay и коннекторы — AGPL-3.0 (доработки раскрываются, в том числе при работе как сервис). SDK — Apache-2.0, registry (данные индекса) — CC0. Подписанные и воспроизводимые сборки.
8. **Агент-агностичность.** MCP для любых клиентов, CLI для агентов с shell и скриптов, skill с инструкцией для агентов. Политики применяются только в ядре — способ вызова на решение не влияет.

## Ключевые решения

| Тема | Решение |
|---|---|
| Название | gate4.ai; CLI и идентификаторы — `gate4ai` |
| Лицензия | ядро, relay и коннекторы — AGPL-3.0; sdk-go — Apache-2.0; registry (данные индекса) — CC0; внешний вклад — с CLA и DCO |
| Исходный код и выпуск | один репозиторий и один Go-модуль (ядро, трей, relay, sdk-go, официальные коннекторы, сквозные тесты); один тег — один релиз всего с общей версией; индекс registry — отдельный репозиторий |
| Платформы | macOS, Linux, Windows |
| Установка | `install.sh` (macOS, Linux) и `install.ps1` (Windows) со страницы gate4.ai: бинарники в каталог пользователя без sudo, автозапуск; браузеру агентов — проверка Chrome, на Linux без графики ещё Xvfb и шрифтов (`gate4ai browser setup`), установка недостающего только с согласия (вопрос в терминале или `GATE4AI_INSTALL_DEPS=1`); `GATE4AI_NO_BROWSER=1` — без этой проверки |
| Стек | Go (daemon, CLI, трей, коннекторы, браузерный воркер, relay) |
| Политики | своя декларативная модель + условия на CEL (`cel-go`); ABAC с профилями как слоем ролей; файл конфигурации — YAML |
| Интерфейсы для агентов | MCP + CLI + skill; один бинарник `gate4ai`, всё генерируется из манифестов коннекторов |
| Relay | собственный; WebSocket поверх TLS:443 + yamux; TLS-passthrough |
| Публичный адрес устройства | один адрес для всего, разделение по путям: MCP на корне адреса (`POST`/`DELETE` `/`) + OAuth, `/v1/…` (CLI агентов), `/ui/` (Web UI), `/telegram` (вебхук); у каждого пути своя аутентификация, API владельца снаружи нет. Через relay или без него (`gate4ai daemon --public`) |
| Изоляция локальных агентов | по умолчанию процессная песочница Anthropic sandbox-runtime + наш Egress Proxy; контейнер и microVM — опции |
| Журнал | квитанция на каждое действие; цепочка хэшей + подписанные чекпоинты, relay — свидетель; шифрование `age` |
| Выходы наружу | только два, оба встроены в бинарник и не удаляются: **Браузер** (выделенный профиль Chrome) и **Файлы**; доступ к ним — списки доменов и папок с режимом (`allow` / `read` / `connector` / `ask` / `deny`, для папок ещё `append`); коннекторы магазина — только WASM к сайтам поверх браузера, своей сети у них нет |
| Браузерный движок | прямой Chrome DevTools Protocol в выделенном профиле Chrome; без LLM: страницу читает сам агент |
| Подтверждения в Telegram | личный бот пользователя (BotFather); daemon работает с Telegram API напрямую |
| Вход в удалённый Web UI | так же, как на устройстве (см. «Защита входа в Web UI»): по постоянному адресу `/ui/` (закладка, QR-код в Настройках, `gate4ai ui --remote` печатает адрес) с паролем и, если включено, подтверждением в Telegram-боте; удалённо — подтверждения, журнал, сеансы браузера (просмотр; управление вне handoff — с подтверждением в Telegram, если вход был без него) и состояние сервера (только чтение), изменения политик, агентов и секретов — только локально |
| Защита входа в Web UI | пароль обязателен всегда (хранится хэшем argon2id), по желанию владельца — ещё подтверждение входа в личном Telegram-боте (другое устройство). Вход по постоянному адресу Web UI, локально и удалённо; `gate4ai ui` и трей просто открывают адрес; сессия — 12 часов. Пароль есть с первой секунды: на свежей установке (и при сбросе) daemon при старте сам генерирует сложный пароль (вид `xxxxx-xxxxx-xxxxx-xxxxx`, ≈100 бит), в State Store кладёт только хэш, а открытый текст держит в памяти и отдаёт владельцу через сокет владельца, пока этим паролем не вошли: его печатают установщик и `gate4ai ui --print` (строки `Web UI:`, `Password:`, `From the internet:` в stdout; `--json` — для программ), показывает трей; установщик всегда доводит до этих строк, при неудаче автозапуска подняв daemon на сессию. Пароль, прочитанный через сокет владельца не человеком в терминале, а скриптом или агентом (установка через OpenClaw), считается прошедшим через чат: после входа Web UI на каждой странице напоминает сменить его или включить подтверждение в Telegram. Формы «задайте пароль» нет ни локально, ни удалённо. Забытый пароль: `gate4ai ui --reset-password` на этом компьютере — новый сгенерированный пароль, подтверждение в Telegram выключено, сессии закрыты, в Telegram — уведомление; запасной путь — `gate4ai daemon --reset-ui-login`. Защита от перебора пароля: после 5 неверных подряд каждая попытка ждёт вдвое дольше (до 15 минут), счётчики локального и удалённого входа раздельные; в Telegram одновременно ждёт ответа не больше одного запроса входа |
| Коннекторы | только `runtime: wasm` (wazero, собственный ABI), без сети: наружу — `service_call` к встроенному браузеру на сайтах из `sites` манифеста, к файлам — `fs_*` в папках из `folders`; владелец сужает эти списки на странице коннектора; Браузер и Файлы — `runtime: builtin`, часть ядра; коннекторы вызывают браузер по контракту из манифеста |
| Межпроцессное взаимодействие | stdio для дочерних процессов; unix-сокет / named pipe для трея и CLI на том же компьютере; HTTPS на публичный адрес — для удалённых агентов; без TCP на localhost |

## Интерфейсы для агентов: MCP, CLI, skill

Один и тот же набор действий доступен через несколько фронтов. Политики, подтверждения и журнал — только в ядре, поэтому результат не зависит от способа вызова, а обойти правила через другой фронт нельзя.

```
              ┌─ MCP (stdio / HTTPS)             ─┐
 агенты ─────►│                                   │
 скрипты ────►├─ CLI `gate4ai` (сокет / HTTPS)    ├──► Action Pipeline ──► коннекторы
 люди ───────►└─ Web UI (localhost / HTTPS /ui/)  ┘    (одни политики, один журнал)
```

### Зачем и MCP, и CLI

| | MCP | CLI `gate4ai` + skill |
|---|---|---|
| Облачные агенты без shell (Claude.ai, ChatGPT) | **единственный вариант** | не работает |
| Агенты с shell (Claude Code, Codex, OpenClaw, Hermes, Aider) | работает | работает; агенты хорошо владеют CLI |
| Агенты с shell на другом компьютере | remote MCP | работает: `GATE4AI_URL=https://<адрес устройства>`, те же команды |
| Расход контекста | схемы всех инструментов постоянно в контексте | skill подгружается по необходимости, детали — через `gate4ai <команда> --help` |
| Скрипты и cron | неудобно | естественно: `gate4ai files append …` из bash / Python |
| Технические пользователи | нужен MCP-клиент | `gate4ai log`, `gate4ai agents revoke`, `gate4ai policy test` |
| Агенты без поддержки MCP | не работают | работают при наличии shell |

### Бинарник `gate4ai`

- **Один бинарник, два режима:** `gate4ai mcp` — MCP-сервер (stdio; он же используется внутри песочниц и контейнеров), `gate4ai <коннектор> <действие> …` — CLI. Оба — тонкие клиенты к daemon: на том же компьютере — через сокет, с другого — по HTTPS на публичный адрес устройства (`GATE4AI_URL`).
- **Команды, MCP-инструменты, skill и формы Web UI генерируются из манифестов коннекторов** — новое действие появляется везде сразу.
- **Машиночитаемый вывод:** JSON по умолчанию; коды выхода для `denied_by_policy`, `pending_approval`, `verification_failed`. Исключение — человек в терминале: если stdout — терминал, списки и состояние для владельца (агенты, подтверждения, коннекторы, хранилище, версии политики, состояние daemon, relay и автозапуска) печатаются таблицей, а ошибки — текстом с подсказкой, что делать; `--json` или `GATE4AI_OUTPUT=json` возвращают JSON. Агенты и скрипты (stdout — pipe или файл) всегда получают JSON; коды выхода от формата не зависят.
- **Подтверждения:** вызов ждёт решения (`--wait 10m`) или сразу возвращает `pending` с ID; статус — `gate4ai status <id>`.
- **Обнаружение:** `gate4ai tools --json` — только действия, разрешённые профилю этого агента (тот же отфильтрованный каталог, что в MCP).

### Skill для агентов

Один `SKILL.md` в общем формате навыков Claude Code / Hermes / OpenClaw, генерируется из манифестов:
- всегда использовать `gate4ai` для действий вне своей среды и не искать обходных путей;
- основные команды с примерами;
- реакция на отказ: не повторять, не обходить, сообщить пользователю причину;
- ожидание подтверждения, повтор при «устройство офлайн», проверка результата (`verified: true / false`).

### Идентичность и права

- Агент вызывает `gate4ai` / MCP со своим ключом (токеном). Ключ лишь идентифицирует агента и не даёт ничего сверх его профиля — даже прочитав его, агент не расширит права.
- **Агент подключается сам, владелец только подтверждает.** Локальному агенту с shell не нужно вписывать токен в окружение: CLI узнаёт агента (`GATE4AI_AGENT`, признаки, которые агент ставит своим процессам, — `CLAUDECODE=1` и т.п., — процессы-предки), создаёт ключ и сохраняет его в каталоге ключей gate4ai (по файлу на агента, права 0600; daemon хранит только хэш), а daemon в ответ на запрос подключения придумывает короткий код. Агент показывает код человеку в чате; владелец сверяет его с кодом в запросе и подтверждает — только в Web UI или Telegram (не командой CLI и не кнопкой трея). Код придумывает daemon, поэтому чужой процесс не подберёт ключ под тот же код. После подтверждения агент работает своим ключом сразу, без перезапуска.
- **Один ключ на тип агента по умолчанию** (все сессии Claude Code — агент `claude-code`) и **ключи с привязкой к каталогу** (`gate4ai pair --here`): такой ключ принимается только от агента, запущенного в этом каталоге, и у него может быть свой профиль; новый агент такого типа по умолчанию получает профиль агента своего типа. Каталог агента — каталог запуска корня агента: самого внешнего процесса-агента среди предков собеседника (подагенты и вложенные запуски агента относятся к нему; `cd` в shell агента каталог не меняет); daemon узнаёт его сам по процессу-собеседнику сокета, а не со слов клиента.
- Человек на хосте использует `gate4ai` с правами владельца через локальный сокет с проверкой собеседника; агентский ключ этих прав не получает. Если среди предков собеседника сокета владельца есть агент, сокет отвечает `agent_required`, а не правами владельца.
- **Граница.** Процесс того же пользователя ОС, отвязанный от дерева процессов агента и без его признаков в окружении, так не опознаётся и может прочитать чужой ключ: опознание и привязка к каталогу защищают от случайного и «ленивого» обхода, изоляцию даёт только песочница (`gate4ai run`, см. «Изоляция локальных агентов») или отдельный пользователь ОС; последний рубеж — подтверждения человека.
- В журнал (и в запрос подтверждения) пишется, откуда пришёл вызов: каталог агента, сессия и цепочка процессов до корня агента; удалённый CLI сообщает каталог сам — так он и помечен.
- Аутентифицируется агент, а не человек за ним; человек — владелец устройства.

| Кто | Канал | Аутентификация |
|---|---|---|
| Облачный агент | remote MCP | OAuth 2.1: динамическая регистрация (RFC 7591), code + PKCE S256, refresh с ротацией, отзыв (RFC 7009), метаданные (RFC 8414, RFC 9728); подключение подтверждается одноразовым кодом владельца, код привязан к агенту |
| Удалённый агент с shell | CLI по HTTPS | ключ агента: спаривание по коду так же, через публичный адрес (без привязки к каталогу); или токен (`GATE4AI_TOKEN`) — для скриптов и CI |
| Локальный агент | сокет агентов, stdio, песочница | ключ агента: спаривание по коду (по умолчанию — один на тип агента, дополнительно — с привязкой к каталогу); или токен (`GATE4AI_TOKEN`); в песочнице — сокет и токен на каждый запуск |
| Владелец на устройстве | сокет владельца, Web UI на localhost | проверка собеседника; Web UI — пароль и, если включено, подтверждение в Telegram (см. «Защита входа в Web UI») → сессия |
| Владелец удалённо | `/ui/` на публичном адресе | вход, как на устройстве: пароль, Telegram → своя сессия (только подтверждения и журнал) |
| Telegram | вебхук `/telegram` | секрет, выданный при `setWebhook`; команды — только от Telegram ID владельца |

## Политики

### Списки доступа Браузера и Файлов

Первый уровень прав — два списка, общие для всех агентов, в Web UI (вкладки «Браузер» и «Файлы» раздела «Доступ»), в CLI (`gate4ai access sites | folders set <значение> <режим>`) и в YAML (`access.sites`, `access.folders`):

- **Домены** (`*.example.org` — поддомены и сам `example.org`, `*` — любой сайт): `allow` — всё без вопроса; `read` — действия класса `read` (чтение страниц и снимки, `open` / `observe`, запросы `get` / `head`) без вопроса, действия класса `write` (клики, ввод, `post` и другие запросы с эффектом, вход, загрузка) — с подтверждением (владелец принимает, что и GET-запрос на сайте может что-то изменить); `connector` — только через коннектор магазина, агенту напрямую — отказ; `ask` — каждое действие с подтверждением; `deny` — закрыто для всех, включая коннекторы.
- **Папки** (путь — папка и всё внутри; `*` и `**` — маски): те же режимы и ещё `append` — чтение и добавление без вопроса, перезапись — с подтверждением.
- Решает самая конкретная подходящая строка, при равенстве — строже. Домен или папка без строки закрыты. Свежая установка: `*` → `read`, `~/Documents` → `ask`.
- Порядок с правилами профиля: `deny` в списке — всегда отказ; сработавшее правило профиля сильнее строки списка; без правила решает список (вместо умолчания класса действия).
- Запрос подтверждения по строке `ask` (и по `read` для изменений) предлагает не только «Разрешить» и «Отклонить», но и «Добавить в разрешённые» (действие чтения — `read`, изменение — `allow` / `append`) и «Добавить в запрещённые» — в Web UI и в Telegram.
- Коннектор магазина объявляет свои сайты и папки с режимом в манифесте (`sites`, `folders`; режима `connector` у него нет); при установке они копируются в его настройки, владелец их меняет. Вызов браузера из коннектора проходит, если его разрешают и строка коннектора, и строка Браузера (`connector` там считается разрешением); `ask` у коннектора — подтверждение внутри вызова. Домен коннектора, закрытый в Браузере, подсвечивается на странице коннектора.

### Модель

- **Профили** (слой ролей): агенту назначается профиль — `assistant`, `drafts-only` и т.п. Профиль перечисляет доступные коннекторы; коннекторы вне профиля агент не видит вовсе.
- **Правила** (ABAC): `action` + условие `when` на CEL + `effect` (`allow` / `deny` / `ask`) + `obligations` (`verify_statement`, маскирование полей, лимит) + `reason`.
- **Вход условий:** аргументы действия, метки происхождения (`provenance`), счётчики (`counters.spent_today`), списки (`lists.*`), время. Собственные функции CEL — `glob()`, `domain_matches()`.
- **Порядок решения:** `deny` важнее `ask`, `ask` важнее `allow`. Если ни одно правило не сработало — значение по умолчанию класса эффекта действия: `read` → `allow`, `write` / `external` / `money` → `ask`. Правило с шаблоном действия (`browser.*`, `*`) не разрешает запросы браузера, меняющие данные на сайтах с cookies пользователя (`browser.post` / `put` / `patch` / `delete`), и вход учётками (`browser.login`, `browser.fill_secret`): их разрешает только правило, которое называет действие; сохранение политики с таким шаблоном предупреждает об этом.
- **Объяснение решения** — `id` и `reason` сработавшего правила; показывается агенту при отказе и человеку в запросе подтверждения.
- **Одно подтверждение на действие.** Всё, что ядро делает внутри действия от имени того же агента — использование учёток, вход коннектором входа, вложенные вызовы браузера, — покрыто решением по самому действию: «оплатить через коннектор банка» спрашивается один раз, без второго вопроса «отдать ли пароль от банка». Исключение — строка `ask` в сайтах самого коннектора. Запрос подтверждения перечисляет учётки, которые будут использованы; вложенные события пишутся в журнал со ссылкой на квитанцию действия.

### Как редактируются

- **Одна модель конфигурации**, два представления: Web UI для обычных людей и файл YAML для технических пользователей. Web UI собирает условия из блоков («получатель из списка…», «сумма не больше…») и генерирует CEL; сырой CEL — для технических пользователей.
- Готовые наборы правил («только чтение», «спрашивать обо всём» и др. — для поставленных коннекторов, с предпросмотром добавляемых правил) и **симулятор** («что будет, если агент попробует…»).
- Каждое изменение — версия с откатом; изменения требуют локальной аутентификации пользователя, кроме действия агента `gate4ai.change_policy`, которое подтверждает владелец (правило `allow` на него не действует, `deny` — запрещает). Кнопка «разрешать так всегда» в запросе подтверждения (в Web UI на этом компьютере) называет, что именно будет разрешено — папку или сайт из аргументов запроса («Разрешать всегда в ~/notes»), — и по нажатию сразу записывает правило `allow` с этим условием для прав агента; правило видно в «Доступ → Правила», его можно сузить или удалить, откат — в версиях. Если запрос нельзя ограничить папкой или сайтом (адресаты, суммы), кнопки нет — правило пишется в форме.

### Пример

```yaml
access:
  sites:
    - { domain: "*", access: read }                    # любой сайт: читать без вопроса, менять — спросить
    - { domain: "*.example.org", access: allow }       # всё без вопроса
    - { domain: bank.example, access: connector }     # только через коннектор банка
    - { domain: ads.example, access: deny }
  folders:
    - { path: ~/Documents/obsidian, access: append }  # заметки: читать и дописывать
    - { path: ~/Documents, access: read }

agents:
  claude-ai:      { profile: assistant }
  claude-code:    { profile: files-only }

lists:
  payees_utilities: ["@uk-dom", "@mosenergosbyt"]

profiles:
  assistant:
    connectors: [files, browser, payments]
    rules:
      - id: payments-utilities
        action: payments.pay_bill
        when: payee in lists.payees_utilities && amount <= 15000
        effect: ask                      # каждый платёж — с подтверждением
        obligations: [verify_statement]
      - id: daily-cap
        action: payments.*
        when: counters.spent_today + amount > 30000
        effect: deny
        reason: "Дневной лимит 30 000 ₽"

  files-only:
    connectors: [files]
    rules:
      - { id: no-write, action: files.write, effect: deny }

connectors:
  payments:                               # коннектор банка из магазина
    sites: [{ domain: bank.example, access: allow }]

approvals:
  channels: [desktop, telegram]
  timeout: 30m
  on_timeout: deny
```

### Зоны доверия

```
 ┌─ НЕДОВЕРЕННАЯ ЗОНА ──────────────────────────────────────────────────┐
 │ Агенты: Claude.ai, ChatGPT, облачный OpenClaw, Hermes, Claude Code   │
 │ Контент: входящие письма, веб-страницы, файлы от третьих лиц         │
 └───────────────────────────────────┬──────────────────────────────────┘
                                     │ MCP / CLI (HTTPS, stdio, сокет)
 ┌─ ТРАНСПОРТ (не должен видеть данные) ────────────────────────────────┐
 │ Relay: публичный HTTPS-адрес устройства, исходящий туннель с компа   │
 │ (или свой HTTPS-адрес: `--public`)                                   │
 └───────────────────────────────────┬──────────────────────────────────┘
                                     │
 ┌─ ДОВЕРЕННОЕ ЯДРО (устройство пользователя) ──────────────────────────┐
 │ gate4ai daemon: политики, подтверждения, секреты, журнал             │
 └───────────────────────────────────┬──────────────────────────────────┘
                                     │ только через коннекторы
 ┌─ ВНЕШНИЕ СЕРВИСЫ ────────────────────────────────────────────────────┐
 │ Сайты (банк, ЖКХ, Госуслуги…) через браузер, файловая система        │
 └──────────────────────────────────────────────────────────────────────┘
```

Главное правило: **агент не имеет пути к внешним сервисам, кроме как через ядро**, а ядро не принимает решений на основе текста от агента — только на основе структурированных параметров действия и правил.

### Компоненты

```
                ┌────────────────────────── gate4ai daemon ────────────────────────────┐
 агент MCP/CLI► │ MCP Front ─► Action Pipeline ──────────────────────────────► ответ   │
                │  (OAuth,      │                                                      │
                │   каталог     ├─ 1. Нормализация (схема действия, аргументы)         │
                │   инструментов├─ 2. Обогащение (агент, метки происхождения, счётчики │
                │   по профилю) ├─ 3. Policy Engine (PDP) → allow/deny/ask + условия   │
                │               ├─ 4. Approval Service (desktop / Telegram / web)      │
                │               ├─ 5. Подстановка секретов (Vault)                     │
                │               ├─ 6. Executor → Коннектор (единая точка исполнения)   │
                │               ├─ 7. Verification (проверка результата по факту)      │
                │               └─ 8. Audit + Evidence, разметка ответа агенту         │
                │                                                                      │
                │ Web UI ─ Config Store ─ State Store (SQLite) ─ Notification Service  │
                │ Egress Proxy (сетевой выход изолированных агентов) ─ Agent Launcher  │
                └──────────┬───────────────────────┬────────────────────────┬──────────┘
                           │                       │                        │
                 «Браузер» и «Файлы»            Коннекторы к сайтам
                 (встроены в ядро: Chrome-      (WASM-модули; наружу —
                  профиль, разрешённые папки)    только через «Браузер»)
```

**MCP Front**
- Транспорты: stdio (локальные агенты), канал из песочницы / контейнера (см. «Изоляция локальных агентов»), Streamable HTTP через relay (облачные агенты).
- Встроенный OAuth 2.1 authorization server: каждый агент регистрируется отдельно и получает свой токен; отзыв — в один клик в Web UI.
- Каталог инструментов фильтруется по профилю агента. Политику агент меняет только действием `gate4ai.change_policy` встроенного коннектора `gate4ai` — всегда с подтверждением владельца (см. «Безопасность самого шлюза»).

**Публичный адрес устройства** — один обработчик, который обслуживают relay и прямой HTTPS (`gate4ai daemon --public`: свой сертификат или loopback за reverse proxy этого компьютера):

| Путь | Что | Учётные данные |
|---|---|---|
| `/` (POST, DELETE), `/.well-known/…`, `/authorize`, `/token`, `/register`, `/revoke` | remote MCP и OAuth 2.1 | токен агента |
| `/v1/whoami`, `/v1/tools`, `/v1/call`, `/v1/status/{id}` | CLI удалённых агентов | токен агента |
| `/v1/pair`, `/v1/pair/{id}` | запрос агента на подключение (спаривание по коду) | без учётных данных: только хэш нового ключа; решение — у владельца, число ждущих запросов ограничено |
| `/ui/` | удалённый Web UI | сессия: пароль и, если включено, Telegram — по защите входа |
| `/telegram` | вебхук бота подтверждений | секрет вебхука |

Учётные данные одного пути не действуют на другом (это проверяет тест); API владельца на публичном адресе нет.

**Action Pipeline** — единственный путь любого действия. Все шаги выполняются в одном месте и в одном порядке, поэтому сюда же подключаются журнал, лимиты и проверка результата.

**Policy Engine (PDP)** — детерминированный, без LLM; модель и порядок решения — в разделе «Политики».

**Approval Service**
- Каналы: уведомление на компьютере, личный Telegram-бот пользователя, Web UI, браузерный push (Web Push) для Web UI — локального и удалённого `/ui/` на адресе устройства.
- **Браузерный push:** краткое уведомление (агент, действие, короткий хэш) со ссылкой на страницу подтверждения; решение принимается только на странице Web UI с сессией. Уведомление идёт через push-сервис браузера (Google, Mozilla, Apple), а не через серверы gate4.ai, и зашифровано для подписанного браузера (RFC 8291); сервер подписан ключом VAPID устройства (RFC 8292).
- **Telegram:** пользователь создаёт своего бота через BotFather и вставляет токен в Web UI (токен — в Vault); daemon опрашивает Telegram API исходящими запросами (или, по выбору, получает вебхук на `/telegram` публичного адреса), бот принимает команды только от Telegram ID владельца. Общего бота gate4ai нет — содержимое подтверждений не проходит через наши серверы.
- Запрос показывает **что именно** будет сделано (получатель, сумма, текст, предпросмотр) и **почему** нужно подтверждение; в мессенджере — кратко, с хэшем квитанции для подробностей.
- Таймаут → `deny` по умолчанию.

**Vault (секреты)** — подробно в [secret-architecture.md](secret-architecture.md)
- Значения видит только ядро (и доверенный браузерный пакет — только при вводе в форму на origin привязки); коннекторы называют алиас или слот учётки и значений не видят.
- Привязка задаёт, куда секрет можно отдать: точный origin (схема, хост, порт; без масок). Единственный способ — ввод в форму браузера по учётке входа (`credentials`: поля, отправка, признак успеха или коннектор входа `via`) на origin привязки; своей сети у коннекторов нет, поэтому подстановки в запросы нет. Ответы и доказательства маскируются, включая производные формы значения (base64, URL-, JSON- и HTML-экранирование, hex).
- Значения — в keychain ОС (запись на алиас и индекс алиасов). Без keychain (`--keystore file`) значения лежат в `keys.json` (права 0600) **открытым текстом** — об этом предупреждают daemon и инструкция; daemon, однажды работавший с keychain, не переключается на файл молча.
- Ответы агенту проходят фильтр: известные секреты и чувствительные поля, объявленные в манифесте, маскируются.

**Provenance (метки происхождения)**
- Всё, что возвращается агенту из недоверенных источников (веб-страницы, файлы), получает метку и идентификатор источника.
- Когда значения из помеченных данных появляются в аргументах действия (адрес получателя, реквизиты, сумма), метка переносится на действие и доступна правилам (`provenance.to`).
- Сопоставление эвристическое (точное совпадение нормализованных значений) — ограничивает ущерб, но не гарантирует полноту.

**Verification** — проверка результата по независимому каналу: операция в выписке, статус на сайте, содержимое файла. Действие без успешной проверки помечается «не подтверждено», а не «выполнено».

**Config Store / State Store** — модель конфигурации с версиями; SQLite для счётчиков лимитов, очереди подтверждений, индекса журнала.

**Agent Launcher и Egress Proxy** — запуск локальных агентов в песочнице и единственный сетевой выход для них (см. «Изоляция локальных агентов»).

### Процессы и стек

| Процесс | Назначение | Технология |
|---|---|---|
| `gate4ai daemon` | ядро: MCP Front, pipeline, PDP, vault, журнал, Web UI (localhost; удалённо — `/ui/`), публичный адрес | Go; тот же бинарник, что и CLI |
| `gate4ai` | CLI для агентов, скриптов и людей + режим `gate4ai mcp`; тонкий клиент к daemon | Go, статический бинарник |
| `gate4ai-tray` — трей | статус, уведомления, быстрые подтверждения, открытие Web UI; отдельный бинарник (на macOS нужен cgo) | Go + fyne.io/systray |
| Коннекторы | действия с эффектом; только функции хоста, без сети | WASM-модули в daemon (wazero, собственный ABI) |
| Браузерный воркер | CDP, executor — встроенный компонент «Браузер» в процессе daemon | Go, websocket к Chrome |
| Chrome (выделенный профиль) | живые сессии пользователя | системный Chrome |
| Telegram-бот | канал подтверждений | личный бот пользователя; часть daemon (Go) |
| Песочницы / контейнеры агентов | изолированные Claude Code / Codex / OpenClaw / Hermes | sandbox-runtime; Docker / Podman |
| Relay | публичный адрес, удалённый доступ, сопряжение устройств, свидетель чекпоинтов | Go |

**Связь между процессами**
- **daemon → коннекторы:** WASM-модули внутри daemon, взаимодействие только через функции хоста (см. connector-architecture.md).
- **daemon → Chrome:** выделенный профиль запускает сам daemon как дочерний процесс; CDP по pipe (`--remote-debugging-pipe`), порта отладки у Chrome нет; клиентам браузера (подключениям воркера к вкладкам и к браузеру) — мультиплексор на 127.0.0.1 с секретным токеном в адресе, без токена — 404. На Windows pipe пока не передаётся (Go `exec.Cmd.ExtraFiles`) — там порт отладки на 127.0.0.1, как раньше. Упавший Chrome перезапускается при следующем действии.
- **трей и CLI → daemon:** unix-сокет (macOS / Linux) или named pipe (Windows) за общим интерфейсом; доступ только текущему пользователю (права `0600` / security descriptor с SID пользователя), проверка собеседника (`getpeereid` / `SO_PEERCRED` / `GetNamedPipeClientProcessId`), на Windows — защита от перехвата имени pipe (`FILE_FLAG_FIRST_PIPE_INSTANCE`).
- **Web UI → daemon:** HTTP на localhost с сессией; удалённо — `/ui/` на публичном адресе устройства (relay или `--public`).
- **удалённые агенты → daemon:** HTTPS на публичный адрес устройства (remote MCP, CLI с `GATE4AI_URL`).
- **песочница / контейнер агента → daemon:** см. «Изоляция локальных агентов».
- TCP на localhost без аутентификации не используется нигде (кроме порта отладки Chrome на Windows — см. выше).

### Режимы развёртывания

1. **Ноутбук пользователя** — всё на одной машине; пока компьютер спит, агенты получают «устройство офлайн» и повторяют позже.
2. **Постоянно включённое устройство** (мини-ПК, Mac mini, сервер без графики) — daemon без трея, Web UI удалённо через relay или `--public`; рекомендуется, когда агенты работают круглосуточно. Браузер на сервере без графики — на виртуальном экране Xvfb (без него — headless), сеансы агентов человек видит по ссылке в Web UI. Агент на том же сервере (OpenClaw и т.п.) — отдельным пользователем ОС или в `gate4ai run`: процесс того же пользователя прочитал бы данные gate4ai. Страница **Настройки → Сервер** (доступна и удалённо, только чтение) показывает состояние компонентов — служба и linger, хранилище ключей, адрес из интернета, защита входа, Telegram, пакет браузера, Chrome, экран, шрифты, агенты через локальный сокет — и что сделать с каждым (команда для терминала или кнопка на настройку). Подробнее — [headless-server.md](headless-server.md).
3. **Изолированные агенты на той же машине** — локальные агенты в песочнице, доступ к хосту только через gate4.ai.

### Безопасность самого шлюза

- Агент не может в обход владельца изменить политику, расширить права или прочитать секреты: единственный инструмент изменения — `gate4ai.change_policy` (ниже), его всегда подтверждает владелец; файлы конфигурации и хранилища защищены.
- **Самонастройка через агента:** у daemon есть встроенный коннектор `gate4ai`: вместо внешнего сервиса он меняет политику самого gate4ai. Его действие `gate4ai.change_policy` (класс `write`) меняет любую часть политики — правила любого профиля, списки, настройки и установку коннекторов — и всегда требует подтверждения владельца (в запросе — сначала что именно изменится, в том числе замена существующих правил, и возможности, runtime, классы действий и лимиты устанавливаемых коннекторов; затем, отдельно и с пометкой, — слова агента; одобрить можно только в Web UI, где видны все правки, отклонить — в любом канале), правило `allow` на него не действует (агент не расширяет себе права — сайты, правила, учётки — сам), правилом `deny` его можно запретить. Каждое изменение — версия политики с откатом. Устанавливается ровно то, что показано в запросе (версия, дайджест пакета или исходников своей сборки, возможности); если к исполнению это изменилось — отказ. Своя сборка агента — только `runtime: wasm`. Значения секретов так не задаются: правки с алиасами Vault и секретными полями ядро отклоняет до запроса подтверждения. Исключение — новая учётка входа (`add_credential`): только новая, только с новыми алиасами в своём пространстве имён (`@<учётка>.<поле>`), которых ещё нет в Vault и политике, и всегда с подтверждением человека; значения задаёт владелец. Запрос на установку своей сборки и правки сайтов и папок коннектора (`sites`, `folders`) и сайтов входа (`bind` учёток) несёт явное предупреждение.
- Web UI слушает только localhost; удалённо — `/ui/` на публичном адресе со входом владельца по паролю, только подтверждения, журнал, сеансы браузера и состояние сервера (пароль и подтверждение в Telegram — см. ниже).
- Адрес Web UI знает и агент, запущенный от того же пользователя ОС (сокет владельца отказывает опознанному агенту, но отвязанный процесс без его признаков так не опознаётся), поэтому сам адрес сессии не даёт: вход в Web UI — локальный и удалённый — всегда по паролю (только хэш argon2id, с задержкой после неверных попыток), по желанию владельца — ещё и с подтверждением входа в личном Telegram-боте. Пароль генерирует daemon при первом запуске — до того, как Web UI станет доступен, в том числе с публичного адреса: окна «пароля ещё нет», в которое агент или кто-то из интернета задал бы его первым, не существует. Открытый текст на диск не пишется: его показывают установщик, `gate4ai ui` и трей, пока им не вошли. Настройки защиты — не в конфигурации (агент не меняет их через `gate4ai.change_policy`) и меняются только из сессии и с текущим паролем. Полностью от агента того же пользователя ОС это не изолирует (отвязанный процесс мог бы сбросить пароль через сокет владельца и прочитать новый), но готовой сессии он не получает, а сброс виден владельцу: сессии закрываются, в Telegram приходит уведомление.
- Подтверждения нельзя подделать текстом от агента: решение принимается только по нажатию в привязанном канале; запрос подписан и одноразовый. Перед исполнением одобренного действия политика проверяется заново (текущие правила, лимиты, профиль и статус агента): если теперь выходит отказ или лимит исчерпан — действие не исполняется.
- Подписанные обновления, воспроизводимые сборки, минимальная поверхность ядра; коннекторы — только в WASM-песочнице и без сети.

## Журнал и доказательства

- **Квитанция на каждое действие** — JSON (каноникализация RFC 8785): `id, ts, agent, action, args` (после маскирования), `decision {effect, rule_ids, reason}`, `approval {channel, who, at, hash превью}`, `execution {status, result_ref, page}` (`page` — адрес страницы, на которой выполнено действие Браузера; `status`: ok | error | invalid_result | skipped | started — квитанция-намерение до исполнения | interrupted; для действий с эффектом намерение пишется до исполнения, и без него действие не исполняется; итоговая квитанция ссылается на намерение полем `intent`), `decision.errors` — ошибки вычисления условий правил, `verification {method, status, evidence_refs[]}`, `prev_hash`. Квитанции — источник истины.
- **Целостность:** цепочка хэшей + подписанные чекпоинты, связанные между собой (раз в N записей / раз в сутки, ключ Ed25519 устройства в keychain); редактирование квитанций по сроку записывается в цепочку квитанцией `journal.redact` (хэш и хэш заголовка каждой стёртой) под чекпоинтом; хэш чекпоинта отправляется на relay как свидетель (relay видит только хэши).
- **Хранение:** SQLite — индекс (время, агент, действие, решение) и зашифрованные поля (AEAD на уровне приложения); доказательства (скриншоты, ответы серверов, `.eml`) — файлы с именем по sha256, каждый зашифрован `age`, ключ хранилища в keychain. В квитанции — только хэш доказательства, поэтому файл можно удалить (crypto-shredding), а цепочка продолжит сходиться.
- **Приватность:** скриншот элемента, а не страницы; поля паролей, карт, паспорта маскируются до записи; тексты проходят тот же фильтр, что ответы агенту.
- **Сроки по умолчанию** (настраиваются): квитанции — бессрочно; доказательства `money` — 3 года; прочие доказательства — 90 дней; отказы политики (`deny`) — 1 год; отклонения и таймауты подтверждений человеком хранятся как квитанции (бессрочно). Доказательство удаляется, только когда на него не ссылается ни одна квитанция со сроком, который ещё не истёк.
- **Экспорт и резервная копия:** `gate4ai export` — подписанный архив (квитанции, доказательства, чекпоинты, публичный ключ), `gate4ai verify` проверяет его где угодно; с `--passphrase-env` архив зашифрован паролем — это и резервная копия.
- **Ссылки в Telegram и уведомлениях:** запросы подтверждения и отчёты содержат краткий хэш квитанции (первые 8–10 символов, например `#a3f9c21e`) вместо подробностей — сообщение не перегружено, а по хэшу запись однозначно находится в Web UI или через `gate4ai show <hash>`.

## Relay

Relay — собственная часть продукта; внешние туннели и VPN-сервисы не требуются.

- **Публичный адрес для облачных агентов.** Устройство держит исходящее соединение к relay — **WebSocket поверх TLS на 443 + мультиплексор yamux** — без открытых портов и настройки роутера. Адрес устройства `<device-id>.relay.gate4.ai` (`device-id` случайный — имена сертификатов публичны в CT-логах) вписывается в Claude.ai / ChatGPT как custom connector.
- **Шифрование до устройства.** TLS-passthrough по SNI (relay читает только ClientHello); сертификат выпускается на устройство (ACME DNS-01, TXT-запись ставит API relay; `certmagic`); расшифровка только на устройстве.
- **Удалённый доступ человека к своему устройству.** Подтверждения, журнал и сеансы браузера (просмотр вживую; управление во время handoff, а вне его — если вход прошёл подтверждение в Telegram или после подтверждения в Telegram самого управления) доступны с телефона или другого компьютера — на том же адресе устройства, под `/ui/`, со своей сессией. Вход — как на устройстве: по адресу `/ui/` (QR-код в Настройках, `gate4ai ui --remote` печатает адрес) с паролем и, если включено, подтверждением в личном Telegram-боте; изменения политик, агентов и секретов удалённо недоступны.
- **Один адрес, разделение по путям.** MCP, CLI агентов, Web UI и вебхук Telegram — на `<device-id>.relay.gate4.ai`; протокол relay от этого не зависит (relay не видит путей).
- **Без relay.** Технический пользователь может выставить тот же адрес сам: `gate4ai daemon --public :8443 --public-url https://… --public-cert … --public-key …` или за своим reverse proxy. Цена — открытый порт; за reverse proxy трафик видит прокси.
- **Свидетель журнала.** Хранит хэши подписанных чекпоинтов устройства.
- **Устойчивость.** Автопереподключение устройства. Если устройство офлайн, relay держит входящее соединение до ~30 с, затем сбрасывает; очереди на relay нет (при passthrough невозможна) — агент повторяет запрос позже.
- **Размещение:** hosted relay `relay.gate4.ai` или self-hosted — тот же бинарник `gate4ai-relay` на своём сервере.
- **Включён по умолчанию.** Daemon без адреса устройства и без запрета владельца сам регистрируется на relay (`relay.url` конфигурации, иначе `relay.gate4.ai`); с прямым адресом (`--public`) — нет. Неудача (сеть, лимиты relay или Let's Encrypt) не отключает функцию: регистрация повторяется раз в час, выпуск сертификата — через 5 минут и далее вдвое реже, до раза в час; пока настоящий сертификат не выпущен, туннель поднимается на временном самоподписанном сертификате устройства (адрес `/ui/` открывается с предупреждением браузера, облачные ассистенты ждут настоящего), и удавшийся выпуск заменяет его; страница **Настройки → Доступ из интернета**, `gate4ai relay status` и `gate4ai ui --print` показывают причину, время следующей попытки и временный сертификат. Выключить — кнопкой там же или `relay.disabled: true` (адрес устройства сохраняется, повторное включение не тратит сертификат); тесты и стенды запускают daemon с `--relay-auto=false`.
- **Ограничения.** Все устройства делят домен relay, поэтому на них действует общий лимит Let's Encrypt (50 новых сертификатов на зарегистрированный домен за 7 дней); relay ограничивает регистрации (на адрес и в сутки) и заказы сертификатов (3 на устройство в сутки), но не исключает, что злоумышленник выберет лимит намеренно.

## Коннекторы

### Общее

- Подробно — в [connector-architecture.md](connector-architecture.md); секреты и учётки — в [secret-architecture.md](secret-architecture.md).
- Единая модель прав: возможности (слоты учёток, хранилище, вызовы браузера) и сайты с папками (`sites`, `folders` с режимом доступа) объявляются в манифесте и обеспечиваются средой исполнения; коннектор не видит секреты и не имеет своей сети.
- **Коннекторы магазина — только `runtime: wasm`** (wazero внутри daemon, собственный ABI; пакеты подписаны Ed25519). Браузер и Файлы — `runtime: builtin`: Go-код ядра на тех же функциях хоста, в бинарнике gate4ai; из магазина не ставятся, не удаляются, обновляются вместе с gate4ai.
- **Вызовы между коннекторами:** функция хоста `service_call(target, action, input)`. Поставщик перечисляет действия, доступные другим (`services`), и номер контракта (`contract`); потребитель объявляет поставщика и контракт в `capabilities.services`, сайты — в `sites`, а **каждое своё действие — его подвызовы** (`calls: [browser.open, browser.act]`). Хост пропускает из действия только объявленные у него подвызовы; класс действия не ниже класса любого его подвызова (действие `read` не может вызвать `write`). Подвызовы видны пользователю в описании действия, в запросе подтверждения и на экране согласия, поэтому **разрешение родительского действия — правилом, по умолчанию класса или подтверждением — покрывает его объявленные подвызовы**: повторно не спрашивается. Явное правило `deny` на действие поставщика действует и во вложенном вызове. Квитанция вложенного вызова ссылается на родительскую. Изменение подвызовов в новой версии требует согласия заново. Типизированный клиент генерируется из манифеста поставщика (`gate4ai contract gen`), несовместимое изменение контракта без повышения `contract` отклоняет CI (`gate4ai contract diff`).
- Каждый коннектор публикует **манифест**: действия, схемы аргументов, класс эффекта (`read` / `write` / `external` / `money`), способ проверки результата (`verify()`), формат доказательства; необязательно — человеческие названия (`title`) и переводы названий и описаний (`i18n`, по языкам) для Web UI. Из манифестов генерируются команды `gate4ai`, MCP-инструменты, skill и формы Web UI.
- SDK коннекторов (`sdk-go`, Apache-2.0) — для сторонних коннекторов.

### Файлы

- Встроены в ядро (`runtime: builtin`), из магазина не ставятся. Папки и режим доступа — список `access.folders` («Списки доступа Браузера и Файлов»); действия: чтение, список, отдельная операция `append` (добавление без перезаписи — удобный класс прав для заметок и журналов), запись.
- **Закрыто всегда**, даже внутри разрешённой папки и при режиме `allow`: скрытые файлы и папки ниже корня (`.ssh`, `.aws`, `.config`, `.git`…; корень, который владелец сам указал скрытым, открыт), файлы ключей и паролей (`id_rsa*`, `id_ed25519*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.kdbx`, `*.keychain*`), связки ключей и данные браузеров и gate4.ai в домашнем каталоге. `files.list` таких записей не показывает. Открыть — настройками `allow_hidden` (скрытые) и `allow_paths` (точные пути) в «Расширенных настройках» на странице «Файлы».
- Коннекторы магазина работают с файлами теми же функциями хоста в папках из своего манифеста, и только если папка не закрыта в списке Файлов.

### Браузер

**Подключение**
- Встроен в ядро (`runtime: builtin`): браузерный воркер и действия для агента — чтение без сеанса и сеанс страницы (открыть, посмотреть элементы и запросы страницы, кликнуть, ввести; страница держится до закрытия сеанса), в том числе чтобы исследовать сайт и написать по нему коннектор; сайты и режим — список `access.sites`. Коннекторам магазина он даёт те же действия с открытой страницей через `service_call` (страница живёт до конца вызова вызывающего коннектора) на сайтах из их манифеста, если список Браузера их не закрывает.
- Выделенный профиль настоящего Chrome пользователя (не headless, не встроенный Chromium), подключение по CDP. С Chrome 136 удалённая отладка не работает с профилем по умолчанию, поэтому отдельный профиль обязателен.
- **Экран** (настройка `display`, по умолчанию `auto`): есть графический сеанс (macOS, Windows, Linux с `DISPLAY` / `WAYLAND_DISPLAY`) — Chrome на нём; Linux без графики — на виртуальном экране Xvfb, который daemon поднимает сам (без TCP, доступ по cookie в каталоге данных gate4ai); без Xvfb — **запасной режим** `--headless=new`: UA без «HeadlessChrome» и полные client hints ставит мультиплексор на каждую вкладку, владелец видит предупреждение (сайты с антибот-защитой замечают headless чаще). Нет Chrome или экран не поднять — агент получает `browser_unavailable`, владелец чинит `gate4ai browser setup`.
- **Сеанс агента — своё окно** (Chrome рисует его, даже когда впереди другое), ответ `browser.open` несёт `view_url` — ссылку на просмотр сеанса в Web UI (публичный адрес устройства или Web UI этого компьютера). Ссылка доступа не даёт: страница требует вход владельца, поэтому агент может отдать её человеку в свой чат. В разделе «Браузер» Web UI (и `gate4ai browser sessions`) — сеансы агентов: кадры вкладки вживую (CDP screencast) и «Взять управление»: ввод человека (мышь, клавиши, текст) идёт в страницу, действия агента в этом сеансе отвечают `session_held_by_user`, пока человек не вернёт сеанс. `browser.handoff` — то же по просьбе агента: уведомление несёт ссылку, управление включено сразу, «Готово» / «Не буду» завершают ожидание.
- Домашний IP, настоящее железо, живые сессии — основные признаки автоматизации отсутствуют. Остаются следы CDP (тот же протокол использует Claude in Chrome) и поведение.
- Логин, пароль и PIN вводятся по учётке (`browser.login`, `browser.fill_secret`: только в поле нужного типа на origin привязки, вход атомарно, без LLM); одноразовый код (SMS и т.п.) человек сообщает через канал подтверждений, и он сразу идёт в поле. Капчи вводит человек (в просмотре сеанса), войти сам он тоже может. С антибот-защитой не воюем: если сайт блокирует автоматизацию, сценарий деградирует до «данные подготовлены — откройте и нажмите сами».

**Движок: прямой Chrome DevTools Protocol**

Воркер говорит с Chrome напрямую по CDP (websocket к вкладке и к браузеру; библиотека — `coder/websocket`, та же, что у relay и Web UI): переходы, текст и элементы страницы через `Runtime.evaluate` со своим JS, ввод через `Input.*`, снимки через `Page.captureScreenshot`, диалоги через `Page.javascriptDialogOpening`, загрузки и перехват ответов через `Browser.setDownloadBehavior` и `Network.*`, просмотр сеанса через `Page.startScreencast`. В Chrome ничего не ставится: ни расширений, ни флагов отладки расширений. LLM у движка нет: данные со страницы читает и понимает сам агент (`read`, `observe`).

Точка перехвата политикой: `observe` отдаёт элементы с селекторами, `act` исполняет одно действие по селектору — Policy Engine видит каждое действие с его аргументами.

Отвергнутый вариант — Stagehand Go SDK v4 (Browserbase): `act`, `observe`, `extract` на естественном языке с LLM, логика в расширении Stagehand Runtime, которое SDK грузит в Chrome (`--enable-unsafe-extension-debugging`, `debugger` и content script на всех страницах). Для gate4ai это второй LLM с ключом у пользователя, действия без точки перехвата и лишний признак автоматизации; после отказа от `extract` SDK ничего не добавлял к CDP, а фоновые вкладки, перехват ответов и тело не-HTML документов умел только прямой CDP.

**Executor** — единая точка исполнения кликов, ввода, навигации.

**Коннекторы к сайтам** — высокоуровневые действия поверх браузерного коннектора (через `service_call`); заготовку даёт `gate4ai connectors new <имя> --site <домен>`, как писать — [connector-authoring.md](connector-authoring.md). Для сайтов с деньгами — модель «агент готовит, человек подтверждает» (класс `money`, по умолчанию `ask`).

## Изоляция локальных агентов

Claude Code, Codex, OpenClaw, Hermes и другие агенты запускаются **на том же компьютере, но в песочнице**. Внутри у агента полная свобода — shell, установка пакетов, работа без подтверждения каждой команды, — а всё за её пределами (файлы хоста, браузер, секреты, сеть) доступно **только через gate4.ai**. Это снимает дилемму «подтверждать каждую команду» или «режим YOLO с доступом ко всему компьютеру».

### Уровни

| Уровень | Запуск | Механизм |
|---|---|---|
| 1 — по умолчанию | `gate4ai run <агент>` | процессная песочница [Anthropic sandbox-runtime](https://github.com/anthropics/sandbox-runtime) (`srt`, Apache-2.0; Seatbelt / bubblewrap, Windows — alpha); наш Egress Proxy — внешний decider для её сети; Docker не нужен |
| 2 — опция | `gate4ai run --container <агент>` | Docker / Podman |
| 3 — опция | `gate4ai run --microvm <агент>` | microVM через [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/): сеть через наш Egress Proxy, доступ к `gate4ai` |
| Облачные агенты | — | песочницы на нашей стороне нет: онбординг-чеклист (отключить родные коннекторы платформы — Gmail, Drive и т.п. — и работать через gate4.ai) |

- **Профиль песочницы** генерируется из профиля агента: запись только в рабочую папку; закрыто чтение `~/.ssh`, keychain, профилей браузеров, данных почтовых клиентов; из unix-сокетов доступен только `gate4ai`; сеть — только через Egress Proxy.
- **`gate4ai doctor`** проверяет обходные пути: агент запущен не через `gate4ai run`, доступен профиль Chrome / Claude in Chrome, токены в окружении, открыт Docker-сокет, — и показывает, как их закрыть.

### Схема (уровень 2, контейнер)

```
┌─ Хост пользователя ─────────────────────────────────────────────┐
│                                                                 │
│  ┌─ Контейнер агента ─────────────────────────┐                 │
│  │ Claude Code / Codex / OpenClaw / Hermes    │                 │
│  │ /workspace — только папка проекта (rw)     │                 │
│  │ нет: ~/.ssh, keychain, браузера, Docker    │                 │
│  └───────┬──────────────────────┬─────────────┘                 │
│          │ gate4ai: MCP или CLI │ HTTP(S)_PROXY                 │
│          ▼                      ▼                               │
│  ┌─ gate4ai daemon ──────────────────────────────────────────┐  │
│  │ MCP Front → Action Pipeline → Файлы хоста, Браузер,       │  │
│  │                               коннекторы к сайтам         │  │
│  │ Egress Proxy → allowlist, подстановка ключей → интернет   │  │
│  │ Agent Launcher: запуск/остановка, токены, профили         │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### Как устроено

- **Запуск:** `gate4ai run claude-code --workspace ~/projects/policy` (профиль — профиль агента в политике) (Web UI или CLI). Шаблоны для популярных агентов: бинарник `gate4ai`, настроенный `gate4ai mcp` и skill. Каждый запуск — отдельный агент в журнале со своим токеном; остановка и отзыв — одной кнопкой.
- **Файлы:** доступна только рабочая папка; остальное на хосте — через коннектор «Файлы» по правилам.
- **Канал к хосту:** агент работает с `gate4ai` (MCP или CLI), `gate4ai` пересылает вызовы в daemon. В контейнере (уровень 2) — unix-сокет агента, примонтированный в контейнер (`/run/user/<uid>/gate4ai/agent-<id>.sock` → `/run/gate4ai.sock`); в microVM (уровень 3) — HTTPS-прокси хоста через `host.docker.internal` с токеном запуска.
- **Сеть (Egress Proxy):** прямого выхода в интернет нет. Контейнер запускается без сети (`--network none`); внутри `gate4ai` слушает 127.0.0.1:3128 и пересылает соединения через примонтированный unix-сокет в Egress Proxy хоста. Поэтому уровень 2 работает только на Linux-хосте (на macOS / Windows — уровни 1 и 3). Прокси подставляет секреты только по точному origin привязки (схема, хост, порт), только по HTTPS, после проверки, что адрес назначения не loopback и не частная сеть.
  - Allowlist доменов: API модели, при необходимости реестры пакетов и `github.com`; остальное — `deny` или `ask`.
  - Подстановка секретов на выходе: внутри — одноразовая на запуск заглушка вместо API-ключа модели или GitHub-токена; при запросе к origin привязки прокси ставит заголовок с реальным ключом целиком (заглушка в другом месте запроса — отказ). Для входа по подписке (OAuth Claude Code / Codex) — тот же механизм для OAuth-токена и его обновления.
  - Журнал соединений: куда и сколько данных отправил агент.
- **Чего у агента нет:** Docker-сокета хоста, `~/.ssh`, keychain, браузера с живыми сессиями, файлов вне рабочей папки — обойти gate4.ai «соседним путём» нельзя.

### Ограничения

- На macOS / Windows Docker Desktop — это VM: медленнее файловые операции в смонтированной папке; лицензия Docker Desktop для компаний — альтернатива Podman.
- sandbox-runtime для Windows в статусе alpha; на Windows уровень 2 (контейнер) и 3 (microVM) — полноценные альтернативы.
- Агентам, которым нужен браузер внутри песочницы, нужен отдельный образ; браузер хоста — только через браузерный коннектор.
- Правила Egress Proxy — по домену (`sandbox.allow_domains`, `sandbox.ask_domains` профиля), не по содержимому запросов.

## Рынок

| Категория | Примеры | Чем отличаемся |
|---|---|---|
| Мосты от платформ | Claude in Chrome, OpenClaw nodes / companion app | работают с одним агентом; правила грубые |
| Локальные MCP для облачных клиентов | LMCP, email-agent-mcp | дают доступ, не контроль |
| Туннели | Sealgate stdio tunnels, AWS AgentCore bridge, ngrok / Pinggy | инфраструктура без политик |
| Корпоративные MCP-шлюзы | Bifrost, MCPX (Lunar), Docker MCP Gateway, Peta | enterprise, RBAC/SSO, правила на уровне инструментов |
| Credential-прокси | Vultrino, Onyx «valet key», agentgateway, Infisical agent-proxy | секреты закрыты, но не потребительский продукт, нет доменных правил |
| Платёжные протоколы | Google AP2, Visa для агентов | только платежи, только через партнёрские сети |
| Песочницы агентов | Anthropic sandbox-runtime, Docker Sandboxes, dev containers | изолируют агента, но не задают правил на действия с личными данными и сервисами; используем как основу изоляции |

**Позиционирование:** единый локальный шлюз для всех агентов пользователя со смысловыми правилами (адресаты, суммы, происхождение данных), подтверждениями в мессенджере и доказательствами выполнения. «Anthropic и Docker изолируют агента; gate4.ai решает, что агент может делать с вашей жизнью за пределами песочницы».

## Риски

- **Платформы сделают своё.** Защита — независимость от агента (одни правила для всех) и глубина правил. Платформам невыгодно давать пользователю контроль над конкурентами.
- **Компьютер спит.** Агенты получают «устройство офлайн»; для бытовых сценариев рекомендуется постоянно включённое устройство (мини-ПК, Mac mini).
- **Prompt injection внутри разрешённого.** Правила ограничивают ущерб, но не исключают. Действия с деньгами — всегда с подтверждением.
- **Обход шлюза.** Если у агента есть параллельный доступ (Chrome с сессиями, shell с curl), шлюз бесполезен. Закрывается изоляцией и `gate4ai doctor`; для облачных агентов — только онбордингом (родные коннекторы платформы технически не закрыть).
- **Шлюз — единая точка отказа и атаки.** Минимальная поверхность ядра, недоверенный код — в WASM-песочнице.
- **Windows-песочница в alpha** (sandbox-runtime). Запасной путь — контейнер / microVM.
- **Хрупкость браузерных коннекторов.** Сайты меняются — коннекторы к ним требуют постоянной поддержки.
- **Регулирование.** Персональные данные (152-ФЗ в РФ), правила сервисов (Госуслуги, банки) об автоматизации — модель «агент готовит, человек подтверждает».
