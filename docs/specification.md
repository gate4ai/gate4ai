## Суть

Приложение для компьютера пользователя, через которое **любой** AI-агент — Claude.ai, ChatGPT, облачный OpenClaw, Hermes Agent, Claude Code — получает доступ к браузеру, почте, файлам и сервисам этого компьютера. Агент не получает прямого доступа и не видит пароли: каждый его запрос проходит через **policy engine**, который разрешает, запрещает или запрашивает подтверждение у человека, подставляет секреты сам и сохраняет доказательство выполненного действия.

Транспорт «облачный агент → мой компьютер» уже существует во многих вариантах. Ценность продукта — **слой политик поверх него, единый для всех агентов**.

## Проблема

1. **Агентам дают слишком много.** Персональные ассистенты (OpenClaw, Hermes и др.) получают shell, залогиненный браузер и почту целиком. Итог 2026 года: CVE, вредоносные skills в маркетплейсах, десятки тысяч открытых в интернет инстансов, запреты на рабочих ноутбуках.
2. **Prompt injection превращается в действия.** Письмо или веб-страница с инструкцией может заставить агента переслать данные или отправить деньги.
3. **Агенты отчитываются «сделано», не сделав.** Самооценка агентов систематически завышена; проверки по факту нет.
4. **Существующие защиты не для людей.** MCP-шлюзы и credential-прокси — корпоративные: RBAC, SSO, SOC. Правила на уровне «какой инструмент», а не «кому и сколько».
5. **У каждой платформы свой мост и свои права.** Claude in Chrome — только для Claude, OpenClaw nodes — только для OpenClaw. Единых правил «для всех моих агентов» нет.

## Для кого

- **Основная аудитория (глобально):** пользователи персональных агентов — OpenClaw, Hermes, Claude Code / Claude.ai, ChatGPT, — которые уже доверяют агенту почту, файлы и рутину и хотят ограничить риск.
- **Вторая волна:** семьи и малые команды — общие правила для нескольких людей и агентов.
- **Локальное применение (РФ):** бытовые сценарии (ЖКХ, штрафы, документы), где у сервисов нет API и единственный путь — браузер пользователя.

Основной пользователь — не программист. Политики настраиваются в Web UI; файл конфигурации доступен, но нужен только техническим пользователям.

## Как это работает

```
 Claude.ai / ChatGPT / облачный OpenClaw / Hermes / Claude Code
                         │  remote MCP (OAuth) или CLI по HTTPS — отдельный токен на агента
                         ▼
              Relay (исходящее соединение, без открытых портов)
              или свой HTTPS-адрес устройства
                         │
┌─────────────── Приложение на компе (трей) ───────────────────┐
│  Policy engine: агент × действие × данные →                  │
│                 allow / deny / ask  + лимиты, whitelist      │
│  Подтверждения: уведомление на компе + Telegram / телефон    │
│  Хранилище секретов: агент видит алиасы, не пароли           │
│  Журнал + доказательства (скриншот, ответ сервера, выписка)  │
├──────────────────────────────────────────────────────────────┤
│  Коннекторы: Браузер (отдельный профиль, домены по списку)   │
│              Почта (IMAP/SMTP, Microsoft Graph)              │
│              Файлы (только разрешённые папки)                │
│              Сервисы: банк, ЖКХ, Госуслуги — высокоуровневые │
│              действия поверх браузера                        │
└──────────────────────────────────────────────────────────────┘
```

**Пример потока**

1. Агент в Claude.ai вызывает `send_email(to="landlord@example.com", subject=..., body=...)`.
2. Policy engine: адресат не в списке доверенных → **ask**.
3. В Telegram: «Claude.ai хочет отправить письмо landlord@example.com `#a3f9c21e` [Отправить] [Отклонить] [Показать текст]».
4. Пользователь нажимает «Отправить» → коннектор отправляет через SMTP, подставив учётные данные из хранилища.
5. Шлюз проверяет, что письмо появилось в «Отправленных», и возвращает агенту результат с идентификатором письма. Квитанция — в журнал.

При отказе агент получает честную, понятную ошибку: `denied_by_policy: recipient not in allowlist; user notified`. Маскировка отказа под сбой провоцирует агента на повторы и обходные пути.

## Принципы дизайна

1. **Высокоуровневые инструменты вместо «сырого» доступа.** `pay_bill(provider, amount)`, `send_email(...)`, `read_statement(period)` — к ним применимы правила. Сырой браузер — только домены из списка; действия на странице (клик, ввод) — класса `write`, под правилами и подтверждением, как любое действие.
2. **Решает код, а не LLM.** Политики детерминированы и не обходятся промптом. LLM допустима лишь для мягких сигналов («похоже на фишинг?»), которые могут только ужесточить решение.
3. **Недоверенные данные помечаются.** Всё, что пришло из писем и веб-страниц, имеет метку происхождения. Пример правила: нельзя отправить письмо или деньги адресату, который появился только из входящего контента.
4. **Права на каждого агента отдельно.** Свой токен, свой профиль прав, отзыв в один клик.
5. **Доказательство вместо «сделано».** Каждое действие с эффектом подтверждается фактом: ответ сервера, письмо в «Отправленных», строка в выписке, скриншот.
6. **Секреты не покидают устройство.** Агент оперирует алиасами (`@amazon`, `@gosuslugi`); реальные данные подставляет ядро или auth-модуль и только по адресу привязки учётки; коннектор значений не видит. Relay видит только шифротекст.
7. **Открытый исходный код.** Никто не поставит закрытый бинарник с доступом к почте и банку. Ядро, relay, коннекторы и auth-модули — AGPL-3.0 (доработки раскрываются, в том числе при работе как сервис). SDK — Apache-2.0, registry (данные индекса) — CC0. Подписанные и воспроизводимые сборки.
8. **Агент-агностичность.** MCP для любых клиентов, CLI для агентов с shell и скриптов, skill с инструкцией для агентов. Политики применяются только в ядре — способ вызова на решение не влияет.

## Интерфейсы для агентов: MCP, CLI, skill

Один и тот же набор действий доступен через несколько фронтов. Политики, подтверждения и журнал — только в ядре, поэтому результат не зависит от способа вызова, а обойти правила через другой фронт нельзя.

```
              ┌─ MCP (stdio / HTTPS)             ─┐
 агенты ─────►│                                   │
 скрипты ────►├─ CLI `gate4ai` (сокет / HTTPS)    ├──► Action Pipeline ──► коннекторы
 люди ───────►└─ Web UI (localhost / HTTPS /ui/)  ┘    (одни политики, один журнал)
```

### Зачем и MCP, и CLI

| | MCP | CLI `gate4ai` + skill |
|---|---|---|
| Облачные агенты без shell (Claude.ai, ChatGPT) | **единственный вариант** | не работает |
| Агенты с shell (Claude Code, Codex, OpenClaw, Hermes, Aider) | работает | работает; агенты хорошо владеют CLI |
| Агенты с shell на другом компьютере | remote MCP | работает: `GATE4AI_URL=https://<адрес устройства>`, те же команды |
| Расход контекста | схемы всех инструментов постоянно в контексте | skill подгружается по необходимости, детали — через `gate4ai <команда> --help` |
| Скрипты и cron | неудобно | естественно: `gate4ai mail send …` из bash / Python |
| Скомпилированные сценарии (запись → скрипт) | скрипт не может вызвать MCP | скрипт вызывает `gate4ai`, каждый шаг проходит политики |
| Технические пользователи | нужен MCP-клиент | `gate4ai log`, `gate4ai agents revoke`, `gate4ai policy test` |
| Агенты без поддержки MCP | не работают | работают при наличии shell |

### Бинарник `gate4ai`

- **Один бинарник, два режима:** `gate4ai mcp` — MCP-сервер (stdio; он же используется внутри песочниц и контейнеров), `gate4ai <коннектор> <действие> …` — CLI. Оба — тонкие клиенты к daemon: на том же компьютере — через сокет, с другого — по HTTPS на публичный адрес устройства (`GATE4AI_URL`).
- **Команды, MCP-инструменты, skill и формы Web UI генерируются из манифестов коннекторов** — новое действие появляется везде сразу.
- **Машиночитаемый вывод:** JSON по умолчанию; коды выхода для `denied_by_policy`, `pending_approval`, `verification_failed`. Исключение — человек в терминале: если stdout — терминал, списки и состояние для владельца (агенты, подтверждения, коннекторы, хранилище, версии политики, состояние daemon, relay и автозапуска) печатаются таблицей, а ошибки — текстом с подсказкой, что делать; `--json` или `GATE4AI_OUTPUT=json` возвращают JSON. Агенты и скрипты (stdout — pipe или файл) всегда получают JSON; коды выхода от формата не зависят.
- **Подтверждения:** вызов ждёт решения (`--wait 10m`) или сразу возвращает `pending` с ID; статус — `gate4ai status <id>`.
- **Обнаружение:** `gate4ai tools --json` — только действия, разрешённые профилю этого агента (тот же отфильтрованный каталог, что в MCP).

### Skill для агентов

Один `SKILL.md` в общем формате навыков Claude Code / Hermes / OpenClaw, генерируется из манифестов:
- всегда использовать `gate4ai` для действий вне своей среды и не искать обходных путей;
- основные команды с примерами;
- реакция на отказ: не повторять, не обходить, сообщить пользователю причину;
- ожидание подтверждения, повтор при «устройство офлайн», проверка результата (`verified: true / false`).

### Идентичность и права

- Агент вызывает `gate4ai` / MCP со своим токеном. Токен лишь идентифицирует агента и не даёт ничего сверх его профиля — даже прочитав его, агент не расширит права.
- Человек на хосте использует `gate4ai` с правами владельца через локальный сокет с проверкой собеседника; агентский токен этих прав не получает.
- Аутентифицируется агент, а не человек за ним; человек — владелец устройства.

| Кто | Канал | Аутентификация |
|---|---|---|
| Облачный агент | remote MCP | OAuth 2.1: динамическая регистрация (RFC 7591), code + PKCE S256, refresh с ротацией, отзыв (RFC 7009), метаданные (RFC 8414, RFC 9728); подключение подтверждается одноразовым кодом владельца, код привязан к агенту |
| Удалённый агент с shell | CLI по HTTPS | токен агента (`GATE4AI_TOKEN`) |
| Локальный агент | stdio, сокет агентов, песочница | токен агента; сокет и токен на каждый запуск |
| Владелец на устройстве | сокет владельца, Web UI на localhost | проверка собеседника; Web UI — способы входа на выбор: одноразовая ссылка, пароль, подтверждение в Telegram (см. «Защита входа в Web UI») → сессия |
| Владелец удалённо | `/ui/` на публичном адресе | способы входа, как на устройстве: одноразовая ссылка, пароль, Telegram → своя сессия (только подтверждения и журнал) |
| Telegram | вебхук `/telegram` | секрет, выданный при `setWebhook`; команды — только от Telegram ID владельца |

## Политики

### Модель

- **Профили** (слой ролей): агенту назначается профиль — `assistant`, `drafts-only` и т.п. Профиль перечисляет доступные коннекторы; коннекторы вне профиля агент не видит вовсе.
- **Правила** (ABAC): `action` + условие `when` на CEL + `effect` (`allow` / `deny` / `ask`) + `obligations` (`verify_statement`, маскирование полей, лимит) + `reason`.
- **Вход условий:** аргументы действия, метки происхождения (`provenance`), счётчики (`counters.spent_today`), списки (`lists.*`), время. Собственные функции CEL — `glob()`, `domain_matches()` и т.п.
- **Порядок решения:** `deny` важнее `ask`, `ask` важнее `allow`. Если ни одно правило не сработало — значение по умолчанию класса эффекта действия: `read` → `allow`, `write` / `external` / `money` → `ask`.
- **Объяснение решения** — `id` и `reason` сработавшего правила; показывается агенту при отказе и человеку в запросе подтверждения.
- **Одно подтверждение на действие.** Всё, что ядро делает внутри действия от имени того же агента — использование учёток экземпляра, вызов коннектора-источника (код из письма), — покрыто решением по самому действию: «перевести через Т-Банк» спрашивается один раз, без второго вопроса «отдать ли пароль от Т-Банка». Запрос подтверждения перечисляет учётки, которые будут использованы; вложенные события пишутся в журнал со ссылкой на квитанцию действия.

### Как редактируются

- **Одна модель конфигурации**, два представления: Web UI для обычных людей и файл YAML для технических пользователей. Web UI собирает условия из блоков («получатель из списка…», «сумма не больше…») и генерирует CEL; сырой CEL — для технических пользователей.
- Готовые шаблоны («безопасная почта», «платежи только с подтверждением»), **симулятор** («что будет, если агент попробует…») и **прогон журнала** за последние 30 дней через изменённую политику: что раньше требовало подтверждения, а теперь прошло бы само.
- Каждое изменение — версия с откатом; изменения требуют локальной аутентификации пользователя, кроме действия агента `gate4ai.change_policy`, которое разрешает политика или подтверждает владелец в любом канале. Кнопка «разрешать так всегда» в запросе подтверждения не меняет политику молча, а создаёт предложение правила.

### Пример

```yaml
agents:
  claude-ai:      { profile: assistant }
  openclaw-cloud: { profile: drafts-only }
```

## Архитектура

### Зоны доверия

```

 │ Агенты: Claude.ai, ChatGPT, облачный OpenClaw, Hermes, Claude Code   │
 │ Контент: входящие письма, веб-страницы, файлы от третьих лиц         │

                                     │ MCP / CLI (HTTPS, stdio, сокет)
 ┌─ ТРАНСПОРТ (не должен видеть данные) ────────────────────────────────┐
 │ Relay: публичный HTTPS-адрес устройства, исходящий туннель с компа   │
 │ (или свой HTTPS-адрес: `--public`)                                   │
 └───────────────────────────────────┬──────────────────────────────────┘
                                     │
 ┌─ ДОВЕРЕННОЕ ЯДРО (устройство пользователя) ──────────────────────────┐
 │ gate4ai daemon: политики, подтверждения, секреты, журнал             │
 └───────────────────────────────────┬──────────────────────────────────┘
                                     │ только через коннекторы
 ┌─ ВНЕШНИЕ СЕРВИСЫ ────────────────────────────────────────────────────┐
 │ Почтовый сервер, сайты банка / ЖКХ / Госуслуг, файловая система      │
 └──────────────────────────────────────────────────────────────────────┘
```

Главное правило: **агент не имеет пути к внешним сервисам, кроме как через ядро**, а ядро не принимает решений на основе текста от агента — только на основе структурированных параметров действия и правил.

### Компоненты

```

 агент MCP/CLI► │ MCP Front ─► Action Pipeline ──────────────────────────────► ответ   │
                │  (OAuth,      │                                                      │
                │   каталог     ├─ 1. Нормализация (схема действия, аргументы)         │
                │   инструментов├─ 2. Обогащение (агент, метки происхождения, счётчики │
                │   по профилю) ├─ 3. Policy Engine (PDP) → allow/deny/ask + условия   │
                │               ├─ 4. Approval Service (desktop / Telegram / web)      │
                │               ├─ 5. Подстановка секретов (Vault)                     │
                │               ├─ 6. Executor → Коннектор (единая точка исполнения)   │
                │               ├─ 7. Verification (проверка результата по факту)      │
                │               └─ 8. Audit + Evidence, разметка ответа агенту         │
                │                                                                      │
                │ Web UI ─ Config Store ─ State Store (SQLite) ─ Notification Service  │
                │ Egress Proxy (сетевой выход изолированных агентов) ─ Agent Launcher  │
                └──────────┬───────────────────────┬────────────────────────┬──────────┘
                           │                       │                        │
                 Коннектор «Почта»       Коннектор «Браузер»          «Файлы»
                 (WASM-модуль)           (нативный пакет: процесс     (встроены в ядро)
                                          + Chrome-профиль)
```

**MCP Front**
- Транспорты: stdio (локальные агенты), канал из песочницы / контейнера (см. «Изоляция локальных агентов»), Streamable HTTP через relay (облачные агенты).
- Встроенный OAuth 2.1 authorization server: каждый агент регистрируется отдельно и получает свой токен; отзыв — в один клик в Web UI.
- Каталог инструментов фильтруется по профилю агента. Политику агент меняет только действием `gate4ai.change_policy` встроенного коннектора `gate4ai` — под той же политикой, что любые действия (см. «Безопасность самого шлюза»).

**Публичный адрес устройства** — один обработчик, который обслуживают relay и прямой HTTPS (`gate4ai daemon --public`: свой сертификат или loopback за reverse proxy этого компьютера):

| Путь | Что | Учётные данные |
|---|---|---|
| `/` (POST, DELETE), `/mcp`, `/.well-known/…`, `/authorize`, `/token`, `/register`, `/revoke` | remote MCP и OAuth 2.1 | токен агента |
| `/v1/whoami`, `/v1/tools`, `/v1/call`, `/v1/status/{id}` | CLI удалённых агентов | токен агента |
| `/ui/` | удалённый Web UI | сессия: одноразовая ссылка, пароль и/или Telegram — по защите входа |
| `/telegram` | вебхук бота подтверждений | секрет вебхука |

Учётные данные одного пути не действуют на другом (это проверяет тест); API владельца на публичном адресе нет.

**Action Pipeline** — единственный путь любого действия. Все шаги выполняются в одном месте и в одном порядке, поэтому сюда же подключаются журнал, лимиты, проверка результата и будущее замедление (pacing).

**Policy Engine (PDP)** — детерминированный, без LLM; модель и порядок решения — в разделе «Политики». Консультативные сигналы от LLM («письмо похоже на фишинг») могут только ужесточить решение (allow → ask).

**Approval Service**
- Каналы: уведомление на компьютере, личный Telegram-бот пользователя, Web UI, браузерный push (Web Push) для Web UI — локального и удалённого `/ui/` на адресе устройства; позже — мобильное приложение с push.
- **Браузерный push:** краткое уведомление (агент, действие, короткий хэш) со ссылкой на страницу подтверждения; решение принимается только на странице Web UI с сессией. Уведомление идёт через push-сервис браузера (Google, Mozilla, Apple), а не через серверы gate4.ai, и зашифровано для подписанного браузера (RFC 8291); сервер подписан ключом VAPID устройства (RFC 8292).
- **Telegram:** пользователь создаёт своего бота через BotFather и вставляет токен в Web UI (токен — в Vault); daemon опрашивает Telegram API исходящими запросами (или, по выбору, получает вебхук на `/telegram` публичного адреса), бот принимает команды только от Telegram ID владельца. Общего бота gate4ai нет — содержимое подтверждений не проходит через наши серверы.
- Запрос показывает **что именно** будет сделано (получатель, сумма, текст, предпросмотр) и **почему** нужно подтверждение; в мессенджере — кратко, с хэшем квитанции для подробностей.
- Таймаут → `deny` по умолчанию.

**Vault (секреты)** — подробно в [secret-architecture.md](secret-architecture.md)
- Три уровня: **ядро** хранит учётки и проверяет привязки, протоколов аутентификации не знает; **auth-модули** (WASM) знают протокол (IMAP, OAuth, SSH, подписи банков) и видят значение, но вывести его могут только к адресу привязки; **коннекторы** называют слот учётки и значений не видят.
- Учётка — алиас (`@amazon`, `@mail.work`) с полями (секретными и публичными) и версиями; привязка задаёт, куда (точный origin: схема, хост, порт; без масок) и как (шаблон, форма браузера, auth-модуль) её можно использовать. Шаблон подставляет секрет только целиком в заголовок аутентификации запроса к origin привязки (не в тело и не в адрес); ответы маскируются, включая производные формы значения (base64, URL-, JSON- и HTML-экранирование, hex), а сжатие ответа коннектор запросить не может.
- Значения — в keychain ОС (запись на алиас и индекс алиасов); целевое состояние — зашифрованный файл `vault.age` (ключ в keychain). Без keychain (`--keystore file`) значения лежат в `keys.json` (права 0600) **открытым текстом** — об этом предупреждают daemon и инструкция; daemon, однажды работавший с keychain, не переключается на файл молча. Внешние менеджеры (1Password, Bitwarden) — позже.
- Новые секреты (пароль при регистрации, ключ, показанный один раз, токен из ответа API) сохраняет ядро с подтверждением человека, не показывая агенту и коннектору.
- Ответы агенту проходят фильтр: известные секреты и чувствительные поля (номера карт, паспорт) маскируются.

**Provenance (метки происхождения)**
- Всё, что возвращается агенту из недоверенных источников (входящие письма, веб-страницы), получает метку и идентификатор источника.
- Когда значения из помеченных данных появляются в аргументах действия (адрес получателя, реквизиты, сумма), метка переносится на действие и доступна правилам (`provenance.to`).
- Сопоставление эвристическое (точное совпадение нормализованных значений) — ограничивает ущерб, но не гарантирует полноту.

**Verification** — проверка результата по независимому каналу: письмо в «Отправленных», операция в выписке, статус на сайте. Действие без успешной проверки помечается «не подтверждено», а не «выполнено».

**Config Store / State Store** — модель конфигурации с версиями; SQLite для счётчиков лимитов, очереди подтверждений, индекса журнала.

**Agent Launcher и Egress Proxy** — запуск локальных агентов в песочнице и единственный сетевой выход для них (см. «Изоляция локальных агентов»).

### Процессы и стек

| Процесс | Назначение | Технология |
|---|---|---|
| `gate4ai daemon` | ядро: MCP Front, pipeline, PDP, vault, журнал, Web UI (localhost; удалённо — `/ui/`), публичный адрес | Go; тот же бинарник, что и CLI |
| `gate4ai` | CLI для агентов, скриптов и людей + режим `gate4ai mcp`; тонкий клиент к daemon | Go, статический бинарник |
| `gate4ai-tray` — трей | статус, уведомления, быстрые подтверждения, открытие Web UI; отдельный бинарник (на macOS нужен cgo) | Go + fyne.io/systray |
| Коннекторы | действия с эффектом; только функции хоста | WASM-модули в daemon (wazero, собственный ABI) |
| Нативные пакеты | коннекторы, которым нужны ресурсы ОС (браузер); только от проверенного издателя | дочерние процессы daemon, бинарник под платформу из магазина |
| Auth-модули | протоколы аутентификации (IMAP, OAuth, SSH, подписи); видят значения учёток, выход — только к адресу привязки | WASM-модули в daemon (wazero, собственный ABI) |
| Браузерный воркер | CDP, движок, executor, сценарии — нативный пакет `browser` | Go + Stagehand Go SDK v4 |
| Chrome (выделенный профиль) | живые сессии пользователя | системный Chrome |
| Telegram-бот | канал подтверждений | личный бот пользователя; часть daemon (Go) |
| Песочницы / контейнеры агентов | изолированные Claude Code / Codex / OpenClaw / Hermes | sandbox-runtime; Docker / Podman |
| Relay | публичный адрес, удалённый доступ, сопряжение устройств, свидетель чекпоинтов | Go |

**Связь между процессами**
- **daemon → коннекторы:** WASM-модули внутри daemon, взаимодействие только через функции хоста (см. connector-architecture.md).
- **daemon → нативные пакеты (браузерный воркер):** дочерний процесс, JSON-RPC через stdin/stdout — одинаково на всех ОС, посторонний процесс подключиться не может, падение сразу видно; daemon перезапускает упавший процесс.
- **трей и CLI → daemon:** unix-сокет (macOS / Linux) или named pipe (Windows) за общим интерфейсом; доступ только текущему пользователю (права `0600` / security descriptor с SID пользователя), проверка собеседника (`getpeereid` / `SO_PEERCRED` / `GetNamedPipeClientProcessId`), на Windows — защита от перехвата имени pipe (`FILE_FLAG_FIRST_PIPE_INSTANCE`).
- **Web UI → daemon:** HTTP на localhost с сессией; удалённо — `/ui/` на публичном адресе устройства (relay или `--public`).
- **удалённые агенты → daemon:** HTTPS на публичный адрес устройства (remote MCP, CLI с `GATE4AI_URL`).
- **песочница / контейнер агента → daemon:** см. «Изоляция локальных агентов».
- TCP на localhost без аутентификации не используется нигде.

### Режимы развёртывания

1. **Ноутбук пользователя** — всё на одной машине; пока компьютер спит, агенты получают «устройство офлайн» и повторяют позже.
2. **Постоянно включённое устройство** (мини-ПК, Mac mini) — daemon без трея, Web UI по локальной сети или удалённо через relay; основной режим для бытовых сценариев.
3. **Изолированные агенты на той же машине** — локальные агенты в песочнице, доступ к хосту только через gate4.ai.
4. **Семейный хаб** (позже) — одно устройство, несколько пользователей и агентов с разными профилями.

### Безопасность самого шлюза

- Агент не может в обход владельца изменить политику, расширить права или прочитать секреты: единственный инструмент изменения — `gate4ai.change_policy` (ниже), он подчиняется политике и подтверждению; файлы конфигурации и хранилища защищены.
- **Самонастройка через агента:** у daemon есть встроенный коннектор `gate4ai`: вместо внешнего сервиса он меняет политику самого gate4ai. Его действие `gate4ai.change_policy` (класс `write`) меняет любую часть политики — правила любого профиля, списки, настройки и установку коннекторов — и подчиняется обычной политике: без правил оно требует подтверждения владельца (в запросе — сначала что именно изменится, в том числе замена существующих правил, и возможности, runtime, классы действий и лимиты устанавливаемых коннекторов; затем, отдельно и с пометкой, — слова агента; одобрить можно только в Web UI, где видны все правки, отклонить — в любом канале), правилом его можно разрешить или запретить. Каждое изменение — версия политики с откатом. Устанавливается ровно то, что показано в запросе (версия, дайджест пакета или исходников своей сборки, возможности); если к исполнению это изменилось — отказ. Своя сборка агента — только `runtime: wasm`. Значения секретов так не задаются: правки с алиасами Vault и секретными полями ядро отклоняет до запроса подтверждения. Исключение — новая учётка входа (`add_credential`): только новая, только с новыми алиасами в своём пространстве имён (`@<учётка>.<поле>`), которых ещё нет в Vault и политике, и всегда с подтверждением человека; значения задаёт владелец. Установка своей сборки и правки настроек, от которых зависит, куда коннектор ходит в сеть и куда отправляет секреты (`network`, `bind` манифеста), всегда подтверждаются человеком — даже при разрешающем правиле — с явным предупреждением.
- Web UI слушает только localhost; удалённо — `/ui/` на публичном адресе со входом владельца по одноразовой ссылке с устройства, только подтверждения и журнал (второй фактор — после старта, см. «Relay»).
- Ссылку из `gate4ai ui` может получить и агент, запущенный от того же пользователя ОС. Поэтому вход в Web UI — локальный и удалённый — защищается сочетанием способов на выбор владельца: одноразовая ссылка, пароль (только хэш argon2id, с задержкой после неверных попыток) и подтверждение входа в личном Telegram-боте. Настройки защиты — не в конфигурации (агент не меняет их через `gate4ai.change_policy`) и меняются только из сессии, открытой с текущей защитой. Полностью от агента того же пользователя ОС это не изолирует (он может перезапустить daemon со сбросом защиты), но готовой сессии он не получает, а сброс виден владельцу. Passkeys — позже.
- Подтверждения нельзя подделать текстом от агента: решение принимается только по нажатию в привязанном канале; запрос подписан и одноразовый. Перед исполнением одобренного действия политика проверяется заново (текущие правила, лимиты, профиль и статус агента): если теперь выходит отказ или лимит исчерпан — действие не исполняется.
- Подписанные обновления, воспроизводимые сборки, минимальная поверхность ядра; недоверенные коннекторы — в WASM-песочнице, нативный код без песочницы — только от проверенного издателя и с согласием владельца.

## Журнал и доказательства

- **Квитанция на каждое действие** — JSON (каноникализация RFC 8785): `id, ts, agent, action, args` (после маскирования), `decision {effect, rule_ids, reason}`, `approval {channel, who, at, hash превью}`, `execution {status, result_ref}` (`status`: ok | error | invalid_result | skipped | started — квитанция-намерение до исполнения | interrupted; для действий с эффектом намерение пишется до исполнения, и без него действие не исполняется; итоговая квитанция ссылается на намерение полем `intent`), `decision.errors` — ошибки вычисления условий правил, `verification {method, status, evidence_refs[]}`, `prev_hash`. Квитанции — источник истины; экспорт в OpenTelemetry (GenAI) — опционально.
- **Целостность:** цепочка хэшей + подписанные чекпоинты, связанные между собой (раз в N записей / раз в сутки, ключ Ed25519 устройства в keychain); редактирование квитанций по сроку записывается в цепочку квитанцией `journal.redact` (хэш и хэш заголовка каждой стёртой) под чекпоинтом; хэш чекпоинта отправляется на relay как свидетель (relay видит только хэши).
- **Хранение:** SQLite — индекс (время, агент, действие, решение) и зашифрованные поля (AEAD на уровне приложения); доказательства (скриншоты, ответы серверов, `.eml`) — файлы с именем по sha256, каждый зашифрован `age`, ключ хранилища в keychain. В квитанции — только хэш доказательства, поэтому файл можно удалить (crypto-shredding), а цепочка продолжит сходиться.
- **Приватность:** скриншот элемента, а не страницы; поля паролей, карт, паспорта маскируются до записи; тексты проходят тот же фильтр, что ответы агенту.
- **Сроки по умолчанию** (настраиваются): квитанции — бессрочно; доказательства `money` — 3 года; прочие доказательства — 90 дней; отказы политики (`deny`) — 1 год; отклонения и таймауты подтверждений человеком хранятся как квитанции (бессрочно). Доказательство удаляется, только когда на него не ссылается ни одна квитанция со сроком, который ещё не истёк.
- **Экспорт и резервная копия:** `gate4ai export` — подписанный архив (квитанции, доказательства, чекпоинты, публичный ключ), `gate4ai verify` проверяет его где угодно; ключ восстановления при установке и зашифрованная резервная копия.
- **Ссылки в Telegram и уведомлениях:** запросы подтверждения и отчёты содержат краткий хэш квитанции (первые 8–10 символов, например `#a3f9c21e`) вместо подробностей — сообщение не перегружено, а по хэшу запись однозначно находится в Web UI или через `gate4ai show <hash>`.

## Relay

Relay — собственная часть продукта; внешние туннели и VPN-сервисы не требуются.

- **Публичный адрес для облачных агентов.** Устройство держит исходящее соединение к relay — **WebSocket поверх TLS на 443 + мультиплексор yamux** — без открытых портов и настройки роутера. Адрес устройства `<device-id>.relay.gate4.ai` (`device-id` случайный — имена сертификатов публичны в CT-логах) вписывается в Claude.ai / ChatGPT как custom connector.
- **Шифрование до устройства — с первой версии.** TLS-passthrough по SNI (relay читает только ClientHello); сертификат выпускается на устройство (ACME DNS-01, TXT-запись ставит API relay; `certmagic`); расшифровка только на устройстве.
- **Удалённый доступ человека к своему устройству.** Подтверждения и журнал доступны с телефона или другого компьютера — на том же адресе устройства, под `/ui/`, со своей сессией. Вход — одноразовая ссылка, выданная на самом устройстве (`gate4ai ui --remote`); изменения политик, агентов и секретов удалённо недоступны. Затем — passkeys (WebAuthn) и подтверждение входа в личном Telegram-боте.
- **Один адрес, разделение по путям.** MCP, CLI агентов, Web UI и вебхук Telegram — на `<device-id>.relay.gate4.ai`; протокол relay от этого не зависит (relay не видит путей).
- **Без relay.** Технический пользователь может выставить тот же адрес сам: `gate4ai daemon --public :8443 --public-url https://… --public-cert … --public-key …` или за своим reverse proxy. Цена — открытый порт; за reverse proxy трафик видит прокси.
- **Сопряжение устройств.** Привязка телефона / второго компьютера по коду или QR, отзыв в Web UI.
- **Свидетель журнала.** Хранит хэши подписанных чекпоинтов устройства.
- **Устойчивость.** Автопереподключение устройства. Если устройство офлайн, relay держит входящее соединение до ~30 с, затем сбрасывает; очереди на relay нет (при passthrough невозможна) — агент повторяет запрос позже.
- **Размещение:** hosted relay (платная функция) или self-hosted — тот же бинарник на своём сервере.

## Коннекторы

### Общее

- Подробно — в [connector-architecture.md](connector-architecture.md); секреты и auth-модули — в [secret-architecture.md](secret-architecture.md).
- Единая модель прав для всех коннекторов, включая наши: возможности (сеть, слоты учёток, файлы, хранилище, вызовы других коннекторов) объявляются в манифесте и обеспечиваются средой исполнения; коннектор не видит секреты.
- **Недоверенный код — только `runtime: wasm`** (wazero внутри daemon, собственный ABI; пакеты подписаны Ed25519). **`runtime: native`** — отдельный процесс под надзором daemon, пакет с подписанными бинарниками под платформы gate4ai; работает без песочницы, с правами пользователя, поэтому ставится только от проверенного издателя (сейчас — только gate4.ai) и с согласием владельца. Нативные пакеты сторонних издателей пока не принимаются — если вы хотите его создать, свяжитесь с нами: мы к этому благосклонны. Песочница ОС для нативных пакетов — позже.
- **Вызовы между коннекторами:** функция хоста `service_call(target, action, input)`. Поставщик перечисляет действия, доступные другим (`services`), и номер контракта (`contract`); потребитель объявляет поставщика, контракт и параметры (например, сайты браузера) в `capabilities.services`, а **каждое своё действие — его подвызовы** (`calls: [browser.open, browser.act]`). Хост пропускает из действия только объявленные у него подвызовы; класс действия не ниже класса любого его подвызова (действие `read` не может вызвать `write`). Подвызовы видны пользователю в описании действия, в запросе подтверждения и на экране согласия, поэтому **разрешение родительского действия — правилом, по умолчанию класса или подтверждением — покрывает его объявленные подвызовы**: повторно не спрашивается. Явное правило `deny` на действие поставщика действует и во вложенном вызове. Квитанция вложенного вызова ссылается на родительскую. Изменение подвызовов в новой версии требует согласия заново. Типизированный клиент генерируется из манифеста поставщика (`gate4ai contract gen`), несовместимое изменение контракта без повышения `contract` отклоняет CI (`gate4ai contract diff`).
- Каждый коннектор публикует **манифест**: действия, схемы аргументов, класс эффекта (`read` / `write` / `external` / `money`), способ проверки результата (`verify()`), формат доказательства. Из манифестов генерируются команды `gate4ai`, MCP-инструменты, skill и формы Web UI.
- SDK коннекторов — для сообщества и для поддерживаемых платных коннекторов сервисов.
- Порядок разработки: **почта → файлы → браузер → ЖКХ / банк**.

### Почта (первый коннектор)

- IMAP/SMTP с паролем приложения: Gmail, Яндекс, Mail.ru, iCloud, Fastmail. Следом — Outlook через Microsoft Graph.
- Действия: чтение, черновики, отправка по правилам; метки происхождения для адресов из входящих писем; проверка по «Отправленным».
- Gmail API — позже (см. «Технический долг»).

### Файлы

- Часть ядра (встроенный коннектор `files`), из магазина не ставится. Только разрешённые папки (`connectors.files.roots`, по умолчанию `~`); чтение, отдельная операция `append` (добавление без перезаписи — удобный класс прав для заметок и журналов), запись.
- В свежей установке профиль `default` содержит `files` и явное правило `ask` на каждое его действие — пользователь видит инструменты и решает, что разрешить.

### Браузер

**Подключение**
- Нативный пакет `browser` из магазина (ставится по умолчанию): браузерный воркер и действия для агента — чтение без сеанса и сеанс страницы (открыть, посмотреть элементы и запросы страницы, кликнуть, ввести; страница держится до закрытия сеанса), в том числе чтобы исследовать сайт и написать по нему коннектор; другим коннекторам он даёт те же действия с открытой страницей через `service_call` (страница живёт до конца вызова вызывающего коннектора), разрешённые сайты задаёт вызывающий в своём манифесте.
- Выделенный профиль настоящего Chrome пользователя (не headless, не встроенный Chromium), подключение по CDP. С Chrome 136 удалённая отладка не работает с профилем по умолчанию, поэтому отдельный профиль обязателен. Несколько аккаунтов на одном сайте — несколько профилей (экземпляров браузерного коннектора).
- Домашний IP, настоящее железо, живые сессии — основные признаки автоматизации отсутствуют. Остаются следы CDP (тот же протокол использует Claude in Chrome) и поведение.
- Логин, пароль и PIN вводит ядро по учётке (только в поле нужного типа на origin привязки, вход атомарно, без LLM); одноразовые коды — TOTP, код из письма или SMS-код, который человек сообщает через канал подтверждений. Капчи вводит человек, войти сам он тоже может. С антибот-защитой не воюем: если сайт блокирует автоматизацию, сценарий деградирует до «данные подготовлены — откройте и нажмите сами».

**Движок: Stagehand Go SDK v4 (Browserbase)**

[Stagehand](https://github.com/browserbase/stagehand) — `act`, `observe`, `extract` на естественном языке; нативный Go SDK (`github.com/browserbase/stagehand/packages/sdk-go/v4`). Логика выполняется в расширении Stagehand Runtime, которое SDK загружает в Chrome; Go управляет им по JSON-RPC. Проверено по исходникам (коммит `f261c38`, 2026-10-10):

1. **Лицензия** — MIT; зависимости Go SDK небольшие, permissive. JS-зависимости встроенного расширения не аудировались (см. «Технический долг»).
2. **Локальная работа** — да: `ConnectLocalBrowser` к нашему профилю; LLM — свой провайдер (`ModelConfig`) или собственный обработчик `Generate` в Go. **Модель указывает пользователь** в Web UI (провайдер + ключ из Vault или локальный endpoint); в тестах — заглушка `Generate` с заранее заданными ответами. Обращения к Browserbase (серверный кэш, Model Gateway) включаются только при наличии API-ключа и сессии Browserbase — мы их не передаём; `*.browserbase.com` дополнительно закрыт в egress. Телеметрия — только при явно заданном endpoint. Кэш в v4 только серверный — не используем, наблюдённые действия храним сами (основа сценариев).
3. **Встраивание политик** — да: `Observe` → `Action {selector, method, arguments}` → Policy Engine → исполнение через `Locator` (без LLM) или `ObservedAction`. `Act` с инструкцией на естественном языке исполняется внутри расширения без точки перехвата — разрешён только для чтения и навигации. `SelfHeal` отключаем.

Условия: профиль Chrome запускаем сами с `--enable-unsafe-extension-debugging` (SDK ставит расширение через CDP `Extensions.loadUnpacked`); расширение получает `debugger` и content script на всех страницах — допустимо, так как профиль выделенный.

**Executor и сценарии**
- **Executor** — единая точка исполнения кликов, ввода, навигации.
- **Темп действий (pacing):** сейчас не реализуется; точка в Executor существует, задержки нулевые. Позже — паузы, посимвольный ввод, плавное движение мыши на уровне профиля или сайта.
- **Scenario Runner** (целевое): запись траектории → компиляция в детерминированный сценарий с переменными и политикой на каждый шаг → исполнение без LLM (через `gate4ai`) → при поломке fallback на агента с подтверждением и пересборка. Референс идеи — [workflow-use](https://github.com/browser-use/workflow-use) (AGPL-3.0 — совместима с нашей лицензией, но развитие фактически остановлено; берём как идею).

### Сервисы (ЖКХ, банк, штрафы)

- Высокоуровневые действия поверх браузерного коннектора: подготовка платежа и **чтение выписки** для проверки результата — первый сценарий класса `money`; затем показания счётчиков, квитанции (часть приходит письмами), штрафы.
- Модель «агент готовит, человек подтверждает».

## Изоляция локальных агентов

Claude Code, Codex, OpenClaw, Hermes и другие агенты запускаются **на том же компьютере, но в песочнице**. Внутри у агента полная свобода — shell, установка пакетов, работа без подтверждения каждой команды, — а всё за её пределами (файлы хоста, браузер, почта, секреты, сеть) доступно **только через gate4.ai**. Это снимает дилемму «подтверждать каждую команду» или «режим YOLO с доступом ко всему компьютеру».

### Уровни

| Уровень | Запуск | Механизм |
|---|---|---|
| 1 — по умолчанию | `gate4ai run <агент>` | процессная песочница [Anthropic sandbox-runtime](https://github.com/anthropics/sandbox-runtime) (`srt`, Apache-2.0; Seatbelt / bubblewrap, Windows — alpha); наш Egress Proxy — внешний decider для её сети; Docker не нужен |
| 2 — опция | `gate4ai run --container <агент>` | Docker / Podman |
| 3 — опция | `gate4ai run --microvm <агент>` | microVM через [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/): сеть через наш Egress Proxy, доступ к `gate4ai` |
| Облачные агенты | — | песочницы на нашей стороне нет: онбординг-чеклист (отключить родные коннекторы платформы — Gmail, Drive и т.п. — и работать через gate4.ai) |

- **Профиль песочницы** генерируется из профиля агента: запись только в рабочую папку; закрыто чтение `~/.ssh`, keychain, профилей браузеров, данных почтовых клиентов; из unix-сокетов доступен только `gate4ai`; сеть — только через Egress Proxy.
- **`gate4ai doctor`** проверяет обходные пути: агент запущен не через `gate4ai run`, доступен профиль Chrome / Claude in Chrome, токены в окружении, открыт Docker-сокет, — и показывает, как их закрыть.

### Схема (уровень 2, контейнер)

```
┌─ Хост пользователя ─────────────────────────────────────────────┐
│                                                                 │
│  ┌─ Контейнер агента ─────────────────────────┐                 │
│  │ Claude Code / Codex / OpenClaw / Hermes    │                 │
│  │ /workspace — только папка проекта (rw)     │                 │
│  │ нет: ~/.ssh, keychain, браузера, Docker    │                 │
│  └───────┬──────────────────────┬─────────────┘                 │
│          │ gate4ai: MCP или CLI │ HTTP(S)_PROXY                 │
│          ▼                      ▼                               │
│  ┌─ gate4ai daemon ──────────────────────────────────────────┐  │
│  │ MCP Front → Action Pipeline → коннекторы: файлы хоста,    │  │
│  │                               браузер, почта, сервисы     │  │
│  │ Egress Proxy → allowlist, подстановка ключей → интернет   │  │
│  │ Agent Launcher: запуск/остановка, токены, профили         │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### Как устроено

- **Запуск:** `gate4ai run claude-code --workspace ~/projects/policy` (профиль — профиль агента в политике) (Web UI или CLI). Шаблоны для популярных агентов: бинарник `gate4ai`, настроенный `gate4ai mcp` и skill. Каждый запуск — отдельный агент в журнале со своим токеном; остановка и отзыв — одной кнопкой.
- **Файлы:** доступна только рабочая папка; остальное на хосте — через коннектор «Файлы» по правилам.
- **Канал к хосту:** агент работает с `gate4ai` (MCP или CLI), `gate4ai` пересылает вызовы в daemon. Linux — unix-сокет агента, примонтированный в контейнер (`/run/user/<uid>/gate4ai/agent-<id>.sock` → `/run/gate4ai.sock`); macOS / Windows (Docker Desktop внутри VM) — проброс сокета, если работает надёжно, иначе TCP до `host.docker.internal` на отдельный порт, доступный только из docker-сети, с токеном агента в каждом запросе.
- **Сеть (Egress Proxy):** прямого выхода в интернет нет. Контейнер запускается без сети (`--network none`); внутри `gate4ai` слушает 127.0.0.1:3128 и пересылает соединения через примонтированный unix-сокет в Egress Proxy хоста. Поэтому уровень 2 пока работает только на Linux-хосте (на macOS / Windows — уровни 1 и 3). Прокси подставляет секреты только по точному origin привязки (схема, хост, порт), только по HTTPS, после проверки, что адрес назначения не loopback и не частная сеть.
  - Allowlist доменов: API модели, при необходимости реестры пакетов и `github.com`; остальное — `deny` или `ask`.
  - Подстановка секретов на выходе: внутри — одноразовая на запуск заглушка вместо API-ключа модели или GitHub-токена; при запросе к origin привязки прокси ставит заголовок с реальным ключом целиком (заглушка в другом месте запроса — отказ). Для входа по подписке (OAuth Claude Code / Codex) — тот же механизм для OAuth-токена и его обновления.
  - Журнал соединений: куда и сколько данных отправил агент.
  - Правила уровня запроса (например, «push только в свою ветку») требуют видеть содержимое HTTPS — собственный CA только для этого агента; целевая возможность, не MVP.
- **Чего у агента нет:** Docker-сокета хоста, `~/.ssh`, keychain, браузера с живыми сессиями, файлов вне рабочей папки — обойти gate4.ai «соседним путём» нельзя.

### Ограничения

- На macOS / Windows Docker Desktop — это VM: медленнее файловые операции в смонтированной папке; лицензия Docker Desktop для компаний — альтернатива Podman.
- sandbox-runtime для Windows в статусе alpha; на Windows уровень 2 (контейнер) и 3 (microVM) — полноценные альтернативы.
- Агентам, которым нужен браузер внутри песочницы, нужен отдельный образ; браузер хоста — только через браузерный коннектор.
- Правила по содержимому HTTPS требуют собственного CA и учёта certificate pinning у клиентов.

## Дорожная карта

### MVP

- Ядро + CLI `gate4ai` (JSON-вывод, коды отказов) и skill — первыми: проще отлаживать и сразу закрывает агентов с shell.
- Трей-приложение + relay; `gate4ai mcp` и remote MCP с OAuth — custom connector в Claude.ai, MCP в Claude Code и OpenClaw.
- Коннекторы: **почта** (IMAP/SMTP), **файлы** (разрешённые папки, `append`, запись с подтверждением), **браузер** (чтение и действия на разрешённых доменах в выделенном профиле Chrome).
- Политики: Web UI + файл конфигурации; подтверждения через desktop-уведомления и Telegram.
- Журнал действий с экспортом.
- **Изоляция локальных агентов — весь объём:** `gate4ai run` (sandbox-runtime), контейнеры, microVM через Docker Sandboxes, Egress Proxy с подстановкой секретов (включая OAuth-токены подписок), `gate4ai doctor`.
- Платформы: macOS, Linux, Windows.

### Этап 2

- Хранилище секретов (1Password / Bitwarden).
- Коннекторы сервисов: ЖКХ / банк (подготовка платежа, проверка по выписке), показания, квитанции, штрафы.
- Метки происхождения данных и правила по ним.

### Этап 3

- Мобильное приложение для подтверждений.
- Семейные и командные профили.
- Готовые наборы политик («безопасная почта», «финансы», «только чтение»).
- Коннекторы к открытым API (Plaid в США, Open Banking в РФ по мере появления).

## Рынок

| Категория | Примеры | Чем отличаемся |
|---|---|---|
| Мосты от платформ | Claude in Chrome, OpenClaw nodes / companion app | работают с одним агентом; правила грубые |
| Локальные MCP для облачных клиентов | LMCP, email-agent-mcp | дают доступ, не контроль |
| Туннели | Sealgate stdio tunnels, AWS AgentCore bridge, ngrok / Pinggy | инфраструктура без политик |
| Корпоративные MCP-шлюзы | Bifrost, MCPX (Lunar), Docker MCP Gateway, Peta | enterprise, RBAC/SSO, правила на уровне инструментов |
| Credential-прокси | Vultrino, Onyx «valet key», agentgateway, Infisical agent-proxy | секреты закрыты, но не потребительский продукт, нет доменных правил |
| Платёжные протоколы | Google AP2, Visa для агентов | только платежи, только через партнёрские сети |
| Песочницы агентов | Anthropic sandbox-runtime, Docker Sandboxes, dev containers | изолируют агента, но не задают правил на действия с личными данными и сервисами; используем как основу изоляции |

**Позиционирование:** единый локальный шлюз для всех агентов пользователя со смысловыми правилами (адресаты, суммы, происхождение данных), подтверждениями в мессенджере и доказательствами выполнения. «Anthropic и Docker изолируют агента; gate4.ai решает, что агент может делать с вашей жизнью за пределами песочницы».

## Риски

- **Платформы сделают своё.** Защита — независимость от агента (одни правила для всех) и глубина правил. Платформам невыгодно давать пользователю контроль над конкурентами.
- **Компьютер спит.** Агенты получают «устройство офлайн»; для бытовых сценариев рекомендуется постоянно включённое устройство (мини-ПК, Mac mini).
- **Prompt injection внутри разрешённого.** Правила ограничивают ущерб, но не исключают. Действия с деньгами — всегда с подтверждением.
- **Обход шлюза.** Если у агента есть параллельный доступ (Chrome с сессиями, shell с curl), шлюз бесполезен. Закрывается изоляцией и `gate4ai doctor`; для облачных агентов — только онбордингом (родные коннекторы платформы технически не закрыть).
- **Шлюз — единая точка отказа и атаки.** Минимальная поверхность, аудит кода, bug bounty.
- **Windows-песочница в alpha** (sandbox-runtime). Запасной путь — контейнер / microVM.
- **Хрупкость браузерных коннекторов.** Сайты меняются → постоянная поддержка. Начинать с почты и файлов.
- **Регулирование.** Персональные данные (152-ФЗ в РФ), правила сервисов (Госуслуги, банки) об автоматизации — модель «агент готовит, человек подтверждает».

## Монетизация

- **Бесплатно, open source:** локальное приложение, политики, базовые коннекторы.
- **Платно:**
  - hosted relay (без своего сервера);
  - подтверждения на телефоне, push;
  - семейные / командные профили;
  - готовые наборы политик и поддерживаемые коннекторы сервисов;
  - для РФ — бытовые сценарии (ЖКХ, штрафы, документы) поверх ядра.

## Технический долг

- **Ограничение частоты на публичном адресе:** динамическая регистрация OAuth-клиентов, ввод кода подключения, вход в Web UI, вебхук — сейчас без лимитов (коды и токены случайные и короткоживущие, но регистрация клиентов может забить память).
- **Лимиты Let's Encrypt** (50 новых сертификатов на зарегистрированный домен за 7 дней) — все устройства делят домен relay, и злоумышленник может выбрать лимит намеренно. Relay ограничивает регистрации (на адрес и в сутки) и заказы сертификатов (3 на устройство в сутки), но окончательно риск снимает только одно из решений ниже. Решения: включение домена relay в Public Suffix List, запасной ACME-CA (ZeroSSL, Google Trust Services), override у Let's Encrypt.
- **Gmail API** — ограниченные области требуют проверки OAuth и ежегодной оценки CASA; до этого Gmail работает через IMAP/SMTP (бета — до 100 тестовых пользователей в режиме тестирования).
- **Аудит лицензий JS-зависимостей** встроенного расширения Stagehand Runtime.
- **Merkle-журнал** (`golang.org/x/mod/sumdb/tlog`) — доказательство одной записи третьей стороне без раскрытия остальных.
- **QUIC-транспорт relay** — как оптимизация поверх WebSocket/TLS с автоматическим возвратом на TCP.
