# gate4ai на сервере без графики (рядом с OpenClaw)

> Исследование и дизайн. Дополняет «Режимы развёртывания» (постоянно включённое устройство), «Браузер» и «Изоляция локальных агентов» в [спецификации](specification.md). Что уже работает сегодня — помечено, остальное — доработки (список в конце).

## Задача

На VPS / домашнем сервере без X работает OpenClaw. Рядом ставим gate4ai: агент делает всё сам через браузер gate4ai под политиками, а когда нужен человек (капча, код из SMS, вход без учётки в gate4ai, «данные подготовлены — нажмите сами») — зовёт его ссылкой. По ссылке человек с телефона или ноутбука видит окно Chrome gate4ai и управляет им, затем агент продолжает.

Что есть:
- `browser.handoff` — уведомление по каналам (рабочий стол, Telegram, push, Web UI → Подтверждения) и ожидание смены адреса или элемента до 9 минут ([handoff.go](../connectors/browser/worker/handoff.go), [daemon/handoff.go](../internal/daemon/handoff.go)). Человек делает шаг «в окне Chrome gate4ai» — на сервере такого окна никто не видит.
- Chrome — настоящий, не headless, с выделенным профилем ([launcher.go](../connectors/browser/worker/launcher.go)); без `DISPLAY` он не запустится.
- Публичный адрес устройства (relay или `--public`) с `/ui/` и входом владельца (ссылка, пароль, Telegram); удалённо — только подтверждения и журнал.
- Daemon как служба: `gate4ai service install -- --keystore file` + `loginctl enable-linger` (README).
- OpenClaw узнаётся по `OPENCLAW_SHELL=exec`, есть шаблон песочницы `gate4ai run openclaw` (образ `node:24-bookworm`).

## Варианты

| | Xvfb/Xvnc + noVNC в `/ui/` (**выбран**) | CDP-screencast в Web UI | Браузер OpenClaw по `cdp_url` |
|---|---|---|---|
| Что видит человек | весь экран Chrome gate4ai: вкладки, попапы OAuth, диалоги разрешений, выбор файла | только вкладку сеанса, кадрами `Page.startScreencast` | sandbox-browser OpenClaw через его noVNC-ссылку |
| Ввод | VNC: мышь, клавиатура, буфер обмена, экранная клавиатура noVNC на телефоне | свой код: `Input.dispatchMouseEvent` / `KeyEvent`, IME и буфер обмена — вручную | noVNC OpenClaw |
| Политики gate4ai | не обходятся: агент VNC не видит, сокет — только у daemon | не обходятся | **обходятся**: агент сам управляет этим Chrome по CDP и видит cookies — против спецификации |
| Зависимости | `tigervnc-standalone-server` (или `xvfb` + `x11vnc`), noVNC (MPL-2.0) в статике Web UI | только Xvfb для headful Chrome | нет |
| Объём работы | средний: процесс дисплея, прокси websocket↔RFB, страница | большой и хрупкий: новые окна, нативные диалоги не видны | минимальный |

Удалённый рабочий стол всего сервера (xrdp, Guacamole) не рассматриваем как продуктовый путь: открывает человеку и агенту гораздо больше, чем браузер, и не связан с handoff.

## Схема

```
 телефон / ноутбук владельца                          сервер (без X)
 ┌──────────────────────┐   HTTPS   ┌──────────┐   ┌──────────────────────────────────────────────┐
 │ Telegram: «агент ждёт │──────────▶│  relay   │──▶│ пользователь ОС gate4ai                       │
 │ вас: <адрес>/ui/      │  /ui/…    │(passthru)│   │  gate4ai daemon (systemd --user, linger)      │
 │ browser/h_…»          │◀──────────│          │   │   ├ /ui/browser/<handoff> — noVNC, сессия     │
 │ noVNC в браузере      │ websocket └──────────┘   │   │  владельца; websocket ↔ unix-сокет RFB     │
 └──────────────────────┘                          │   └ пакет browser (дочерний процесс)          │
                                                    │       ├ Xvnc :N  (-rfbunixpath, без TCP)      │
                                                    │       └ Chrome (DISPLAY=:N, профиль gate4ai)  │
                                                    ├──────────────────────────────────────────────┤
                                                    │ пользователь ОС openclaw                      │
                                                    │  OpenClaw gateway → exec → `gate4ai …` CLI    │
                                                    │  (ключ агента; к Xvnc, CDP, данным gate4ai    │
                                                    │   доступа нет)                                │
                                                    └──────────────────────────────────────────────┘
```

## Поток «агент зовёт человека»

1. Агент: `gate4ai browser open --session …` → работает сам (`observe`, `act`, `login --account @…`).
2. Встретил капчу / SMS / вход без учётки: `gate4ai browser handoff --session s-… --message "Введите код из SMS"`.
3. Daemon заводит handoff `h_…`, пакет browser держит окно сеанса на переднем плане виртуального дисплея. Уведомление в Telegram-боте gate4ai, push и Web UI несёт ссылку `<публичный адрес>/ui/browser/h_…`.
4. Ссылку можно отдать и в канал самого OpenClaw (WhatsApp, Telegram и т.п.): ответ handoff возвращает её агенту (`result.user_url`). Ссылка сама доступа не даёт: страница требует сессию владельца Web UI (пароль и/или подтверждение в Telegram; на сервере одной «ссылки входа» недостаточно — её может получить агент того же пользователя ОС, поэтому мастер на сервере предлагает пароль + Telegram).
5. Человек входит, видит Chrome, делает шаг. Агент ждёт как сейчас (смена адреса / `--until_selector`), итоговый адрес проверяется по списку сайтов.
6. Handoff закончен (done / timeout / отмена) — websocket закрывается, страница показывает «агент продолжил». Вне handoff смотреть браузер можно только из локального Web UI (через ssh-туннель) или кнопкой «Посмотреть браузер» в удалённом `/ui/` — только просмотр, без ввода (решение — в правке спецификации ниже).

Блокировка: сегодня `handoff` ждёт до 9 минут и ничего не возвращает до конца. Чтобы агент успел переслать ссылку, нужен двухшаговый режим: `handoff --wait 0` сразу отвечает `{id, user_url, status: "waiting"}`, `handoff --id h_… --wait 5m` ждёт. Пока режима нет, ссылку доставляют каналы gate4ai (Telegram-бот), и этого достаточно.

## Установка (целевая)

```sh
# root
apt install -y google-chrome-stable tigervnc-standalone-server fonts-noto-color-emoji
useradd -m gate4ai && useradd -m openclaw
loginctl enable-linger gate4ai

# пользователь gate4ai
curl -fsSL https://gate4.ai/install.sh | GATE4AI_NO_OPEN=1 sh
gate4ai service install -- --keystore file
gate4ai relay register --url https://relay.gate4.ai      # публичный адрес: /ui/ и CLI агентов
gate4ai ui --remote                                       # ссылка/QR: войти с телефона, задать пароль, подключить Telegram
# пакет browser сам видит, что DISPLAY нет, и поднимает Xvnc (настройка display: auto | virtual | host)

# пользователь openclaw
curl -fsSL https://gate4.ai/install.sh | GATE4AI_NO_START=1 GATE4AI_NO_OPEN=1 sh   # нужен только CLI
export GATE4AI_URL=https://<device-id>.relay.gate4.ai
gate4ai pair --wait 5m                                    # код подтвердить в Web UI / Telegram
gate4ai skill > ~/.openclaw/skills/gate4ai/SKILL.md
# в настройках OpenClaw выключить его собственный браузер для сайтов с личными данными (или целиком)
```

Сегодня работает всё, кроме виртуального дисплея и `/ui/browser/…`: можно поставить daemon, relay, Telegram и подключить OpenClaw; браузер запустится, если вручную поднять `Xvfb :99` и задать службе `DISPLAY=:99` (окно при этом никто не видит, handoff бесполезен).

Почему отдельный пользователь ОС для OpenClaw: агент OpenClaw — это shell. Процесс того же пользователя может читать данные gate4ai, подключиться к сокету VNC и к порту отладки Chrome — то есть обойти политики. Отдельный пользователь закрывает файлы и unix-сокеты (права `0600` / `0700`). Альтернатива — `gate4ai run openclaw --container`: сокет агента и токен монтируются в контейнер.

Сокет агентов сейчас `0600` — другой пользователь ОС до него не дотянется, поэтому OpenClaw ходит по `GATE4AI_URL` через relay (лишний круг через интернет, но без открытых портов). Доработка ниже — групповой сокет агентов.

## Безопасность

- **Порт отладки Chrome.** `--remote-debugging-port=0 --remote-debugging-address=127.0.0.1` — TCP на localhost без аутентификации: на многопользовательском сервере к нему может подключиться любой локальный процесс, включая OpenClaw другого пользователя, и управлять профилем с живыми сессиями. На ноутбуке это риск того же пользователя, на сервере — главный обход. Закрыть: `--remote-debugging-pipe` (если Stagehand Go SDK примет транспорт поверх pipe; иначе — свой мост pipe → unix-сокет 0600 для SDK) или отдельный network namespace пакета; запасной вариант — правило `iptables -m owner --uid-owner gate4ai` на петле.
- **VNC.** Xvnc слушает только unix-сокет в каталоге пакета (`0700`), TCP выключен (`-nolisten tcp`, без `-rfbport`), `-SecurityTypes None` допустим, потому что доступ даёт файловое право. Наружу RFB идёт только через daemon: websocket `/ui/browser/<id>/ws` с сессией владельца, проверкой `Origin` и привязкой к активному handoff.
- **Канал.** relay — passthrough TLS: кадры экрана и ввод relay не видит.
- **Журнал.** Открытие и закрытие просмотра, вход в `/ui/browser/…` — записи журнала (кто, откуда, какой handoff); ввод человека не журналируется (там пароли).
- **Что видит человек.** Весь виртуальный экран Chrome gate4ai, включая вкладки других сеансов. Это профиль владельца — допустимо; агенту экран не отдаётся (скриншоты — по-прежнему `page_screenshot` своего сеанса).
- **IP сервера.** На VPS теряется «домашний IP» из спецификации: сайты с антифродом (госуслуги, банки) чаще просят капчу или блокируют. handoff как раз закрывает капчу; для жёстких сайтов — сервер дома или исходящий прокси через домашнюю сеть (вне этого дизайна).

## Доработки (отдельные задачи)

1. **Виртуальный дисплей в пакете browser.** Настройка `display: auto | virtual | host` (auto: нет `DISPLAY`/`WAYLAND_DISPLAY` на Linux → virtual). Пакет запускает `Xvnc :N -geometry 1280x900 -depth 24 -rfbunixpath <dir>/vnc.sock -SecurityTypes None -nolisten tcp` (запасной путь — `Xvfb` + `x11vnc -unixsock`), ждёт готовности, запускает Chrome с `DISPLAY=:N` и `--start-maximized`; падение Xvnc — перезапуск вместе с Chrome; остановка пакета гасит оба. Нет Xvnc в системе — понятная ошибка с подсказкой `apt install tigervnc-standalone-server`. Путь к сокету — в ответе служебного вызова пакета daemon.
2. **Просмотр в Web UI.** Встроить noVNC (MPL-2.0, статикой; лицензию — в NOTICE), страница `/ui/browser/<handoff>` и websocket-мост к RFB-сокету в daemon (Go, без websockify). Масштаб под экран телефона (`resize=scale`), кнопка экранной клавиатуры, «Готово» (досрочно завершить ожидание) и «Отклонить» (агент получает `status: "declined"`).
3. **Ссылка в handoff.** Уведомления (Telegram, push, Web UI) несут `<публичный адрес>/ui/browser/<id>`, если публичный адрес есть; иначе — локальный адрес и текст «откройте через ssh -L 7431:127.0.0.1:7431». Ответ handoff — `user_url`; двухшаговый режим `--wait 0` / `--id`.
4. **Закрыть порт отладки Chrome** (см. «Безопасность») — нужно и на ноутбуке.
5. **Групповой сокет агентов** (опция `--agent-socket-group openclaw`, права `0660`): OpenClaw другого пользователя ходит локально, без relay. Опознание агента по процессам другого пользователя не работает — только ключ агента.
6. **Мастер «Сервер»** в Web UI и `gate4ai doctor`: нет X → предложить виртуальный дисплей, пароль + Telegram для входа, отдельного пользователя ОС для агента; предупредить, если агент того же пользователя.
7. **SKILL.md:** для handoff — «отправь пользователю `user_url` в свой канал, если он не ответил в Telegram gate4ai»; не просить пароли в чате (уже есть).
8. **e2e:** handoff на стенде без X: Xvnc поднимается, `/ui/browser/<id>` без сессии — 401/редирект на вход, с сессией — websocket отдаёт RFB-рукопожатие (`RFB 003.008`), по завершении handoff — закрывается.

## Правки спецификации (нужно согласие владельца)

- «Браузер → Подключение»: на Linux без графического сеанса пакет запускает Chrome на виртуальном дисплее (Xvnc), человек видит его в Web UI.
- «Удалённый доступ человека»: кроме подтверждений и журнала, удалённо доступен экран браузера gate4ai — с вводом только во время активного handoff, вне его — только просмотр.
- «Режимы развёртывания», п. 2: сервер без графики, агент — отдельным пользователем ОС или в `gate4ai run`.
- «Связь между процессами»: исключение «TCP на localhost без аутентификации не используется нигде» сейчас нарушает порт отладки Chrome — либо закрыть (доработка 4), либо записать исключение.
